# Work the drain sets aside leaves no ref

Settles issue #328. Read with ADR 0023, whose point 9 says an interrupted drain loses no work. Amends `skills/feature/SKILL.md`, `skills/method/pipeline.md`, `skills/method/route.md` and `docs/model/drain.md` where they said the drain stashes.

**What was asked.** When the drain closes a ticket, or removes the work tree of an interrupted run, it set aside what the tree held uncommitted as a git stash. A stash is a commit under `refs/stash`. In an adopted project, a gate that reads the repository's history judged every reachable commit, so one parked ticket's uncommitted test, which held a made-up value shaped like a live key, turned that gate red for every later ticket, on a commit that was on none of their branches. The plugin cannot know which refs or paths a project's gates read, so the fix is that the plugin keeps none of its own state in the repository's refs.

## Decision

**1. The drain sets work aside as a file, not a stash.** What one closing of one ticket sets aside is one unit, however many passes it takes, and a unit is one file: `<git common directory>/ratchet-kept/<branch>/<n>-<time>-<id>.kept`, with each `/` of the branch written as `-` and `n` one more than the branch's last unit, so the units sort in the order they were made. Its first line is JSON: the commit the work was on (`base`), the tree of the index, the tree of the work tree (the tracked files as they were there, and the untracked files that are not ignored), and the length of each of two patches. The two patches follow, both from `base`, one to each tree, written by `git diff-tree --binary --full-index`. Together they hold staged and unstaged changes, untracked files, deletions, binary files, file modes, symbolic links and any file name. For a work tree the `id` is random, and the drain writes it to `ratchet-kept` in the tree's own directory under the git directory before it writes the file, so every pass and every rerun for that tree writes to the same unit, and the `id` goes when the tree is removed. A unit moved from an old stash takes the stash's commit as its `id`. Nothing reachable from any ref holds the work.

What the drain removes with the tree and does not keep is what a stash left out at `origin/main` too, so a close loses nothing it lost before: ignored files, an untracked nested repository with all its work, and empty directories. An untracked file whose path has a line-ending attribute comes back with the line endings the attribute names, not the ones it had (with `text eol=crlf`, a file written with LF comes back with CRLF), as it did from a stash.

**2. Nothing leaves the work tree before the unit is proved.** The steps of one pass, and what holds the work after each:

| Step | What holds the work after it |
| --- | --- |
| 1. The note says the ticket is closing (`discarding`), as before | the work tree |
| 2. The drain reads the tree's index and files into a scratch index and a scratch object directory. A tree whose `index.lock` exists is left as it is | the work tree |
| 3. It reads the tree's unit `id`, or writes a new one | the work tree |
| 4. When the unit has a file from an earlier pass, or `.partial` files a killed pass left, it lays the tree over what each gives back, newest first: each path where the tree differs from `HEAD` takes the tree's entry, and every other path keeps the file's. A `.partial` file that was cut short gives nothing back and is skipped. When the unit has a file, no `.partial` file is left and that changes nothing, it writes nothing | the work tree, the unit, and any `.partial` file |
| 5. It writes the unit under a new `.partial` name of its own, applies both patches to `base` in a fresh scratch index and object directory, compares each tree with the one it means to keep, and only then renames the file to the unit's name and removes the unit's older `.partial` files, whose work the unit now holds | the work tree, and the unit |
| 6. It puts the work tree back to `HEAD` (`reset --hard`, then `clean -d`) | the unit |
| 7. It ends the programs that still run from the tree, and sets aside what they wrote since by steps 2 to 6, into the same unit | the unit |
| 8. It prints the unit's line, removes the work tree, and drops the note's `discarding` | the unit |

If step 2, 4 or 5 fails, such as a held `index.lock`, a merge left unfinished, a file that cannot be written or read back, a disk that is full, or a proof that does not give the same trees, the drain removes the `.partial` file it wrote, leaves the work tree and any older `.partial` file as they are, and prints `kept: the work tree stays at <tree>: <why>`. A unit is never replaced by a file that is not proved, so what an earlier pass set aside stays in it, and its line is printed too.

A kill at any point leaves the work in the tree, in the unit, or both, and leaves no lock: the drain takes none of git's, and its own is the drain lock of ADR 0023, which the kernel releases when its holder dies. Git's commands take `index.lock` for the instant they need it, and a program still writing in the tree is ended before the second pass, which keeps what it wrote. The next drain command that finishes the close, or `clean --all`, reads the same `id`, lays what the tree still holds over the unit and over each `.partial` file of that `id` the kill left, and finds nothing new or the rest. A `.partial` file is never written over, whatever the clock says, and goes only once the proved unit holds its work. So a rerun converges on one unit, no `.partial` file and no tree, and the line names that unit on the first run and on every rerun. When the tree is gone before the rerun, so that its `id` went with it, the rerun names the newest unit of the branch.

No object of the set-aside work is written to the repository's object store. The scratch object directory borrows the repository's objects for reading (`GIT_OBJECT_DIRECTORY` with `GIT_ALTERNATE_OBJECT_DIRECTORIES`), and it is deleted with the scratch index.

**3. One command puts it back.** `drain.py restore <branch>` takes the oldest unit of that branch and refuses a checkout that holds uncommitted work of its own. It switches the checkout to the branch when the branch is still at `base`, and to `base` otherwise, then checks that both patches apply, the first to the index and the second to the files, applies both, and reads the checkout's index and files back into a scratch index. It deletes the unit only when both applied and the two trees it reads are the unit's. If any of this fails, such as a folder the checkout cannot write, it puts the checkout back (`reset --hard`, `clean -d`, and a switch to where it was), keeps the unit, exits 1, and prints one line: `restore: <file> <why>, so it stays and the checkout is as it was: once the checkout can take it, run drain.py restore <branch> again`. The checkout held no uncommitted work of its own, so that puts back only what the restore wrote. When it succeeds it names the unit, and names the next unit of the branch and how many stay. A unit it cannot read gets one line that names the file and says to run the command again once the file can be read. A second restore with nothing left says so and changes nothing. Each line the drain prints about set-aside work names the unit and this command: `kept: what the work tree of <branch> held uncommitted is set aside at <file>: drain.py restore <branch> puts it back in the checkout`.

**4. The drain's old stashes move when the drain can prove it made them.** The drain at `origin/main` recorded nothing of a stash it made: its note holds no stash commit, and the commit holds nothing of who made it. It labelled the stash `<branch>: <word> run`, and four of its words are written by nothing else: `merged`, `unapproved`, `split` and `interrupted`. The fifth, `blocked`, is also what `/ratchet:feature` writes when it sets a blocked run aside, and the route holds that ticket on it. On each `clean` and `restore`, the drain reads the stash list, oldest first. It moves a stash only when its message is exactly `On <branch>: <branch>: <word> run`, the word is one of the four and is the one for the outcome the branch's note records (`interrupted` when it records none), and the commit the stash was made on is the `head` of the start the note records. A stash made on a detached head, a stash the owner made with an `interrupted` label on a branch the drain closed, and one made on a commit the note does not record all stay. Each such stash becomes its own unit by steps 4 and 5, with the stash's commit as its `id`, and only then is it dropped, so a rerun after a kill between the two writes the same unit again and drops the stash. Every other stash whose message has that form stays, `blocked` among them, and the drain prints one line for it: ``kept: stash <commit> (`<message>`) stays: nothing the drain recorded proves the drain made it; to move it by hand, run `git stash pop --index stash@{<n>}` in a clean checkout of `<branch>` ``. Every other stash is left alone, and the route's reader of blocked runs gives the same answer before and after each drain command.

**5. What stays a stash.** The split's landing keeps its check that the commit hooks did not move `refs/stash` (`harmed`): that stash is the owner's, in the owner's checkout, and the check protects it. A `/ratchet:feature` run that is not approved is still stashed by the orchestrator as its skill says, and the route still holds that ticket on its `blocked` stash. Moving that stash out of the refs is the same class of defect, and it is a follow-up unit, since it needs a command for the orchestrator and a new reader in the route.

## What a project sees

A parked, waiting, split, merged or interrupted ticket no longer adds a commit to `refs/stash`, and a gate that reads every reachable commit judges the next ticket on its own commits. The `kept:` line says where the work went and how to get it back. The route and the plan hold a parked ticket by its note, as before, so nothing a project sees about holds changes.

## What an upgrade does

The first `clean` after the upgrade moves the stashes the drain can prove it made into units, oldest first, so `restore` gives them back in the order they were made, and the gate that read them goes green on the next run. A stash with the drain's message that it cannot prove is its own, each `blocked` one included, stays and is named on every `clean` and `restore` until the owner moves it by hand.

## Known limits

A gate that reads files under the git directory, rather than the history, still sees the units. A project with such a gate excludes `ratchet-kept/` under the git directory from it, or restores and removes the kept work it no longer needs. A unit holds patches against `base`: if that commit is no longer in the repository, `restore` says the unit does not apply and keeps it, and `git apply` onto another commit is the way back.

A gate that reads every object, reachable or not, still sees what an agent staged with `git add` in the tree: git wrote those blobs to the repository's store when the agent staged them, before the drain ran, and they stay there, unreachable, until git prunes them (`gc.pruneExpire`, two weeks by default). The drain adds nothing to the store. A restore writes the staged part back to the store, as staging it again does. Likewise, the objects of a stash the drain moves stay in the store, unreachable, until git prunes them.

A role that writes a file, or runs `git add`, after the drain has proved the unit and before it resets the tree loses that write, as a write made while `git stash push` ran, between its save and its reset, was lost at `origin/main`. The drain ends the programs that run from the tree only after the reset.

## Evidence

`hooks/tests/test_drain_kept.py` closes a ticket with each outcome and walks every object reachable from every ref and reflog for a marker of the uncommitted work: none holds it, no object in the store holds an unstaged or untracked file of it, and a stand-in gate that fails on any reachable commit holding it is green in the next ticket's tree. A restore gives back the same index tree, the same files and the same executable bits, for staged, unstaged and untracked files, a deletion, a binary file, a file name with a space and one with a newline. A file that cannot be written or read back, a full disk, or a proof that fails leaves the work in its tree with the `kept: the work tree stays at` line and no `.partial` file, and a later `clean --all` sets it aside. A close killed at each boundary between two effects, from naming the unit to removing the tree, between the reset and the clean, and in a second pass that keeps what a program wrote late, reruns to one unit that every line names and no tree, and the restore gives back the tree byte for byte, the late file with it; a second restore says nothing is set aside and changes nothing. A close killed outright while it proves its file leaves nothing the rerun waits on. A second pass that cannot be kept leaves the tree with what came late. Two closings of one branch are two units, which `restore` gives back oldest first, naming the one it took and the next. A unit that meets an ignored file in the checkout restores nothing and switches the checkout back. A restore into a folder the checkout cannot write, an apply to the files that fails, and one that says it applied but wrote nothing each keep the unit, leave the checkout as it was, and print the line that names the unit and the command. A close killed while it writes its `.partial` file, once it is written, or while it proves it, reruns under a clock that moves to one unit and no `.partial` file, and a `.partial` file holding a file the tree has since lost gives that file to the unit. A rerun after the tree was removed between two passes names the unit. A unit that cannot be read, or was cut short, gets one line. A detached stash made in another ticket's tree, an `interrupted` stash the owner made on a branch the drain closed, and a stash made on a commit the note does not record each stay and are named. A stash `/ratchet:feature` made on a branch the drain opened stays through `clean`, `clean --all` and `restore`, and `route.blocked_runs` reads the same before and after. The drain's model is unchanged: its stash is the set-aside unit, and step 6 is why a kill after it leaves a clean tree, as the model says.

## Refutation criterion

This is wrong if a drain loses uncommitted work that a stash would have kept, or if `restore` gives back a tree other than the one the drain set aside. It is also wrong if an adopted project's gates go red on the kept files often enough that the known limit costs more than the stash did: count the projects that have to exclude `ratchet-kept/` in the first ten that upgrade.

## Considered options

- **Tell the history gate to scan only the change's own commits (`<base>..HEAD`) in tier 0.** Declined as the fix. The plugin names no gate's tool and cannot know which refs a project's gates read, and any other ref the plugin wrote would hit the same gate.
- **Run the gate over the stash at `close` and warn.** Rejected. It names the harm and leaves it in place for every later ticket.
- **A stash commit kept in a ref of the plugin's own, such as `refs/ratchet/kept`.** Rejected. A gate that reads every ref reads it too.
- **Keep the objects as a pack file.** Rejected. Patches can be read and applied with git alone, and the proof that applies them to `base` tests the file itself, not objects the repository already holds.
