# An agent adds to a record, and only the owner changes one

`GLOSSARY.md` and `docs/adr/**` sat in the `decisions` group, so every edit of either asked the owner. The owner reported approving each new term and each new ADR as an interruption with nothing to decide in it, and ADR 0013 named the same cost as its known residue: in the trial of 2026-11-11 the first owner-away `/ratchet:feature` stopped at its spec stage, and one of the guard edits it stopped on was a glossary entry.

We decided that a guard group can be marked `edit = "append"`, and that the template manifest puts `docs/adr/**` and `GLOSSARY.md` in such a group, `records`, split out of `decisions`. On those paths an addition passes without a prompt and everything else asks as before. One function, `ratchet_guards.records.additions`, tells the two apart, and the hook and `guard-diff` both call it against the same "before": the file at the merge base of `HEAD` with the default branch. The work tree is not the standard, so a branch may rework a term or a record it added itself, as when the conformance gate sends an agent back to its own ADR for a missing refutation criterion. The default branch's tip is not the standard either, so a branch that has not caught up is not refused for lacking terms it never had.

An addition to a glossary leaves everything the merge base holds in place, in order and under the same heading: every term with the lines that define it, every item of every `_Avoid_` list, every heading, every line outside the entries. What comes in is a term, an `_Avoid_` item or a cluster heading. An addition to the decision records is a new file named `NNNN-<slug>.md` whose number is above every number the merge base holds, with a title, with no `Relaxes:` line (the `ratchet-lowered` gate reads one as leave to loosen a threshold) and without the word "supersede" in any form. What the function cannot read is not an addition: a term defined twice, in any case or spacing; a new term an `_Avoid_` list bans, or a new `_Avoid_` item that bans a term; an indented term, heading or `_Avoid_` line; a line break that is not a newline; a code fence or an HTML comment in new text; a new glossary file; a tool call whose result the hook cannot compute. Each is a way to make a changed record look like an addition, and each is a row in `hooks/tests/test_records.py`.

The permission rules change with it. `settings_rules.py` writes no `Edit` rule for an append group, because a rule matches a path and cannot read the edit: an `ask` there would prompt for the additions the hook lets through, as a `deny` on `gh label create` would have refused the recorded label (ADR 0006). On these paths the hook is therefore the only layer in the harness. The cost is that where the hook does not run (a harness that does not load the plugin's hooks, a session started with hooks off) an edit of a record meets no prompt, where the permission rule used to ask. `guard-diff` stands behind it: it lists and counts every changed record, prints `additions:` with each term, `_Avoid_` item and ADR that came in or `not additive:` with the reason, and with `--fail-unless-additive` exits 1 on any guard path that changed other than by an addition. The pipeline treats an `additions:` path as no guard change, the spec role adds the term it needs instead of returning it as a guard edit, and the pull request's Decisions section lists every addition. A shell write to these paths is denied as before. Decided 2026-11-11.

An adopted repository gets this when its owner moves the two patterns into a group marked `edit = "append"` and runs `just settings`; the manifest is locked, so that change is the owner's.

## Refutation criterion

This is wrong if a changed record reaches the default branch as an addition. The standing attempt is the property test in `hooks/tests/test_records.py`: it edits a glossary at random and, for every edit the function accepts, compares the banned words and the lines before and after with readers that share no code with the function (the prose gate's, and a plain line comparison). One accepted edit that loses a banned word or a line refutes the parser, and the two patterns go back to `ask` until it is fixed. It is also wrong if additions carry decisions the owner would have refused: read the Decisions section of the first ten pull requests built this way, and if the owner reverts or rewrites more than one added term or ADR in five, an addition is not cheap to take back and the group returns to `ask`.

Known residue, shown in the pull request and caught by no gate. An added term can restate a concept the glossary already names under another word. A new ADR can contradict an old one without saying so. The function reads lines, not meaning and not rendered Markdown; the critic and the reviewer are told to read each addition against the records, and that is criticism, not a gate. Two branches can each add an ADR under the same next number, and the conformance gate goes red on the second to merge. Only Claude Code's Edit, Write and MultiEdit are computed: Grok's own edit tools, a Codex patch, and the pi and OpenCode adapters, which send the path alone, still ask on every record edit. The "before" is read through the default branch's ref, as the committed manifest is, and a ref moved back would make every term merged since read as the branch's own. ADR 0016 closes that: the hook refuses a command that moves the ref, in every spelling it reads, so what is left is its known residue (a ref name or a script the hook cannot read). A forge compares with its own copy of the default branch, so `guard-diff` in CI still names the change; a repository with no forge has no second reader. The pipeline's script reads the `additions:` note as its reviewer relays it, as it reads dependency notes (ADR 0011); `--fail-unless-additive` is the exit code for a check that must not rest on an agent's report.

## Considered options

- Keep asking and collect the prompts at the end of a run: rejected, an owner-away run has nobody to ask, and the stop at the spec stage is the cost being removed.
- Drop the two paths from the manifest: rejected, an agent could then rewrite a definition, shorten an `_Avoid_` list a fitness test enforces, or write the `Relaxes:` line the lowered gate honours.
- Let the pipeline cover the path on the spec's word, as it covers a dependency the spec named (ADR 0011): rejected, the spec role is the agent whose edit is being judged, and "it only adds" is a property a function can decide.
- Compare with the work tree in the hook: rejected. It is safe, since additions compose, but an agent's second edit of its own new ADR would ask, and the gates send agents back to their own records.
- Compare with the tip of the default branch: rejected, with branches built in parallel the tip gains terms a branch lacks, and every later addition on that branch would read as a removal.
- Keep an `ask` permission rule beside the hook: rejected, the rule prompts on every edit, additive or not, which is the state this decision leaves.
- Judge by the diff, passing a change with only added lines: rejected, an `_Avoid_` item is added inside a line, and an added line can be a second definition of an existing term or a heading that moves the terms below it.
