# The spec is checked against the ticket before the build

The pipeline writes a spec from the ticket, builds to the spec, and the review judged the build against the spec. Before this decision no role after the spec read the ticket. A spec that dropped or bent a promise of the ticket was built to the letter, every check passed, and the owner got something he had not asked for. An audit of the method's promise, that the owner need not review the code, named this its weakest point.

A prototype on 2026-11-13 checked the spec of a test project's first ticket (a read-later list) against the ticket, with one agent that read only the two. It took 1.9 minutes and 57k tokens. It found that one ticket promise, "no client JavaScript", had no criterion: the spec said it only in its Problem and Out of scope sections. It found that an assumption in the spec, "ticket 01 saves whatever is pasted", decided two real defects: a blank link and a `javascript:` link were both saved. It did not find what the ticket never mentioned, cross-site posts and input length.

A first version put the check in the review alone. An independent verification traced what happened when it found something: nothing repaired it. The review filed the issue and the script forced `request_changes`. With the critic off, Critique and Fix did not run, and with it on, the fix loop fixes only the critic's findings. The owner got a stash and an issue title, and his only move was a rerun whose spec role never saw the finding. On the spec that test project's spec role really wrote, every ticket that accepts input would have stopped this way. One of three readings of a faithful spec took a sentence about what a gate charges for a product promise the spec bent. A check that stops the owner's work on a reading he cannot judge gets in his way.

## Decision

**A ticket check runs after Spec and before Implement.** One agent reads the ticket and `spec.md`, and no code, no tests and no other record. It returns two axes. `ticketPromises` gives each promise of the ticket in the ticket's words, read as `covered` (with the criteria that carry it), `dropped`, `bent` (with what the spec says instead) or `assumed` (with what the owner would see). Each reading except `covered` quotes the spec line it rests on. `acceptedInputs` gives, for each thing the change lets users or other systems send the running product, a plain name a person who cannot read code would recognise ("the link you paste"), and the criterion that decides an empty, an oversized and a hostile value, or null. The owner reads each input by that name: before it, an assumption read "What the app does when The `POST /items` request body as a whole (the form post carrying `link`) is far longer than anyone would type". A sentence about how the method treats the work, such as what a gate charges, is no promise. A header the change itself checks to guard the product, such as an `Origin` check that refuses cross-site posts, is no input: one of two checks of a fresh spec counted one, and sent its cases back as gaps.

**A gap goes back to the spec role once.** A promise read `dropped` or `bent`, or an input case no criterion decides, goes to the spec role with the findings in hand. It closes each gap with the smallest change that makes the plan do what this ticket says, or that makes an accepted input safe, and changes nothing the gaps do not touch: every other criterion keeps its wording exactly. In 2 of 10 real amends an earlier wording let it split criteria the gaps did not touch. It decides an input case itself with the narrowest safe answer: for an empty value nothing is saved and nothing breaks, an oversized one is refused with a message that keeps what the user typed, and a hostile one is kept as plain text that does nothing. A message or a rule for an empty value is a product another ticket may promise. It never brings forward what another ticket of the feature promises; when the smallest safe answer overlaps another ticket, it takes the narrower answer and names that ticket in the assumption. In all eight sampled amends of the version before this rule, the plan brought a later ticket's rule forward to close a gap (refusing a link that is not a web link when it is saved). Of 10 real amends under it, 9 took the narrower answer and named the later ticket, 1 still brought its rule forward, and none asked the owner. An amend took 2.9 to 5.5 minutes and the second check 0.6 to 0.9. It leaves a finding it reads otherwise, and the check reads the amended spec once more. No code exists yet, so nothing is thrown away.

**After the amend the run decides, and asks the owner nothing.** A promise still `dropped` is kept from the ticket. The readings the script settles say, in the ticket's own words, that the app does it. The implementer is told to build it with a test that fails without it, the review judges the build against it, and the pull request lists it with the run's other assumptions: "the plan left this out, so it was built as your ticket says". The owner overrules it as he overrules any assumption. A ticket line about how the change is built, such as a tool to run, is kept the same way and never reaches him as a question. A case still undecided is kept the same way with the safe answer: the script writes it into the settled readings, the implementer builds it, the review judges the build against that text, and the pull request lists it under the input's plain name with its refuter. An input case that is a real product choice, where the safe answer takes something from the user (refusing an empty value that clears a note, or a limit that loses what the user typed), is the spec role's to raise as a `direction` question under the fork test. So is a promise the role believes cannot or should not be built as written; it is raised, never left out. These questions, and the spec role's others when the ticket contradicts itself, still stop the run before the build. A promise still read as `bent` is a reading the check and the spec role do not share. It joins the assumptions the pull request lists, and holds nothing.

**The review stays the backstop, with a narrower job.** The review reads the ticket and receives the readings the check settled, and does not argue them again. It judges whether the change, as built, still keeps each promise and decides each input case as `spec.md` states, or as the settled reading states where the run kept the promise from the ticket or assumed the case. A second review, of a branch brought up to date behind another merge, is held to the same readings: the skill passes back the first result's `settled`. Without them, all three real second reviews of a run that had assumed the link field's cases read each case as undecided, and the script refused the change, which parks the ticket in a drain with nothing for the owner to answer. A `dropped` promise or a null case there means the build lost what the spec had. The script files it as a major issue, the verdict record lists it as unresolved, and the merge judge refuses. A `bent` reading at the review joins the assumptions and holds no merge. The result's `ticketFindings` carry what was lost. The `/ratchet:feature` skill builds the ticket again once with them in `args.ticketFindings`, so the next spec role starts from them.

**The ticket is read as the owner agreed it.** The spec role, the check and the review read a local ticket file as the base branch holds it (`git show <base>:<path>`), not the copy in the working tree that an agent of the run could have edited. A tracker issue is read with `gh issue view`. An agent can still edit an issue's body or add a comment under the owner's token, and nothing records what the owner agreed. A hash of the body and comments recorded at the preflight would; it is parked.

**What the schema holds, and what it cannot.** The check and the review share one definition of the two axes. The schema makes each role answer both and gives each reading the evidence that shows it. It cannot make an answer complete: a list that leaves a promise out fits it, and so does an empty `acceptedInputs`. Completeness rests on the prompt and on two independent reads.

**What it costs.** The check is one more agent on every run that builds a ticket, and two more when it finds a gap. A run spawns at most seven agents before the project is `depended-on` (preflight, spec, check, amend, second check, implement, review) and at most twelve after, where it spawned four and nine. A run whose check finds nothing spawns five before `depended-on`, and six after when the critic leaves nothing to fix. In the samples of the test project's first ticket, a check took 0.6 to 1.1 minutes (median 0.7, 32 runs) and an amend 2.9 to 6.9 minutes (median 3.5, 8 runs), with the amend's file writes and test runs simulated. All five checks of a faithful spec found no gap, so a run of a good spec pays one agent and about a minute, and a run whose spec has a gap pays three agents and about 4 to 9 minutes. `AGENTS_AT_MOST` in `workflows/pipeline.js` declares the numbers, `scripts/drain.py` reads them, and a test counts a worst-case run against them. This supersedes the counts ADR 0023 states in decision 3: a pipeline is at most seven agents before `depended-on` and twelve after, and a drain of N tickets at most 9N - 2 and 14N - 2. It also supersedes ADR 0028's sentence that before `depended-on` a ticket is built by spec, implement and review: the ticket check runs between Spec and Implement on every run that builds a ticket.

## Refutation criterion

This is wrong if the owner overrules more than one in three of the promises the run kept from the ticket, the `bent` assumptions and the assumed input cases the check leaves him over the next ten tickets. Then the check reports readings, not promises, and must decide less. It is also wrong if a promise the run kept from the ticket is one the owner did not want built, and he could have said so in one answer before the build: then a promise still left out needs his question after all. It is also wrong if a change merged after this decision lacks a promise its ticket made while both the check and the review called it `covered`. Then two reads of the same spec share its blind spot, and the promise needs a role that runs the built product, after Implement.

## Considered options

- **Check only in the review.** The first version. Rejected by the trace above: the review comes after the code, and nothing between the review and the merge repairs a spec.
- **Thread the ticket text through the run.** Rejected. The script cannot read the tracker, and only an agent could relay the text. An agent's copy would be one more thing the reader must trust.
- **Ask in the prompt alone.** Rejected. A role could skip an axis and still return a valid result. The schema makes each axis required.
- **Have the reviewer file the findings in `issues` itself.** Rejected. The reviewer could read a promise as dropped and file nothing. The script derives the issues from the readings, so the reading alone decides.
- **Ask the owner about a promise still left out.** The version before this one asked: "Your ticket says "…", but the plan leaves that out, so the app would be built without it; is that what you want?" It asked him to confirm what his ticket already says. Its recommended answer was always to build it as the ticket says, and he had to answer "No" to get what he asked for. Over the 42 real check readings of the test project's first ticket, fed to that script as both the first and the second check, it would have stopped 6 runs with 7 questions. One quoted a build step naming a tool (`impeccable shape`). In the 10 real second checks after an amend it stopped once, on the promise that the phone and the laptop see the same list, which criterion 10 of that plan carries: a second app over the same database file shows the same list. Rejected: an agent would build it as the ticket says anyway, and the owner can still overrule it in the pull request.
- **Stop on a `bent` reading after the amend.** Rejected. The check reads `bent` where a spec keeps a promise in a way it would not have chosen. On the test project's ticket it read the new-tab promise as `bent` against a criterion that shows a non-web link as plain text: once on a faithful spec, and once on the spec an amend had just repaired. A stop there would halt the owner's work on a reading he can judge in one look. He sees it as an assumption and counters it if it is wrong.
- **Skip the check when the ticket promises nothing the product shows.** Rejected. Every ticket promises something, and the check reads two documents and no code.
