# A guard reads a name the way what acts on it does

The plugin is about to be published, so its guards must hold against an agent that tries to get round them, and no longer only against one that slips. An adversarial review on 2026-11-12 found eleven ways round, in the hook, the merge job, the queue, the additive-records check, the merge judge and the bite proof. Closing them turned up more of the same kind. They share one cause. Each guard read a spelling: a ref name, a directory, a variable, a run's branch, a line of Markdown, a path. What acts on that spelling reads it by rules of its own. Git matches a pushed name against tags, heads and remotes in turn, works on whatever repository `GIT_DIR` names, and shows a symbolic link's target as a file's text. A shell that fails to `cd` runs the next command where it stood. The forge lists on a run every open pull request that has the run's head commit. A Markdown renderer makes a heading of a line with `===` under it. The filesystem follows a link. Where the guard's reading and the actor's differed, the difference was a way through.

We decided that a guard reads a name the way what acts on it does: it asks that actor where it can, and where it cannot it takes the reading that protects, or refuses. Nine parts carry it.

First, a pushed or fetched name is every ref git may match it to (`ratchet_guards.refs.pushed`): `refs/<name>`, `refs/tags/<name>`, `refs/heads/<name>`, and `refs/remotes/<name>` with its `HEAD` when the name begins with `origin`. A source-only refspec, `tag <name>`, the matching refspec `:`, a pattern, `HEAD` and `@` are each read as git reads them. `refs/tags/main` and `refs/tags/master` are protected, `git tag` may not create one, and `gh release create main` and the API calls that write a ref, merge a branch or write a file on the default branch are judged as the git commands they stand for.

Second, a `git` told to work on another repository (`--git-dir`, `--work-tree`, `--namespace`, or `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_NAMESPACE` reaching it) is judged as if it ran on a default branch. The hook does not work out which repository that is: every difference between its working-out and git's would be a way through. One module (`ratchet_guards.environment`) reads every variable a command line sets, in front of a command, through `env`, `export`, `declare -x`, `typeset -x`, `readonly`, `local`, `read`, `mapfile`, `getopts` and `printf -v`, so a spelling closed for `SKIP` is closed for `GIT_DIR`. `HOME` and `XDG_CONFIG_HOME` set for `git` are refused as a hooks-path change, since git reads its global configuration from under them.

Third, a command is judged in every directory and on every branch the line may be in when it runs. A `cd` or a `git switch` that fails leaves the shell where it was, and the hook used to believe the move: `cd /nonexistent; rm -rf guards` and `git switch nope; git reset --soft old` passed. The hook now drops the earlier state only after a plain `cd <directory> &&` or a switch it can read, chained with `&&`, on a line that redefines no command. A target it cannot read (`-`, `~user`, a variable, a glob, `popd`) means every directory seen so far. A line that would need more than 64 states asks.

Fourth, what git is told to run or to write is read. A command string in `rebase --exec`, `difftool --extcmd`, `bisect run`, `submodule foreach`, a `-c` value, a stored `git config` value, an alias or credential helper that begins with `!`, and the value of any `GIT_*` variable or of `EDITOR`, `VISUAL`, `PAGER` and `SSH_ASKPASS` is judged as a script of its own. A file git is told to write (`--output`, `format-patch -o`, `archive -o`, `config --file`, `bundle create`) meets the path rules, so `git log --output=.git/refs/heads/main` is a write to that ref.

Fifth, a sync on a default branch passes only when git itself reads what it merges as the remote's default branch. `git merge --ff-only @{u}`, `origin/main` and a bare `git pull` each name their source through something an agent can set: the branch's upstream, or a short name a local branch, a tag or a stray ref of the same spelling is read before. The hook asks git for the full name (`rev-parse --symbolic-full-name`) and passes `refs/remotes/origin/main` or `master` alone. Since the tampering can sit on the same command line, the sync must be preceded there by nothing but a status, a plain fetch, a switch or a stash. A push that names no destination is resolved the same way, through `@{push}`, and `push.default` is not an agent's to set.

Sixth, the merge job counts a run only for what it tested (`scripts/forge_runs.py`, called from `merge.yml`). A `ci` run on a pull request's head commit used to count whichever pull request started it, and the run of a second pull request from the same branch against another base tests a merge with that base, whose `ci.yml` is that base's. The run must now be a `pull_request` run of `ci.yml` on that commit and branch of this repository that names the pull request against the default branch. That list may hold every open pull request with the run's head and not only the one that started it, in which case it names the pull request under attack too, so two more things must hold: no pull request from the branch, open or closed, has another base, and the pull request was never retargeted. The job reads the pull request again before the merge call. Tier 2 is the result on the commit nearest the default branch's tip, among completed runs of this repository that a trigger of the template started on a commit of the default branch, so a run on a tag named `main`, or an old green run started again, changes nothing. An answer that is missing or cut short reads as red. A branch whose name holds a character a URL reads is merged and not deleted.

Seventh, the queue's work trees go in a directory per user and repository under the temporary directory, made with mode 0700. `drain.py` refuses one that is a link, a file, another user's or writable by others, and empties only what git lists as a work tree of this repository directly inside it. A link is never followed, anything else that is not an empty directory is left and named, and a work tree nested in a queue tree goes with that tree.

Eighth, new glossary text is refused when a reader of the rendered page would take it for something the listing does not show: a term that mixes Latin, Cyrillic and Greek letters, a term or `_Avoid_` item whose skeleton is another term's (accents dropped, 56 Cyrillic and Greek letters read as the Latin letter they are drawn like), a line inside a new entry that renders as a term of its own (`***Order***:`, `__Order__:`), the underline of a setext heading, and any raw HTML tag.

Ninth, the judge and the bite proof read file kinds. A guard, door or record path that is a symbolic link or a submodule, at the merge base or the head, is the owner's (`file:` in the judge's output). A `write` fault or an `include` entry that leaves the copy or the repository through a link is refused before anything is written.

## What was observed

Every hook finding was reproduced before its fix, by the hook's own decision on the command and, for the ref and sync findings, by running the command in a real repository and reading the result. `hooks/tests/test_default_ref.py` and `hooks/tests/test_default_sync.py` keep both halves: each attack first runs unguarded and must switch the path guards off or bring another branch onto `main`, then runs behind the hook and must not. The queue finding emptied a directory through a planted link with the script as it was. The judge passed a `GLOSSARY.md` that was a link whose target was the text of an addition. The bite proof left a file outside the copy.

The merge job is tested against a stand-in for `gh` only. No run on a forge was made for this decision, so these are inferred and not observed. That a run's `pull_requests` lists every open pull request with its head is recalled from GitHub's API description; the REST documentation page read on 2026-11-12 gives the field no description, so the rule does not depend on it either way. The rest is inferred from that documentation: that retargeting starts no `pull_request` run and leaves a `base_ref_changed` or `automatic_base_change_succeeded` event; that a `pull_request` run's `head_branch` is the pull request's branch; and that the runs API filters by `head_sha`, `event` and `branch` as written. If the forge leaves `pull_requests` empty on a run it should name, nothing merges and every pull request says so, which is the direction a wrong guess here fails in.

## What it costs

These passed before and now ask or are refused. On a default branch, a sync after any other command on the line (`echo hi && git pull`, `git fetch origin feature/x && git pull`) asks. `cd x; command` with `;` is judged in both directories. `git checkout <name> && git reset` from a default branch is trusted only when git reads `<name>` as a local branch. More than six unchained relative `cd`s ask. `HOME=… git …` and `git config push.default` are refused. A pull request that was retargeted, or whose branch ever had a pull request against another base, is the owner's to merge, which includes a stacked pull request the forge retargets when its base merges. A glossary term that mixes scripts (`β-carotene` written with a Greek letter), or new glossary text with `<` before a letter, is the owner's. An unregistered, non-empty directory in the queue's own is left for the owner to remove.

## Refutation criterion

This is wrong if a command line the hook reads, a pull request, a planted file or a line of Markdown gets a guard to act on a reading that git, the forge, the filesystem or the renderer does not share, and the change reaches the default branch, a guard path or a directory outside the repository without the owner. The standing attempts are the two real-repository files above, the corpus rows, `test_forge_runs.py`, the link cases in `test_drain.py`, `test_merge_ready.py` and `test_project_bite.py`, and the look-alike rows in `test_records.py`. A new way through goes into the matching file before it is fixed. The forge part is refuted by one run on GitHub: a second pull request from a branch against a base with a weakened `ci.yml`, and a retargeted one, must each be left alone, and an ordinary pull request must still merge. It is also wrong if the cost above is paid often: count the asks on a sync and the pull requests left for a retarget in the first ten built this way, and if more than one in ten was ordinary work, the rule gains a narrower reading.

Known residue, caught by no rule. A script run by path, and a ref, path or branch name that a variable, a file or a sourced script supplies (ADR 0016). A script a program assembles and pipes to a shell (`printf … | sh`). The owner's own global configuration: an alias, or `push.default = upstream` with a branch made and pushed on one line. A default branch not named `main` or `master`, for the tag rule. A tag named `main` that arrives by fetch or is made on the forge's pages, which shadows `git pull origin main`. `git worktree add <path> main && cd <path> && …`, where the directory does not exist when the hook decides (ADR 0021). A move of `HEAD` by anything other than `switch`, `checkout`, `symbolic-ref` and `bisect`. `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY` and `git update-index --cacheinfo`, which change what a commit holds, and the diff check reads that. Look-alikes inside one script (`l`, `I` and `1`; `O` and `0`; `rn` and `m`), other scripts, and letters only some typefaces draw alike. A process of the same user that swaps the queue's directory for a link between the check and the removal. A tier 2 run an agent starts again on the tip until it is green: the result is a true run of the default branch's gates.

## Considered options

- Work out in the hook which repository `--git-dir` names and judge the command there: rejected, the hook would hold a second copy of git's discovery rules, and each difference is a way through.
- Refuse upstream changes on a default branch and keep trusting `@{u}`: rejected, a tag or a stray ref named `origin/main` needs no upstream change, and an upstream set before the session started would still be trusted. Asking git reads both.
- Believe a `cd` whose target exists when the hook runs: rejected, an earlier command on the line can remove or make it.
- Read the run's `pull_requests` list alone, as the review proposed: kept as one condition and not relied on, since a list of every open pull request with the run's head would name the pull request under attack too.
- Have the merge job start `ci` itself on the merge with the default branch and wait: rejected for now, it doubles every run; it is the next step if the forge refutes the inferred behaviour.
- Take the newest tier 2 run on any commit of the default branch: rejected, an old green commit run again would hide a red one nearer the tip.
- A full Unicode confusables table for glossary terms: rejected, it is a dependency or a large table to keep; the skeleton says what it covers and the listing still shows every term to the owner.
- Refuse every symbolic link in a change: rejected, a link outside the guard, door and record paths is ordinary.
- Remove any directory found in the queue's own: rejected, that is how a planted link emptied what it pointed at.

Decided 2026-11-12.

## What the forge showed

The merge job was run on a private sandbox repository on 2026-11-12, one pull request per case.

A run's `pull_requests` list holds every open pull request with that head commit, each with its current base, even for a run made before a retarget. So that list alone would have counted a green run against a weakened base for the pull request against the default branch. The rule that a branch with a pull request against another base is the owner's is what stopped it, and the retarget rule is what stops a retargeted pull request. The rules were right not to rest on the list.

A manual retarget records the event `base_ref_changed` and starts no new run. `automatic_base_change_succeeded` was not observed, so the rule keeps naming it on inference.

The `head_branch` of a pull request run is the pull request's branch. A `workflow_dispatch` on a tag named as the default branch gets a `head_branch` equal to that name, and the runs API's branch filter returns it. `forge_runs.py deep` did not count it: given the forge's answer with every branch run edited to failure and the tag run left green, it said red.

The loop over every green pull request ran on the forge. Two green pull requests were judged in one run and one merged. The other was told `behind` against the new tip, and the next run edited the same comment.

The clean case merged itself, deleted its branch and dispatched `deep`. The `unflagged` reason sent a pull request that added to a surface snapshot with no flag to the owner. A pull request that removed guard paths went to the owner with each path listed.

Not observed: read-only default workflow permissions, a merge the token is refused, and a red tier 2 on the default branch's tip.

The fixes that followed that run were run on the same sandbox on 2026-11-13, pinned at the 0.10.0 merge commit. A pull request opened against another branch got one `merge: owner` comment with `target` and `unnamed`. Retargeted to the default branch, it had the same comment edited to `retargeted`. Of two pull requests from one branch, the one against the default branch got `twin`, naming the other, and the other got `target`. A pull request against another branch gets `unnamed` beside `target`, which says the same thing twice. The weekly run, red on two gates, opened its issue with the output of those two gates and no other.

The conformance finding for a missing tier list was not run on the forge, since the sandbox's `ci` does not run conformance. In a clone of the sandbox with `tier1_sharded` removed, conformance named the variable, the `ci.yml` job that reads it and what to add. On the forge the `shape` job of that pull request failed with the runner's own error, and a pull request whose `ci` is red gets no comment from the merge job.
