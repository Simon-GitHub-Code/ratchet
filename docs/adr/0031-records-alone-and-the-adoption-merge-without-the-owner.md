# Records alone and the adoption merge without the owner

ADR 0021 asks every change for a verdict record, the pipeline's approval of the tree it reviewed, and sends any change without one to the owner. The records the owner's own conversation writes never carry one: a spec from `to-spec`, the tickets from `to-tickets`, a conjecture, a change description, a new term or ADR. No pipeline built them, so none approved them. The adoption went to the owner too, because the default branch held no `guards/manifest.toml` to judge it against. In the dogfood run of 2026-11-13 the owner merged by hand five times, pasting git each time: the adoption, the spec, the conjecture and the tickets. Each merge asked them to confirm something they had said minutes before, which ADR 0022 says the method never asks. The route made it worse: on a dirty default branch it said "run `just check`, then commit on branch `main`", so the agent's instruction was to commit where no judge reads.

## Decision

**Records alone are asked no verdict record.** A change with no verdict record passes the `record` reason when every path it touches is a record, read by the manifest the default branch holds, never the change's. A record is one of three kinds, in `RECORDS` in `scripts/merge_ready.py`:

- *a ticket*: `.scratch/**/issues/*.md`, which holds every file the route, the drain and the feature preflight's ticket numbers read as a ticket (`.scratch/*/issues/*.md`);
- *the tracker's markdown*: `.scratch/**/*.md`, which holds the spec, the change descriptions and the conjecture;
- *an addition to a record*: a path whose first guard group is `edit = "append"`, as `docs/adr/**` and `GLOSSARY.md` are, when the change is an addition as ADR 0014 reads one (a new ADR, a new term).

The first two hold only where no guard group and no one-way door holds the path, letter case set aside. The third holds only where every group that holds the path is an append group, so a stricter group further down the manifest keeps it out, and no door holds it. Each path must be a regular text file on both sides, and the change must keep it: a symbolic link, a submodule, a file that is not text and a deletion are each the owner's. Every other reason of the judge still applies: `guard`, `door`, `dispute`, `target`, `behind` and `tier2` read records alone as they read any change. When one path is not a record, the reason is the plain one ADR 0021 gives. When every path is a record and some change is more than a record takes, the reason names up to three of them and why.

**The agent-ready label stays the owner's act (ADR 0008).** A ticket whose change raises the count of the label, in the spelling `docs/agents/triage-labels.md` gives the `ready-for-agent` role at the tip or the role's own name, in any letter case, anywhere in the file, is the owner's to merge. A ticket that held the label at the merge base takes only text appended after what it held: the conjecture and the owner's answers are appended, and any other edit of an agreed ticket is the owner's. A records-only merge is therefore never a way to apply the label.

**Records land from the default branch through the judge.** `merge.py --records`, the `merge` entry point with `--records`, lands what the owner's conversation left uncommitted on the default branch. Every uncommitted path, tracked or not, must be a record by the default branch's manifest; otherwise it changes nothing and says which paths are not. It commits them on `records/<UTC time>` with the repository's commit hooks, switches back, and merges that branch as `merge.py <branch>` does: the judge, then `check` on the merge result. A merged records branch is deleted. One the judge leaves to the owner stays, with the owner's command printed. Nothing is committed on the default branch itself. With a forge it refuses: the records go on a branch and through a pull request, and `merge.yml`, unchanged, merges what the judge passes.

**The route never says commit on the default branch.** A dirty default branch that holds records alone gets `just merge --records`, which an agent runs, or with a forge a branch and a pull request. Anything else gets "run `check`, then commit on a branch of its own, never on `main`". `/ratchet:next` runs a `next:` line that names the `merge` entry point, as it already ran `hooks-install`: the entry point merges only what the judge and `check` pass, and prints the owner's command otherwise. `/ratchet:conjecture` and the feature drain's answers land a local ticket the same way.

**The adoption is judged by its own gates.** A change is the adoption when neither the tip of the default branch nor the merge base holds `guards/manifest.toml` or `docs/process/binding.md`, and the head holds both and its manifest parses. There is no gate before it to loosen, and the owner answered `/ratchet:adopt` minutes before. The judge reads the head's manifest for it, and the `guard`, `door`, `unflagged` and `record` reasons are not asked: the guard paths are all new, and nothing before the adoption was judged. `target`, `behind`, `tier2`, `dispute`, the flag registry and the file-mode reasons still are. The judge prints a note that names the adoption. `merge.py` runs `check-deep` on its merge result in place of `check`, so every bound gate runs and `bite-all` shows each one bites before the gates bind the default branch. A merge base with a manifest is never the adoption, whatever a branch deletes, and a tip that lost one is the owner's to explain. Decided 2026-11-13.

Amends ADR 0021's `record` reason and its no-forge path. The rest of ADR 0021 stands.

## What an agent could forge

Nothing new is read from what an agent writes. The judge decides record kinds from the default branch's manifest and the diff, as it decides guard paths. An agent can write a spec that asks for anything, and it lands; what is built from it waits for a ticket with the label, which is the owner's. An agent can append to an agreed ticket, and the drain then builds the ticket as it reads; see the residue. An agent before the adoption can already commit anything on the default branch, since no path rule holds yet, so letting the adoption merge loosens nothing that held.

## Refutation criterion

This is wrong if a records-only merge carries something the owner would have stopped. Read the first twenty records-only merges: one the owner reverts or rewrites names a record kind or refusal the judge lacks, and it becomes a test in `hooks/tests/test_merge_ready.py` before the judge changes. It is also wrong if it saves nothing: replay a dogfood run from `/ratchet:init` to the first `/ratchet:feature`, and if the owner types a git command for anything but a labelled ticket batch, the kinds are too narrow. For the adoption: it is wrong if an adoption merged by `merge: agent` leaves a bound gate that does not bite, which `bite-all` in `check-deep` is there to catch.

Known residue. Text appended to an agreed ticket can widen what it asks for, and the drain builds the ticket as it then reads: the judge cannot tell a section that widens scope from an answer. `to-tickets` writes `Status: ready-for-agent` on the tickets it makes, so on a local tracker a ticket batch from it still costs the owner one merge: the label is in the change. The label is counted as text anywhere in the file, so a ticket whose new text quotes it, in a conjecture for instance, goes to the owner too. Editing `Blocked by:` on an agreed ticket is not an append and goes to the owner. The label is read on tickets only: other markdown of the tracker that carries it lands, as the dogfood's spec did, because `to-spec` wrote `Status: ready-for-agent` on it. Nothing that starts a build reads it there: the route and the drain find tickets under `issues/` only, so such a file is built only when the owner types its path to `/ratchet:feature`. The hook still asks when an agent writes the label on any markdown under `.scratch/`. On a forge, `merge.yml` reaches the default branch with the adoption, so no merge job runs on the adoption's own pull request and the owner merges it once. After the adoption merges with no forge, `merge.py` names `check-deep` as the next command, though it has just run on that tree.

## Considered options

- Ask a review for records, so they carry a verdict record: rejected. A reviewer would approve the owner's own words back to them, and a pipeline run per spec costs more than the merge it replaces.
- Commit records on the default branch, which ADR 0016 lets pass with no forge: rejected. The commit never meets the judge, and the route's instruction to commit on `main` is the habit this removes. One path through the judge for every change is what the judge's reasons rest on.
- Treat any markdown as a record: rejected. Skills, `AGENTS.md` and the process documents are instructions to agents and stay guard paths.
- Let the label through when the guard hook asked the owner as it was written: not chosen here. The hook's ask is the owner's act in a harness that runs the hook, but the judge cannot see that it ran, and a harness without the hook could write the label. It would save the one merge a `to-tickets` batch costs; the owner decides.
- Keep the adoption the owner's: rejected. The owner chose to adopt minutes before, the default branch has no gate to loosen, and `check-deep` on the merge result is a stronger check than the owner's reading of a large first change.
