# Records alone and the adoption merge without the owner

ADR 0021 asks every change for a verdict record, the pipeline's approval of the tree it reviewed, and sends any change without one to the owner. The records the owner's own conversation writes never carry one: a spec from `to-spec`, the tickets from `to-tickets`, a conjecture, a change description, a new term or ADR. No pipeline built them, so none approved them. The adoption went to the owner too, because the default branch held no `guards/manifest.toml` to judge it against. In the dogfood run of 2026-11-13 the owner merged the adoption, the spec, the conjecture and the tickets by hand, pasting git each time. Each merge asked them to confirm something they had said minutes before, which ADR 0022 says the method never asks. The route made it worse: on a dirty default branch it said "run `just check`, then commit on branch `main`", so the agent's instruction was to commit where no judge reads.

## Decision

**Records alone are asked no verdict record.** A change with no verdict record passes the `record` reason when every path it touches is a record, read by the manifest the default branch holds, never the change's. A record is one of a closed list of shapes, `RECORDS` in `scripts/merge_ready.py`, each the whole path that the skill writing it names:

| Record | Shape | Written by | Manifest groups that may hold it |
| --- | --- | --- | --- |
| ticket | `.scratch/<feature>/issues/<n>-<slug>.md` | `to-tickets` on a local tracker | none |
| spec | `.scratch/<feature>/spec.md` | `to-spec`; `/ratchet:conjecture` may write the conjecture into it | none |
| change description | `.scratch/changes/<name>.md` | the change template, filled with no forge at the path `/ratchet:adopt`, `/ratchet:feature` and the route name | none |
| glossary term | `GLOSSARY.md`, an addition as ADR 0014 reads one | `domain-modeling` | `edit = "append"` only |
| decision | `docs/adr/<nnnn>-<slug>.md` | `domain-modeling` | `edit = "append"` only |

`<feature>`, `<slug>` and `<name>` are lower case. A path in any other shape is not a record, under `.scratch/` or not: a wayfinder map, an `Issues/` folder or a `run.md` beside a spec makes the change more than records. No one-way door holds a record. Each must be a plain file of mode `100644` wherever it exists, and the change must keep it: a symbolic link, a submodule, an executable file, a file that is not text and a deletion are each the owner's, and so is a path with a twin in another letter case at the head or the tip, which a file system that ignores case opens as one file. Each must also be as the change found it at the default branch's tip: a record that changed there after the change forked would merge into text the judge never read, so the change is brought up to date first. Every other reason of the judge still applies: `guard`, `door`, `dispute`, `target`, `behind` and `tier2` read records alone as they read any change. When one path is not a record, the reason is the plain one ADR 0021 gives. When every path is a record and some change is more than a record takes, the reason names up to three of them and why.

**No instruction file is a record, and none lands unseen.** An agent reads `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `GEMINI.md` and anything under a `.claude/` directory as instructions, wherever they sit and in any letter case. None is a record at any depth. In any change the judge gives the `guard` reason for one that no group of the manifest holds, so a nested `src/CLAUDE.md` is the owner's to merge, beside code as much as beside records.

**The agent-ready label stays the owner's act (ADR 0008), and a labelled ticket stays still.** A ticket whose change raises the count of the label, in the spelling `docs/agents/triage-labels.md` gives the `ready-for-agent` role at the tip or the role's own name, in any letter case, anywhere in the file, is the owner's to merge. A ticket that holds the label at the merge base or at the tip is agreed, and records alone change nothing it reads to decide what it builds and whether it may start. `feature_preflight.reads` names that set once: the ticket and the spec it inherits from (its `Parent:` line, or the `spec.md` beside its `issues/`), read whole, and each ticket it is blocked by, read for whether it is open. The judge asks it at the merge base, the tip and the head, so a file the change creates there, a spec beside `issues/` or a blocker that was missing, counts too. Any change to the ticket or its spec is the owner's, the conjecture and the owner's answers among them, and so is a change that opens or closes one of its blockers. What the preflight, the drain and the route open to decide whether a ticket may start lies inside that set: `test_the_readers_of_a_ticket_read_only_what_reads_names` watches the files each opens. A new ticket whose name starts with the number of another ticket beside it is the owner's, since a `Blocked by` line that names the number reads the first such file, and a closed namesake would release what the owner ordered after the real one. A records-only merge therefore never gives the label, never changes a labelled ticket or its spec, and never changes whether one may start. It can still add a glossary term the pipeline reads; see the residue.

**No ticket is closed by records alone.** A change that takes a ticket from open to closed is the owner's: a ticket closes with the merge of its build, which carries a verdict record.

**A decision is the owner's to agree.** A new or changed ADR among records alone sends the merge to the owner with one sentence that names it, `record: docs/adr/0005-<slug>.md records a decision: "<title>". Yours to agree.`, the title taken from its first `# ` heading, printable characters only and at most 100 of them, or the file's name when it has none. The judge cannot read whether an ADR reverses another; the owner can. A term added to the glossary stays an agent's to land (ADR 0014).

**Records land from the default branch through the judge.** `merge.py --records`, the `merge` entry point with `--records`, lands what the owner's conversation left uncommitted on the default branch. Every uncommitted path, tracked or not, must be a record by the default branch's manifest; otherwise it changes nothing and says which paths are not. It commits them on `records/<UTC time>` with the repository's commit hooks, switches back, and merges that branch as `merge.py <branch>` does: the judge, then `check` on the merge result. When the hooks refuse the commit or change a file as they run, it puts the index back as the owner left it and deletes the branch, so the records stay uncommitted. A merged records branch is deleted. One the judge leaves to the owner stays, with the owner's command printed. A run stopped partway, in the commit hooks or after its commit, leaves HEAD on its records branch; the next run switches back, carrying what is uncommitted, and lands the records or merges their commit, and when git cannot switch back it prints git's line and what to type before running again. Nothing is committed on the default branch itself. With a forge it refuses: the records go on a branch and through a pull request, and `merge.yml`, unchanged, merges what the judge passes.

**The route never says commit on the default branch.** A dirty default branch, checked out by name, that holds records alone gets `just merge --records`, which an agent runs, or with a forge a branch and a pull request. Anything else gets "run `check`, then commit on a branch of its own, never on `main`". A `records/<time>` branch checked out gets `just merge --records` again. For a `records/<time>` branch not yet merged the route asks the judge: the owner's merge command with the judge's first reason, or `just merge <branch>` for an agent when the judge passes it, as it does after a run stopped while `check` ran. `/ratchet:next` runs a `next:` line that names the `merge` entry point, as it already ran `hooks-install`: the entry point merges only what the judge and `check` pass, and prints the owner's command otherwise. `/ratchet:conjecture` and the feature drain's answers land a local ticket the same way.

**The adoption is judged by its own gates.** A change is the adoption when neither the tip of the default branch nor the merge base holds `guards/manifest.toml` or `docs/process/binding.md`, and the head holds both and its manifest parses. There is no gate before it to loosen, and the owner answered `/ratchet:adopt` minutes before. The judge reads the head's manifest for it, and the `guard`, `door`, `unflagged` and `record` reasons are not asked: the guard paths are all new, and nothing before the adoption was judged. In their place the manifest must guard at least what the shipped template does (`skills/adopt/templates/guards/manifest.toml`): every template group, in the template's order, with its rule, its exclusions and every template path. It may add paths to a group that asks or denies, and groups after the template's; a path added to an `append` group, a path dropped or a rule loosened is a `guard` reason. Otherwise an adoption could leave the binding unguarded, or put it where a later records-only change reaches it. `target`, `behind`, `tier2`, `dispute`, the flag registry and the file-mode reasons still are. The judge prints a note that names the adoption. `merge.py` runs `check-deep` on its merge result in place of `check`, so every bound gate runs and `bite-all` shows each one bites before the gates bind the default branch. Decided 2026-11-13.

**The adoption's ADRs land with it, and no other change is the adoption.** The dogfood adoption brought four ADRs (0001 to 0004), its `AGENTS.md` and `.claude/settings.json`, and the judge at this ADR passes it as before. The judge tells the adoption apart by the default branch alone, never by what the change holds: once the tip or the merge base holds the manifest or the binding, no change is the adoption. An ADR written to look like the adoption's, with the template's text and title, is then a decision the owner agrees to, and a branch that also deletes the manifest and the binding is the owner's for those deletions; `test_no_adr_can_be_dressed_as_the_adoptions` holds both.

Amends ADR 0021's `guard` and `record` reasons and its no-forge path. The rest of ADR 0021 stands.

## What an agent could forge

Nothing new is read from what an agent writes. The judge decides record kinds from the default branch's manifest and the diff, as it decides guard paths. An agent can write a spec that asks for anything, and it lands while no labelled ticket inherits from it; what is built from it waits for a ticket with the label, which is the owner's, and from then on the spec is still. An agent before the adoption can already commit anything on the default branch, since no path rule holds yet, so letting the adoption merge loosens nothing that held; what it must not do is bind the gates weaker than the template, and the template comparison says so. An agent that writes a verdict record skips what records alone are refused; see the residue.

## Refutation criterion

This is wrong if a records-only merge carries something the owner would have stopped. Read the first twenty records-only merges: one the owner reverts or rewrites names a record kind or refusal the judge lacks, and it becomes a test in `hooks/tests/test_merge_ready.py` before the judge changes. It is also wrong if it saves nothing: replay a dogfood run from `/ratchet:init` to the first `/ratchet:feature`, and if the owner types a git command for anything but a labelled ticket batch, a labelled ticket's answers or conjecture, or an ADR, the kinds are too narrow. At this writing the dogfood's record-only changes (the spec, the conjecture, the tickets) hold no ADR, and the replay costs the owner one merge: the tickets, which carry the label. For the adoption: it is wrong if an adoption merged by `merge: agent` leaves a bound gate that does not bite, which `bite-all` in `check-deep` is there to catch.

## Known residue

- A verdict record is written by an agent, so an agent can forge it (ADR 0021), and a change that carries one is judged as the pipeline's: the label, a labelled ticket, a closed ticket and an ADR in it meet only the guard rules. The guard hook still asks when an agent writes the label on any markdown under `.scratch/`.
- A spec no labelled ticket inherits from is still being written and takes any edit.
- A term added to the glossary lands, and the pipeline reads the glossary beside a labelled ticket.
- Answers and a conjecture written on a labelled ticket each cost the owner one merge, and so does the route's step that marks resolved a ticket whose branch merged: the judge cannot tell an answer from a widened scope, nor a close after its build from one that skips it.
- `to-tickets` writes `Status: ready-for-agent` on the tickets it makes, so on a local tracker a ticket batch costs the owner one merge. The label is counted as text anywhere in a ticket, so one whose new text quotes it goes to the owner too.
- The label is read on tickets only: other markdown of the tracker that carries it lands, as the dogfood's spec did. Nothing that starts a build reads it there: the route and the drain find tickets under `issues/` only.
- The guard hook does not ask when an agent writes an instruction file below the root, such as `src/CLAUDE.md`: the judge sends its merge to the owner, but a session on that branch reads it first. Other harnesses' folders (`.codex/`, `.gemini/`, `.opencode/`) are not instruction paths to the judge: none is a record, and a change of code that carries one is judged by the manifest alone.
- A run killed in the commit hooks folds the owner's staged and unstaged versions of a record into the unstaged one's text when the next run carries it back. A run killed while `check` ran leaves its scratch work tree, `/tmp/ratchet-merge-*/tree`, registered with git, which `git worktree prune` keeps while the folder exists.
- On a forge, `merge.yml` reaches the default branch with the adoption, so no merge job runs on the adoption's own pull request and the owner merges it once. After the adoption merges with no forge, `merge.py` names `check-deep` as the next command, though it has just run on that tree.

## Considered options

- Ask a review for records, so they carry a verdict record: rejected. A reviewer would approve the owner's own words back to them, and a pipeline run per spec costs more than the merge it replaces.
- Commit records on the default branch, which ADR 0016 lets pass with no forge: rejected. The commit never meets the judge, and the route's instruction to commit on `main` is the habit this removes. One path through the judge for every change is what the judge's reasons rest on.
- Treat any markdown, or any markdown under `.scratch/`, as a record: rejected. This ADR first read the tracker's folder (`.scratch/**/*.md`) as records, and review landed a nested `CLAUDE.md`, an `AGENTS.md` under `.scratch/`, an executable spec and a twin in another letter case through it unseen. A closed list of the shapes the skills write is what the judge can name.
- Let a labelled ticket and its spec take appends, the conjecture and the answers among them: rejected after review. An appended section can widen what the ticket builds, and an appended `Parent:` line can point it at another spec; the judge cannot tell either from an answer.
- Let a new ADR land as an addition, as the glossary's terms do: rejected. An ADR can reverse an earlier decision in plain words, which the judge cannot read.
- Let the label through when the guard hook asked the owner as it was written: not chosen here. The hook's ask is the owner's act in a harness that runs the hook, but the judge cannot see that it ran, and a harness without the hook could write the label. It would save the one merge a `to-tickets` batch costs; the owner decides.
- Keep the adoption the owner's: rejected. The owner chose to adopt minutes before, the default branch has no gate to loosen, and `check-deep` on the merge result is a stronger check than the owner's reading of a large first change.
