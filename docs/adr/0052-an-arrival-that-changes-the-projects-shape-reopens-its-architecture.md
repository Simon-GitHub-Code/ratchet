# An arrival that changes the project's shape reopens its architecture, and the review lands before the next instance

The owner put the principle on 2026-11-14: getting each project's architecture right, asking the owner about it, and enforcing it deterministically is a large part of what the method is for. The macro architecture is the stack, where it runs, where its data lives and how its parts talk; the micro architecture is its modules, layers and seams. ADR 0049 and ADR 0050 (in flight beside this one) ask the architecture at adoption and record it as a decision with alternatives, a reversal cost and a refuter, with the layers declared in the binding and held by conformance checks. That decision is right for the project the adoption saw. A hobby project adopted as one command that keeps nothing becomes, ten changes later, a thing that stores data, calls an outside service and serves a page. Nothing re-read the decision when that happened, so the layers the gates hold stay the ones drawn for a project that no longer exists, and the first stored format lands wherever the ticket's agent put it.

The method already knows when the project's shape changes. ADR 0028 counts the instances of each kind of code, ADR 0030 and ADR 0048 make the first arrival of a kind free once and the next instance red while a safeguard is owed, and the owner declares the life events. This decision reuses that machinery for the architecture.

## Decision

**Some triggers reopen the architecture.** The catalogue (`skills/method/application-types.toml`) gains an `[architecture]` table: each key is a trigger, and its text is the question the arrival reopens, which the review answers.

| Trigger | Why its first arrival changes the shape |
| --- | --- |
| `code:stored-format` | The project now keeps data. Where it lives, which part alone reads and writes it, and how its shape changes without loss are decided once; a second store or a format written from three places is the drift the review prevents. |
| `code:listener` | A process now keeps running to serve. That is a new process boundary: what starts and stops it, and how the other parts reach it. |
| `code:outbound-call` | The project now depends on a system it does not run. Which part alone talks to it, and what the project does when it is slow, wrong or gone, is a seam that is cheap to draw at the first call and costly at the fortieth. |
| `code:user-interface` | A screen now exists where there was none: a presentation layer, often a second runtime, and the question of where the rules live so the screen does not hold them. |
| `code:scheduled-work` | A clock now starts work. Where that work runs, and what happens when a run overlaps, fails or is missed, is a runtime decision no caller makes. |
| `code:access-control` | More than one person now acts in it. Whose data each may see or change, and the one place that rule is held, partitions the data and every layer that reads it. |
| `code:concurrency` | Parts now run at once. What they share, who may change it and how they hand work to each other is how the parts talk. |
| `life:deployed` | Others can now reach it: where it runs, how it is configured there, and how a bad release is undone. |
| `life:irreplaceable-data` | It now holds data that cannot be recreated: where that data lives, how it is copied and how it is restored. |
| `life:depended-on` | People now rely on it: which of its surfaces are promises, and how they change without breaking anyone. |

Two kinds are new, because the owner's list named concepts no kind covered: `scheduled-work` (work a clock starts rather than a caller) and `access-control` (a check of who is acting or what they may see or do). Every repository's Triggers table holds a row for each kind that reopens the architecture, whatever its application types, or the arrival could never be seen; conformance is red on a missing one, and a repository that will never have the kind writes `none: <reason>`.

The other kinds do not reopen it. `source` and `entry-point` arrive with the first slice, which the adoption's decision drew; more of them are more of the same shape. `config-read`, `dependency`, `doc-example`, `flag` and `formal-model` are a setting, a package, an example, a switch and a proof inside the shape: a package that does reshape the project is already a decision recorded in an ADR (the method's `code.md`). `public-interface` arrives with the first exported module in many stacks; the point at which a surface becomes a promise is `depended-on`, which does reopen it. `untrusted-input` is a parser placed behind an entry point, a call or a store, each of which is reviewed or was decided at adoption. `container` is packaging; where the project runs is reviewed at `deployed`. `layer` is the architecture itself, changed only through a review.

**A review is owed as a safeguard is owed.** When a kind the table names arrives for the first time ever on the default branch (ADR 0048), the change that brings it is free, however many files it touches (ADR 0030), and `triggers.py` notes that it reopens the architecture. From then until the review lands, a change that adds another instance of the kind is red, with a line of its own (`triggers: architecture review owed: '<kind>' gained ...`) that names `/ratchet:architecture`. A kind that went back to none and returns is owed, not arriving. A declared life event the table names owes a review too and is never red (ADR 0028). A review is owed beside any Gates rows the same arrival makes owed; each says its own line. The route names `/ratchet:architecture` before `/ratchet:safeguard`, with `then:` naming the safeguard when rows are owed too, since the review decides where the new kind lives and so where its safeguards go; like the safeguard it never hides the build, and its `why:` ends `or carry on with <the step it would otherwise name>`. The drain holds a ticket that went red for an owed review, with a reason that names `/ratchet:architecture`, until no review it names is owed.

**The review is a skill of its own, `/ratchet:architecture`, not a step of `/ratchet:safeguard`.** Three reasons. The safeguard skill asks the owner nothing (ADR 0034) and a review that finds the architecture should change asks him one question; folding it in would make every safeguard run a possible question. The order matters: the review may move where the new kind lives, and a safeguard bound first would be bound to the old place. And the review's record must land on the default branch on its own before the next instance (below), where a safeguard change carries recipes, faults and tool config the owner merges for other reasons.

**What the review does.** The agent re-reads the architecture decision record (ADR 0049/0050's, and every review since; for a repository adopted before the architecture was asked, the ADRs, `AGENTS.md` and binding that decided the stack, where it runs, storage and how the parts talk), the declared layers and the design brief, then the code as it now is: every instance of the arrived kind, which layer it sits in, what it reaches. It answers the question the catalogue gives the trigger. Then one of two outcomes:

- **Holds.** Every new instance sits in a layer whose job covers it, the declared direction still describes every dependency, and the reopened question has its answer in the existing decision. The agent writes a short dated record that cites the trigger, says why the decision holds with the files that show it, and gives a refutation criterion. Nothing is asked: the hand-over lists it under **Assumed** (`architecture.holds` in `skills/method/questions.toml`), with what reopening it costs.
- **Changes.** The new kind has no layer whose job covers it, covering it would break the direction, or what the product now needs contradicts where it runs, where its data lives or how its parts talk. The agent prepares two or three whole options with their trade-offs, running cost and reversal cost, recommends one, and asks the owner in one message (`architecture.change`, a product question in the registry: each option is a different product to live with, and undoing it rewrites the project). It records the answer as a superseding record with every option and its reversal cost, and updates the declared layers and the dependency-direction tool's config so the gates hold on the code as it stands. Code that must move is listed as the first work under the new decision; the review change moves none of it.

This asks the owner about how the project is built, which ADR 0034 assumed. The owner's principle of 2026-11-14 overrides that for the architecture, as ADR 0049 and ADR 0050 do at adoption; the question is asked only when the review finds a change, and a decision that holds stays an assumption.

**When the review is done.** When a decision record under `docs/adr/` at the merge base names the trigger on a `- Architecture review:` line (the keys separated by commas), has `- Outcome: holds` or `- Outcome: changes`, a `- Decided: YYYY-MM-DD` line, a `## Decision` and a `## Refutation criterion` that each say something, and, when it changes the architecture, two or more options under `## Considered options`. The gate checks that structure and names, in its red line, why a record that cites the trigger does not count. A record written in the same change as another instance does not count: the review lands on its own, so the unattended pipeline cannot decide the architecture beside the code that grows under it. The route reads the work tree, so on the review's own branch it already moves on. The review change brings an ADR, so the merge judge leaves the merge to the owner (ADR 0031), and his merge is his read of it.

**Where the reviews start, and existing repositories.** The review is asked by a Gates row, `architecture reviewed when its shape changes`, bound to the plugin's `scripts/triggers.py` and run by the `triggers` gate. The first commit on the default line whose binding held that row starts the reviews: a kind with an instance at or before that commit, and an event declared on it, count as reviewed by the adoption, or by the upgrade that added the row. The template binding carries the row, so a new adoption starts with the kinds and events its own architecture decision saw. An adopted repository gets the row from `upgrade.py --apply`: it is an `always` row bound to the plugin's own gate, which conformance already offers as an edit. Before that upgrade nothing is asked; after it, what the repository held is reviewed by the upgrade and only what arrives later owes a review. A repository therefore never turns red for what it already had. The search is one first-parent `git log -S` over the binding, run only when a reopening kind grows at head with no review at the base, or a reopening event is declared, and for `reviews_owed` when the route runs.

**What the change owes in existing repositories.** The two new kinds and every reopening kind a repository's types were not asked about are missing rows in its Triggers table. Conformance names each; the upgrade cannot write a stack's paths, so it records each as owed in `quality/owed.toml` (ADR 0037) and an agent writes them. A kind whose row is written after its code exists is judged by the same start rule: code held at or before the start is reviewed; code that arrived after the start owes a review from the next change.

## Refutation criterion

This is wrong if reviews are paperwork, arrive too late, or turn adopted repositories red. Read the first ten reviews written under it across the owner's projects, and the first thirty merged changes of three repositories after their upgrade. It is refuted as paperwork if more than half of the reviews that conclude `holds` name no file in their Decision, or if the owner says of a review that it asked him nothing he cared about. It is refuted as too late if the owner later changes the architecture for a reason a kind's arrival already showed, and that kind's review said `holds` (the review read the wrong thing), or if a reopening kind arrived and no review was owed because its Triggers row matched nothing. It is refuted as a wall if an upgraded repository's `triggers` gate goes red for an architecture review of a kind it held before the upgrade, or if a review owed blocks the same ticket's build more than once.

## Considered options

- **A step of `/ratchet:safeguard`.** Rejected: that skill asks nothing, binds tools to the shape as it is, and lands recipes the owner merges for other reasons; the review may ask, may move the shape, and must land first and on its own.
- **The owed ledger of ADR 0037 for existing repositories.** Rejected: an entry excuses a conformance finding, and an owed review is the `triggers` gate's, not a conformance finding. An entry that excused a review would keep the kind owed and never red for as long as the entry stood, which lets instances pile up, the cost ADR 0028 exists to bound. The start commit reads history, which the repository cannot forge, and needs no new file.
- **Reviewed by the adoption commit alone (the first binding).** Rejected: a kind that arrived between an older adoption and this release would turn red the day the plugin updates.
- **Start at a plugin version on the pin line.** Rejected: the version is fixed at release time, after this merges, and a repository pinned to a commit between releases would read the wrong side of it.
- **A review in the same change as the instance counts, as a row bound in the same change does.** Rejected: binding a row is mechanical and its bite proves it; a review is a judgement, and in the same change it would be written by the agent that built the ticket, unattended.
- **Every kind reopens the architecture.** Rejected: ten reviews in a project's first week is the paperwork ADR 0028's refuter warns about. The list keeps the kinds that add a store, a process, a dependency on another system, a runtime, a clock, a second person or parallelism.
- **Red on a declared event.** Rejected as in ADR 0028: an event has no instance to add, and declaring it is the owner's.

Decided 2026-11-14.

Depends on: ADR 0049 and ADR 0050 for the architecture decision record at adoption and the declared layers in the binding; until they land, the review reads the records that decided those things and `AGENTS.md`'s layers.
