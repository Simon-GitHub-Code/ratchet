# An agent changes a guard path on a branch, and the owner decides at the merge

Every change an agent made to a guard path stopped at a permission prompt. In the owner's transcripts from two of his projects, 174 tool calls raised one. Replayed through the hook and the generated permission rules, 173 still do; the last edited a scratch copy the replay cannot rebuild. Of the 173, 153 change a guard path, almost all of them on a feature branch, 14 apply the agent-ready label and 6 merge a pull request. In a session on 2026-11-13 that reviewed these prompts, the owner said he accepts every one of them and refuses none. A prompt the owner always accepts controls nothing.

It also asked at the wrong moment. A guard path changed on a branch changes nothing on the default branch until the branch merges, and the merge judge (ADR 0021) already sends every change to a guard path to the owner, with its reasons in writing, as one decision over the whole change. The prompt at the edit asked the owner the same question earlier, once per file, with less to go on.

## Decision

Edit-time control stays for exactly the files whose effect comes before the merge; everything else is judged at merge. Two kinds of file act the moment they are written: CI workflows and agent-instruction files. The hook asks the owner before each write of either that it reads, on every branch, and judges a change to any other guard path by where its commit lands. The hook is a check on an agent's ordinary writes. It is not a boundary against an agent that sets out to get round it: the section in plain words below says what it stops, what it does not, and where the boundary is.

- **On a branch, no verdict.** An Edit, Write, MultiEdit, NotebookEdit, patch or shell write of a guard path in a group that is not locked gets no answer from the hook when its commit lands on a branch other than the default one. The hook reads the branch from git: the branch of the checkout that holds the file, or the one a `git switch` or `git checkout` earlier on the same command line moves that checkout to. A detached `HEAD` counts as a branch, since nothing reaches the default branch from it but a push or a merge, which the hook judges. The harness's own permission flow decides, as for any other file.
- **Where the hook cannot tell, the default branch.** A switch it cannot read as one may move any checkout to its default branch: a branch named by a variable or a substitution, or a `git switch` or `git checkout` inside a shell's script, a substitution, `eval`, `xargs`, `find -exec` or a script git runs. A shell write of a guard path after one on the same line is judged as on the default branch, and so is a relative path written after a `cd` the hook cannot follow, on any branch, since the shell may then be in any checkout. Where only such a switch puts the write on the default branch, the deny says to run the switch in a tool call of its own, so the next call is judged on the branch it leaves.
- **On the default branch, a deny with the way out.** Where the commit would land on `main`, `master` or the branch the committed manifest is read from, or the hook cannot tell where it lands, the change is denied, and the message says: make the change on a branch and commit it there, where the merge judge reads it. An addition to a record still passes there (ADR 0014). No judge reads a commit made on the default branch, so that is where the hook must hold.
- **A locked group is denied everywhere.** A locked group holds files that act before any merge, in any session started in the checkout that holds them. Claude Code reads the settings, hooks, workflows, agents, skills and commands under `.claude/` from that checkout and reloads them while a session runs; an agent file can set `permissionMode: bypassPermissions`, and a skill can grant tools and register hooks. Git runs `.git/hooks` and reads `.git/config` and the refs the guard trusts (ADR 0016). The plugins and the user's settings act in every session. Removing a directory is judged by the strictest group below it, so `rm -rf .` is a write of a locked path.
- **A file that acts at once is asked, on every branch.** GitHub runs the workflow files directly under a branch's own `.github/workflows/` on a push or a pull request, with the repository's token and secrets, before any merge. It reads no subdirectory of it. Claude Code loads an agent-instruction file, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `GEMINI.md` or anything under a `.claude/` directory, at any depth, and follows it: a headless probe showed a nested `CLAUDE.md` loaded and obeyed once the agent read a file beside it. An agent on a branch could write one, let the pipeline's critic and reviewer run under it, and delete it before the commit, so the merge judge would never see it. The merge judge cannot protect against a file that has already acted, so the hook asks the owner before each write of either kind that it reads: an Edit, Write, MultiEdit, NotebookEdit or patch, or a shell write, move or delete whose path the command line names. A move or delete of `.github/workflows` itself, of `.github`, or of a directory named `.claude`, is asked too, since it changes every file the directory holds. The question is one sentence he can answer without knowing the guard: "This changes what GitHub runs with this repository's secrets, before any merge (`<path>`). Allow it?" or "This changes the instructions agents follow in this project, starting now (`<path>`). Allow it?". An inline program that writes is read as writing each file one of its strings names whole, or names as a word of a string that reads as a command (one holding a redirect, or starting with a command that writes). A program that names `AGENTS.md` inside a sentence and writes another file asks nothing. A locked path among them stays denied; on the default branch a guard path among them is denied with the way to a branch, and a nested instruction file that is no guard path is asked there too. The definition of an instruction file is one, `ratchet_guards.early`, matched without letter case; `.claude/worktrees/` is not an instruction directory, since each worktree under it is a checkout judged from its own root. Like every path rule it is on only once the manifest is on the default branch, so the adoption writes its workflows and instructions with no prompt. The workflows need no group of their own, so the template has none: they stay in `ci`, which the merge judge reads.
- **The manifest is locked against loss and open to additions.** The hook and the merge judge read it as the default branch holds it (ADR 0005), so a branch that edits it changes nothing until the owner merges it, and the judge sends that merge to the owner. On a branch, an agent's Edit or Write of `guards/manifest.toml` passes when all it does is add: a path after the others in a group's or a door's `paths`, which is how `/ratchet:safeguard` guards a new tool's config, or whole `[[group]]` or `[[door]]` tables after the ones there. The first group that matches a path wins, so a path added to a group that matches a pattern of a group below it, or is matched by one, would take paths from that group, and is not an addition. Any other change to the file, and every shell write, move or delete of it, is denied on every branch, and the owner makes it by hand. If the default branch loses the file anyway, the hook reads the last manifest the branch held and locks every path it named until the owner puts the file back. Before this, a `git rm guards/manifest.toml` committed on a branch, then carried to the default branch by a route the hook does not read (a `git apply` of the diff, or a forged remote-tracking ref), switched every path rule off. The template moves `guards/**` from the harness group into a group of its own, `manifest`, and `.claude/rules/**` into `decisions` beside `CLAUDE.md`: a rule is an instruction, which runs nothing. The conformance gate now checks that `guards/**` is in some group, where it checked that it was locked.
- **What else asks.** A merge an agent types (`gh pr merge`, or a `git merge`, `git cherry-pick`, `git am`, `git read-tree` or `git pull` of another branch into the default one), the agent-ready label, and a hook that cannot run. `git am` and `git read-tree` are new to the list: with a guard path free to change on a branch, either would carry that change onto the default branch past the judge. Each is the owner's to give, and no later step judges it. Each of these prompts says in plain words what the call does and where to look. The merge prompt says the merge job merges a pull request by itself once its checks pass and nothing in it needs the owner, that once they pass it comments on the pull request with each reason it waits for him, one a line, and that `just merge-ready --head <branch>` prints the same reasons. The label prompt says the label marks a ticket ready for agents to build without him. A hook that cannot run says it could not check the call, and to allow it only if he knows what it does.
- **The permission rules are fixed.** The `deny` list in `.claude/settings.json` no longer mirrors the manifest. It is the same in every repository: an `Edit` deny on each path the owner changes by hand, and the command denies, now with `git config core.hooksPath` and `git -c core.hooksPath`. The `ask` list is empty, `gh pr merge` included: a settings `ask` prompts whatever the hook answers, cannot tell a branch from the default one, and shows the owner a rule where the hook shows reasons. This supersedes ADR 0006 in part.
- **Every deny names the way out.** For a locked path or a bypass, a dispute; for the default branch, a branch; after a switch the hook cannot read, that switch in a tool call of its own; for a relative path written after a `cd` the hook cannot follow, an absolute one. That last case is now denied rather than asked, on a branch too, since an agent can always name the path.

## In plain words

**What the hook stops.** The hook reads each tool call before it runs. An agent writes a file with Edit, Write, MultiEdit, NotebookEdit or a patch, or with a shell command that names the file: a redirect, `tee`, `cp`, `mv`, `rm`, `sed -i`, an inline program, or a `git` command that writes that path. For each such write the hook does one of four things:

- It refuses a change to a file the owner edits by hand, on every branch.
- It refuses a change to any other guard path when the commit would land on the default branch, and says to make it on a branch.
- It asks the owner before a write of a CI workflow or an agent-instruction file, on every branch.
- It lets every other change through, and the merge judge reads it at the merge.

It also asks before a merge an agent types and before the agent-ready label. It refuses the gate bypasses, history rewrites and ref moves it reads.

**What it does not stop.** It does not stop a write whose path the command line does not name, or names in a form the hook does not read. In runs against a scratch repository, each route below wrote a nested `CLAUDE.md` on a branch with no prompt. Ten of them (`tar -x`, `unzip`, `git apply`, a variable, `xargs`, a built name, `curl -o`, `git checkout-index`, `git switch`, `git reset --hard`) also wrote `CLAUDE.local.md`, a rule, a skill, a workflow and `.claude/settings.json`, and on the default branch all of those but `git reset --hard` did the same.

- An archive or patch tool writes the files it carries: `tar -x`, `unzip`, `git apply`, `patch`.
- The path is built at run time: a shell variable, a substitution, brace expansion, `xargs`, `awk`'s `print >`, or a name an inline program puts together.
- The tool is one the hook does not read as a writer, such as `curl -o <path>`.
- Git brings the file from a commit: `git switch`, `git reset --hard`, `git checkout-index`, `git merge`, `git cherry-pick`, `git stash pop`, `git worktree add`, `git clone` into a directory, `git update-index`.
- A directory is copied in whole (`cp -r`, `rsync -r`), or the file is written through a symbolic link to a directory.
- A script run by path writes it.

It does not stop a change that reaches the default branch without a merge the judge reads, by the routes under Known limits. It does not guard the files outside the checkout that every session reads: `~/.claude/CLAUDE.md`, `~/.claude/rules/` and `~/.gitconfig`.

**Where the boundary is.** Against an agent that sets out to get round the guard, the boundary is elsewhere, and none of it is in place for the method yet: a hook on the default branch's ref that refuses any commit no merge brought, an operating-system sandbox around the agent's session, and the forge's branch rules. The hook stops the ordinary write and says what to do instead. The boundary has to stop the deliberate one. This decision relies on that boundary, and the hook does not stand in for it.

## Measurement

The owner's calls were replayed from the transcripts: 230 calls, the 174 prompts, 27 denies and 29 calls whose hook timed out in the session. Each ran through the hook as Claude Code runs it, and through a simulation of the settings layer, in scratch copies of both repositories built from their default branches. The copies were upgraded as below for the new hook.

| Calls | Before | After, on a branch | After, on the default branch |
| --- | --- | --- | --- |
| Prompts | 173 | 36: 14 labels, 6 merges, 8 workflow writes, 8 instruction-file writes | 20: 14 labels, 6 merges |
| Guard path changes among them | 153 asked | 139 pass, 14 asked: 8 workflows and 6 edits of `AGENTS.md` | 153 denied, each naming a branch as the way out |

The 16 writes asked on a branch all came from the main agent, none from a subagent, and none was a nested file. The 8 workflow writes came from `/ratchet:adopt` (2), from `/ratchet:feature` rewriting all four workflows (4), and from a session in one project fixing CI (2). The 8 instruction-file writes are real writes of the root `AGENTS.md`: `/ratchet:init` (1), `/ratchet:adopt` (3), `/mattpocock-skills:to-tickets` (2), `/ratchet:feature` (1) and a session in that project writing records (1). The replay copies hold the manifest on the default branch. Six of the 16 came before the other project's adoption merged: the `/ratchet:init` write, three `/ratchet:adopt` writes made while the manifest still held its `# bind:` comments, and the two workflows the adoption brings. With no manifest on the default branch the hook asks none of those, so the sessions as they ran would have met 10 of these prompts.

Three more asks came from inline programs that wrote another file and named `AGENTS.md` or `.claude/skills/` in a string. The hook now reads only a string that names the path whole, or that reads as a command, as a write of it. One of the three now passes. The other two rewrite the manifest from a shell program to bind its `# bind:` lines, and the manifest lock denies them: the hook cannot see what a shell write leaves, so only the Edit and Write tools may add to the manifest. Those 2 calls are what the lock costs in the replay. Both timed out in the sessions as they ran, and ran unjudged. In the same project 5 Edits bound `# bind:` lines inside the groups and doors, which the settings layer denied in the sessions. The replay copies no longer hold the lines those Edits replace, so the hook cannot work out what they write, and denies them there. Judged against the manifest they met, rebuilt by undoing the 5 Edits from the committed one, all 5 are additions and pass.

Hook latency was timed with the two hooks interleaved call by call, so both met the same load (a shared machine at a load average between 12 and 31 on 16 cores), with `main` as this change merges it. The median was 215 ms before and 241 ms after, and the median of each call's ratio, after to before, 1.07; two runs against the `main` of a day earlier gave 1.08 and 1.06. The 99th percentile was 20.3 s before and 0.8 s after, and 22 calls took more than the 10 s Claude Code gives the hook before, none after. The worst cases before were calls the hook never finished: a program whose text held `/** ...`, a JavaScript doc comment, which the hook expanded as a recursive glob from the filesystem root. Claude Code runs a call whose hook times out, so those calls ran unjudged. The hook now expands `**` as a shell without `globstar` does, as `*`. Git processes per call were counted in scratch repositories with a remote. A call that writes no guard path starts 3, and a write of a guard path starts 6, whichever tool makes it. A command that writes three guard paths in one checkout also starts 6, since the count is per checkout, not per file. Without a remote the counts are 5 and 10. In a checkout whose default branch holds no manifest every call starts 4: the fourth walks that branch's history for a commit that held one. On a scratch history of 4,000 commits, packed by `git gc`, the walk took 0.02 s; at that rate it reaches its 5 s limit near a million commits. A path in the project with a `.git` between it and the project root adds one, which lists the project's work trees.

Each tamper attempt below was typed directly at the hook, on a branch and on the default branch, before and after: `Edit` or `Write` of `.claude/settings.json`, `settings.local.json`, `.claude/hooks/`, `agents/` and `skills/`, `~/.claude/settings.json`, `~/.claude/plugins/`, the plugin's own files, `.git/hooks` and `.git/config`; `sed -i`, `echo >`, `rm`, `mv`, `ln` and an inline `python3 -c` on the same paths; `--no-verify`, `-n`, `SKIP=`, `core.hooksPath` by `git config` and `git -c`, `pre-commit uninstall`; `update-ref`, `branch -f`, `replace` and a push to `main`; a forced push; a nested `claude --settings`, `claude plugin disable`, and a branch protection change. Every one is denied in all four runs. The settings layer now also denies `~/.claude/plugins/**` and both `core.hooksPath` spellings.

## Known limits

- A change made on a branch and carried to the default branch uncommitted (`git switch main` with a dirty work tree, or a stash applied there) is committed there unjudged: the hook judges the write, not the commit. So is one carried by git plumbing the hook does not read as a merge, such as `git --git-dir=<main checkout>/.git --work-tree=. commit -a`, which commits a branch's work tree onto the default branch. Denying `git commit` on the default branch closes both. Without a forge, nothing stands behind the local default branch: a change that reaches it by any of these routes is in, and the judge never reads it.
- The label ask reads the label's name from the work tree's `docs/agents/triage-labels.md`. On a branch an agent may edit that file with no prompt, and once it names another label, applying the real one asks nothing.
- A pull request merged through the forge's API by a tool other than `gh`, such as `curl -X PUT .../pulls/<n>/merge`, is not asked about.
- A forge other than GitHub that runs a branch's own CI file (`.gitlab-ci.yml`, for one) is not asked about; its CI paths stay in `ci`. Nor is a file a workflow runs from the branch, such as a local action under `.github/actions/` or a script the workflow calls.
- Removing a directory that holds an instruction file (`rm -rf .scratch/feature`) is not asked: the hook matches the path it is given, not what lies below it. Only `.github/workflows` and a directory named `.claude` are asked as directories. A write of the file is asked only when the hook reads the write, and the plain-words section above lists the writes it does not read. A file planted by one of those is seen first at the merge, or never, if it is gone by then. The same routes write a locked file: `f=.claude/settings.json; cp new.json "$f"` replaces the project's settings with no deny.
- A guard path that acts in the agent's own session can be changed on a branch, used and changed back before the commit. A justfile recipe edited to pass, run by the pipeline's critic, then restored, leaves no change for the merge judge to read.
- An agent's memory under `~/.claude/projects/`, `~/.claude/CLAUDE.md`, `~/.claude/rules/` and `~/.gitconfig` are loaded into every later session and are in no checkout, so a write of them is not asked about. A `git config --global` of a key the hook guards is still denied.
- `.mcp.json`, which names the MCP servers a session in the checkout may start, is in no group the template names and is not asked about. Nor are the instruction files of the other harnesses the plugin supports, beyond `AGENTS.md` and `GEMINI.md`.
- OpenCode has no prompt a plugin can raise, so there a write of either kind throws, and the owner makes it himself.
- A script run by path still writes what it likes. On a branch the merge judge sees the guard path it changed; on the default branch nothing does, as before.
- Claude Code runs a call whose hook times out. Hooks can be registered with `"onFailure": "block"` from Claude Code 2.1.295; the plugin does not yet, since the other harnesses that read `hooks.json` were not checked against the key.
- When git is missing, or a git call runs past its 5 s limit, the hook reads no manifest, and the path rules give no verdict: the call runs as in a checkout that was never adopted. Where the default branch has no manifest at its tip, the hook walks its history for the last commit that held one, and on a long enough history that walk is what runs out of time.
- A default branch replaced by a history that never held the manifest reads as never adopted. The hook refuses each ref move it reads; one it does not read leaves the path rules off.
- A harness that does not set `CLAUDE_PROJECT_DIR` is judged from the session's working directory. Outside the project the checkout is the nearest directory holding `.git`, so a `.git` an agent makes in a sibling checkout still moves that checkout's root.
- A path added to a manifest group is compared with the patterns of the groups below it as written. One that overlaps a pattern only in the paths both match, such as `.claude/hook?/x` against `.claude/hooks/**`, passes as an addition, and the merge judge shows the change to the owner as any manifest change.
- An inline program that names a locked path anywhere in its text, in a docstring as well, and writes any file is denied. Writing this change met three such denials; the Write and Edit tools were the way through.
- The merge prompt names where the reasons are, not the reasons.
- An owner-invoked skill that changes a guard path on the default branch, such as `/ratchet:init` run again, is now denied there, and runs on a branch.

## Upgrading an adopted repository

1. The owner moves `guards/**` in `guards/manifest.toml` out of the `harness` group into a group of its own with no `edit` key, and may move `.claude/rules/**` into `decisions`. The manifest stays locked until this merges, so the owner makes the edit. After it merges, an agent may add to the manifest and change the other files under `guards/` on a branch. No `workflows` group is needed: the hook asks before a workflow write whatever the manifest says.
2. The owner runs `just settings` and commits `.claude/settings.json`. Until then `settings-check` is red and names each `ask` rule and each missing deny.

Without the first step the manifest stays locked, and the hook denies an agent's edit of it as before. Without the second, the old `ask` rules keep prompting for the paths they name.

## Refutation criterion

This is wrong if it lets a guard path change past the owner, or if the prompts come back. Re-run the replay on the owner's next two weeks of transcripts across adopted repositories. It is refuted if a commit on a default branch changes a guard path and reached it by neither a merge the owner made nor one the judge passed; if the owner meets more than five prompts on a working day; or if an agent meets the same default-branch denial three times in a session without making a branch, which would mean the way out does not work.

## Considered options

- **Keep the prompts and ask the owner to read them.** Rejected: the owner said they accept every one, and a control that depends on reading 150 prompts is not one.
- **Answer `allow` on a branch.** Rejected: `allow` skips the harness's own permission flow, and in Antigravity its prompt. The guard never answers `allow`.
- **Ask only on the default branch.** Rejected: an ask there is the same rubber stamp, and no judge reads that commit afterwards. A deny with the way out costs the agent one `git switch -c`.
- **Unlock the agents, skills, commands and workflows under `.claude/` too.** Rejected on the evidence above: they act in a session started in the branch's checkout before any merge.
- **Lock the workflows (`edit = "deny"`).** Rejected: a deny makes the owner edit YAML by hand on every workflow change, which costs him more than a prompt he can answer in a sentence.
- **Leave instruction files to the merge judge.** Rejected: a nested one acts before the commit and can be gone by the merge.
- **Keep settings `ask` rules for the paths that are not locked.** Rejected: a settings `ask` prompts even when the hook is silent, and cannot read the branch.
