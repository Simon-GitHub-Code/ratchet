# User interfaces are designed with impeccable, and its records are guard paths

The method composed with two plugins for how work is done and in what style, and said nothing about how anything a person sees is designed, so a user interface built under it had no standard a review could judge against. We decided that `impeccable` is the fourth plugin: every user interface, web or native, goes through it (`shape` before a surface is built, `polish` before it ships, `audit` and `critique` in the critic's hands), its `PRODUCT.md` and `DESIGN.md` are records in the decisions guard group, and `init` names it in `AGENTS.md`. Decided 2026-11-07.

## Refutation criterion

The composition is wrong if agents building a user interface under the method skip `impeccable` in more than an occasional change, or if holding `DESIGN.md` as a guard path blocks `impeccable`'s own commands more often than it catches an unreviewed design change. Check after the first repository with a user interface has ten merged changes.

## Considered options

- Describe design rules in the method's own text: rejected, that is the duplication ADR 0002 removed, for a domain the method has no stance on.
- Leave `DESIGN.md` unguarded: rejected, a design system an agent can rewrite silently is a standard nobody can review against.
