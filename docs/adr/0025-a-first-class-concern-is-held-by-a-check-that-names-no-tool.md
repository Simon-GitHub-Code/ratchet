# A first-class concern is held by a check, and the check names no tool

ADR 0012 made telemetry, feature flags, security testing and load testing first-class, and ADR 0017 said the method ships questions and never a tool. A read of the plugin before its first public release found both claims weaker than they read. A repository could follow every instruction and still ship new behaviour with no flag, run a load smoke that requested only the health route, and keep a telemetry gate whose one planted fault had nothing to do with the instrumented seam, with every gate green. And four tools were required in effect: the mutation gate read two tools' output and nothing else, the coverage gate read one report format, the conformance gate wanted one hook framework's file, and the gates that the method says run weekly had no schedule.

We decided to close each of these with a check a script runs, and to make each check ask for the concept.

- **New surface ships behind a flag, or the owner sees it.** The flags gate judges the registry, so a change that added a route with no flag met no gate. The merge judge already reads the files that record the surface: the paths behind a door whose `on` is `"removal"`, which are the contract artefacts and public-surface snapshots. When a change adds to one of them and only adds, the judge now asks for a flag. The change passes when `flags.toml` gains a flag that is off, or when a line the change adds names a flag the registry holds off. The lines read are the added ones outside `docs/`, the registry and the surface files themselves, so a spec that names the flag proves nothing and a route that shares a flag's name does not hide itself. Otherwise the judge prints `unflagged` and the owner merges. The second way to pass exists because a feature built over several changes sits behind one flag: without it every change after the first would reach the owner. The judge asks only the application types that `application-types.toml` asks `changed flags off and on` of, read from the binding at the default branch's tip, so a library is exempt; a binding that names no type, or one the catalogue lacks, is asked.
- **Any mutation tool feeds the mutation gate.** `scripts/mutation_survivors.py` took `--tool mutmut|stryker` and nothing else, so a Rust, Go or JVM repository had no way to the gate the method calls the test of the tests. It now takes `--tool <name> --mutants <file>`: JSON lines, one object per mutant, with the file, the mutator, the replacement, a status from six words, the start and end of the mutated text, and the first and last line of the enclosing unit when the tool gives them. The repository converts its tool's report in a gate tool of a few lines, which it guards and bites like any other. The identity, the unit hash, the one-to-one matching and the reading of a timeout are those of ADR 0018, unchanged, and the register's `tool` key is whatever name the recipe passes. Stryker's report is turned into the same records inside the script, and mutmut keeps the names it prints, since it prints no position. The docstring carries a converter for `cargo mutants`, and a test runs that text against the output of a real run on a small crate, so the example cannot rot.
- **A question can require a proof by name.** The tier 1 telemetry gate is the repository's own tests, and its one bite was whatever fault the repository chose, so nothing showed that the instrumented seam was what the gate held. ADR 0020 already made one kind of fault compulsory, the emptied collection. This generalises it. A question in `application-types.toml` may list `proofs`, each described once under `[proofs]`; a `[[bite]]` claims one with `proof = "<name>"`; the conformance gate is red while a bound row lacks a bite for a proof its question requires, and `project_bite.py` then requires the gate red on that fault like any other. Three are required: `outside-the-seam` of `telemetry emitted`, `broken-flag-state` of `changed flags off and on`, and `erroring-route` of `load smoke`. The catalogue names what the fault must be and never how to plant it, so it holds for any stack.
- **The load smoke requests what a user requests.** The template recipe sent every request to the readiness URL, and a health route answers while every other route is broken. `with_service.py` now exports the URL it waited on as `RATCHET_READY`, and `load_smoke.py` is red, before it sends anything, when every `--url` is that URL. The template recipe ships with a `--url` still to bind, so it is red until a route is named. A walking skeleton whose one route is readiness passes `--health-only` in place of a `--url`: the smoke requests readiness, is green, and prints on every run that it is health only. The check is in the gate and not in the conformance gate, because the gate is the one place that sees the URLs whatever runs the recipe.
- **The plugin version is one fact.** CI checked the plugin out at a commit written into each workflow, ADR 0001 recorded a version, and a local run took whatever the harness had last fetched, so local and CI gates could differ with nothing saying so. The binding now carries the one pin, `- Ratchet plugin: <version> at <commit>`. The conformance gate is red while a workflow checks the plugin out at any other commit. `plugin_pin.py`, which every tier of the template `justfile` runs first, is red while the plugin the run uses is at another commit or version. Its message gives both ways out: run from a checkout of the pin through `RATCHET_PLUGIN`, or upgrade by changing the pin and every workflow `ref` in one change, which the owner sees because both are guard paths. The fallback path stays Claude Code's. Under any other harness the recipe says to set `RATCHET_PLUGIN`, and each harness page names the path.
- **A ceiling does what the method says of it.** `tiers.md` says a ceiling blocks on the default branch and nightly and reports on a pull request, because runners vary. `budget.py` exited 1 anywhere and the CI template wrapped pull-request jobs in it, and the tier ceilings adopt sets were never measured in CI, where a tier is split into one job per gate. `budget.py` now takes `--over report`, which prints and records the red and exits 0, and the CI template passes it on a pull request only. It also takes `--tier`: a tier's wall clock in CI is its slowest gate, so a gate over the tier's ceiling is the tier over it, and each job is held to the lower of its own ceiling and its tier's. No job adds the gates up. The conformance gate is red on a `ci.yml` without `--over` and on a tier workflow without `--tier`.
- **The weekly gates are scheduled.** `tiers.md` and the binding say `audit-all`, `licenses`, `drift` and `load-soak` run weekly, and nothing ran them. A `weekly` entry point now runs the four one after another, and the `weekly.yml` template schedules it. The gates block nothing, so a red run would be seen by nobody: the workflow may read the repository and write issues, nothing else, and a red run opens one issue or comments on the one already open. The conformance gate is red on a forge that runs `ci` with no `weekly.yml`, with one that has no schedule or cannot write an issue, and on a binding with no `weekly` entry point. With no forge the machine's own scheduler runs `just weekly`, which `runners-and-forges.md` says.
- **Commit hooks are a concept, not one framework.** The conformance gate required `.pre-commit-config.yaml`. What the method requires is that a commit runs tier 0, which `hooks_installed.py` already proves by running the hooks git would run. The binding's `- Commit hooks:` line now names what the hooks are installed from and, for a mechanism other than the `pre-commit` framework, the command that installs them. The conformance gate is red when the named file or directory is missing, when it names no `pre-commit` or no `commit-msg` hook, when a hook runs the whole `tier0`, and when no install command is named. The probe is unchanged and a red names the binding's command. With no line the framework is assumed, so an existing adoption changes nothing. The template stays the `pre-commit` example.

Decided 2026-11-12.

## What these checks do not see

`unflagged` shows that a flag was declared or named beside new surface. It does not show that the surface sits behind the flag: a change can declare a flag nothing reads, which the flags gate catches only where the binding passes `--used-in`. Three false positives are accepted, and each costs the owner one read. A refactoring that exports a helper adds a line to a public-surface snapshot and reaches the owner. So does surface with nothing to turn off, such as a new field on a response that old consumers ignore. So does a change that adds a route behind an existing flag when the code naming the flag was merged by an earlier change. One false negative is known: surface no snapshot records, such as a screen in a user interface with no contract artefact, is not seen, and the review role is still told to look.

The mutation gate trusts the converter. A converter that drops survivors makes the gate green, which is why it is a gate tool: a guard path with a bite of its own. Without a `unit` the gate takes the enclosing top-level declaration, which for a method inside a class is the whole class: an edit anywhere in the class then sends its registered survivors back for review. That is coarse and safe. An entry whose `tool` names no tool the repository runs is never judged, so a misspelt name excuses nothing and is never reported stale.

A named proof is a claim. The conformance gate sees that a bite carries the name, and the bite run sees the gate go red with the words the bite expects. Neither sees that the planted fault is the one the name describes: a bite named `outside-the-seam` that plants a failing assertion passes both. The registry is a guard path, so the owner reads each claim once, when it is written or changed.

`--health-only` does not expire. A service that gains routes and keeps the flag stays green on a smoke that overlaps none of them. Three things stand against that, and none is a proof: the flag sits in the command contract, a guard path; the gate prints that it is health only on every run; and the `erroring-route` proof the load smoke row requires needs a route the smoke requests. A smoke that names one real route and leaves out the ten that matter passes too: which routes are worth overlapping is a judgment the review makes.

The pin check runs where a tier runs. A gate run alone, such as `just lint`, skips it, and so does a runner other than the `just` example until its owner wires the script in. A plugin copy with no `.git` is compared by version only, so two commits that share a version pass. A checkout with uncommitted edits at the pinned commit also passes. The copies Claude Code, Codex and Grok keep on the build machine are git checkouts and were read; pi and OpenCode were not installed there to look at.

The tier ceiling adopt records is a local wall clock, and CI compares each gate's own seconds on a hosted runner with it. Queueing, checkout and toolchain setup are in neither number. A tier that is slow in CI only because its jobs wait for runners is not seen. The conformance check reads for `--over` and `--tier` as words; a workflow that passes `--over report` on every event satisfies it.

The weekly workflow has run on no forge. Its issue step was run against a stand-in for `gh`, and its pins and permissions were read by `pins.py`; a schedule that GitHub disables after sixty days without a commit, a token an organisation forbids from writing issues and a search that misses the open issue are not seen. With no forge nothing checks that a scheduler runs the entry point at all.

For another hook mechanism the conformance gate reads for the two hook names as words in a file it cannot parse; a `lefthook.yml` that names `commit-msg` in a comment passes it. The probe is the proof and it runs before a feature and in `just ratchet`, never in CI, where no hooks are installed. Only plain hook scripts and the `pre-commit` framework were run against the probe; lefthook and husky were not installed to try.

## Refutation criterion

This is wrong if the checks nag or miss. Read the first twenty changes the judge marks `unflagged`: if the owner merges more than half of them unread, the rule is too wide, and the first thing to drop is whichever false positive above accounts for most of them. If a change ships behaviour a user meets with no flag, and its contract or surface snapshot gained a line, the rule has a hole that becomes a test in `hooks/tests/test_merge_ready.py`. The neutral input is wrong if a tool's report cannot be put into it: a mutation tool that gives no file and line for a mutant, or whose statuses do not map onto the six words, shows the record is too narrow. The named proofs are wrong if the catalogue's list grows by tool or by stack: a proof whose description names a product is a preset under another name. They are theatre if, on the next two adoptions, a claimed proof plants something other than what its name says and the adoption review passes it. The readiness check is wrong if adopted services keep `--health-only` past their first feature: find one that has merged a route and still passes the flag, and the flag needs an expiry the gate can check. The pin is wrong if harness updates turn local tiers red so often that owners approve the upgrade unread: that is the silent difference again, with a prompt in front of it. The ceiling split is wrong if red timings on pull requests are never read and the default branch then goes red on a ceiling the pull request already reported: the report would have to block, or be posted where the author looks. The weekly schedule is wrong if the one issue stays open for months with a comment a week: a finding nobody acts on should become a tier 2 gate or be dropped by an ADR. The hook line is wrong if a second mechanism needs a rule of its own in the conformance gate: that would be a list of frameworks again, and the gate should then read nothing but the path and leave the rest to the probe.

## Considered options

- A gate that fails the pull request when new surface has no flag: rejected, some new surface has nothing to turn off, and a red gate has no way to say "the owner decides". The merge judge does.
- Trust the spec's "Feature flag: none" line: rejected, the spec is an agent's word, which is what ADR 0021 refuses to read.
- Require the new flag in the same change every time: rejected, the second change of a feature behind one flag would always reach the owner.
- Ask every type, libraries included: rejected, a library has no runtime to read a flag in, and the catalogue already says so.
- A reader in the plugin for each mutation tool: rejected, that is a list that grows with every tool and goes stale with every release of one, which ADR 0017 ruled out.
- A neutral input that carries the unit's hash: rejected, the gate would then trust the converter for the one value that decides whether an entry is stale.
- Turn mutmut's results into records too: rejected, mutmut prints no position, and its names are already unique, which is what ADR 0018 keyed them on.
- A conformance check that looks for the fitness test itself: rejected, it would have to know each stack's test layout, and a test that exists is not a test that bites.
- Ship the fault for each proof: rejected for the reason ADR 0020 rejected a fault library, whether a fault bites depends on the configuration the repository wrote.
- Make every question's bite a named proof: rejected, for most questions one fault of the repository's choosing is the right size, and a name per question would be a list nobody reads.
- Have the conformance gate read the `load-smoke` recipe: rejected, it would read a `justfile`, and the binding may name another runner.
- Make the skeleton add a real route on day one: rejected, a route with no behaviour behind it is a second health route, and the skeleton's job is to boot.
- Bind the skeleton's row `none` under an ADR until the first route: rejected, nothing would turn the row back on, and a `none` row prints nothing on each run.
- Warn about another plugin version and stay green: rejected, a warning in a tier's output is read by nobody, least of all an agent.
- Have the recipes fetch the pinned commit and run from that copy: rejected for now, it puts a network fetch and a second copy of the plugin on every machine, and the red line already names the fix.
- Keep the commit in ADR 0001: rejected, an upgrade would rewrite a record.
- Try each harness's install path in turn as the fallback: rejected, two harnesses installed at different commits would make the choice depend on the order tried.
- A closing CI job that downloads every timing record and judges the tier: rejected, the slowest gate over the ceiling is the same fact, with no extra job and no extra action to pin.
- Let `budget.py` read the event from the forge's environment: rejected, the script would know one forge; the workflow says which event it is.
- Fail the weekly run and file nothing: rejected, a scheduled run that is red tells only whoever opens the Actions page.
- One issue per red run: rejected, the same finding would be filed every week until it was fixed.
- Add the four gates to the nightly: rejected, the method says they block nothing, and `load-soak` holds load for an hour.
- Drop the conformance check and trust the probe alone: rejected, the probe does not run in CI, so a repository with no hooks at all would pass every CI gate.
- A parser per hook framework: rejected, it is the list of tools this ADR exists to avoid.
