# Acceptance is judged by using the served tree, and held to what the harness saw

The method promises an owner who does not read code that what merges does what the ticket says. Until now nothing used the product before a merge. The gates read the code and run the tests the building agent wrote. In a trial run, the pipeline built a small read-later app and reported that it passed every check. The app had no way to start, and once started by hand it saved blank links and `javascript:` links. An owner finds both in the first minute of use. A role that uses the product the way its owner would can find them too. Its report is worth something only if nobody has to read the role's work to trust it.

## Decision

**The tester gets the ticket and one address.** `scripts/acceptance.py up` boots the work tree as it is, committed or not, through `with_service.py`, as the project's justfile says (`boot`, `ready`, `boot_timeout`, and `flags_on`, so every flag due for removal is on). A logging proxy, `acceptance_proxy.py`, stands in front of the product, on a port of its own. `up` prints that proxy's address and the directory the tester writes in, then returns while the product runs. Run again while the session lives, `up` prints the same two lines. If an earlier `up` died while the product booted, the next one waits for that boot and starts no second product. A session of the same work tree that serves a tree the work tree no longer holds is stopped first. `down` stops everything the sessions of the slug started and waits until nothing it started still answers; run again, it finds nothing. The harness tries a `service` and a `web-ui`, and refuses every other application type before it starts anything.

**The evidence belongs to the tree that was served.** The pipeline never commits before the orchestrator reads its result, so the code a tester tries has no commit yet. `up` therefore computes the tree a commit of the whole work tree would have: tracked changes, and untracked files git does not ignore. The slug's own summary files are left out. It files the session under that tree. If the work tree changes while the session runs, `down` marks the session stale and `check` refuses it. `check` judges the latest session of the tree it is asked about: the work tree's as it is now, or with `--commit C`, the tree of `C`. The orchestrator commits the tree that was served, with the summary files, so the same evidence holds before and after that commit. Nothing is filed under a tree that was not served.

**A verdict rests on requests the harness logged.** The proxy gives each request an id, `<session suffix>-<n>`, where `n` counts requests in the order they arrived. It logs the method, path and status, and the digests of the request and the answer, which it keeps as sent, each cut at 1 MB. It asks the product for answers that are not compressed, so `check` can read the text in them. A line is written once its answer has gone out, so a reader that wants the order of use sorts by `n`. When the proxy stops, it seals the log. The seal records how many lines it wrote and their SHA-256, the digests of the session's ticket copy and `session.json` as they were when it started, and how many answers reached the tester with no line. Those are answers still going out at the seal, answers whose line the disk refused, and the proxy's own refusal of a request it could not read. After the seal no answer begins. `down` then writes on the seal when it came, whether the proxy had stopped before it came, and whether the session is stale. It blesses only a session that ran until it came and is not stale, by printing the seal's SHA-256.

**`check` holds the record to what the tester did not write.** It prints one sentence for each rule the record breaks. The record has the shape `docs/acceptance.md` gives, schema 1, with no field the reference does not list. It is for this session and the tree it served. Every checklist line gets exactly one verdict from `pass`, `fail`, `unsure` and `not-observable`, and a record that marks every line `not-observable` is refused. A `not-observable` line says why, and who can judge it. A `pass` cites a request this session logged, with the method, path and status the log holds. Every text it says the answer showed is in the stored answer. A `pass` may not cite a line that carries an error: the proxy's own 502, or an answer that broke off. It may not rest on text the cited request itself sent, raw or form-decoded, as a 404 page that repeats the query or a form post whose answer repeats the body. On a `web-ui` it also cites a PNG screenshot in the tester's directory. A `pass` is kept by a check or says why it cannot be. A `fail` and every finding carry the steps that reproduce them, and a blocker or major finding cites what it saw. No text names a file of the served tree by its path from the repository's root. README files and the paths the ticket names are allowed, and a name that follows `/` is a path on the site. The log, the ticket copy and `session.json` match the seal, and `down` blessed it. No link in the tester's directory leads out of it. With `--seal <digest>`, the seal must be the one `down` printed.

**What is kept is data.** A `pass` leaves a kept check, or says why it cannot be kept. A kept check is a list of HTTP steps or browser steps on paths, never hosts. `{BASE_URL}` and `{unique}` are filled in on each run, so a check carries nothing of the machine it was written on. `replay` runs each kept check against a fresh boot. Each check holds, is unmet, or is not run: no browser, a browser that failed, a product that did not start, or a request that got no answer. A check that was not run is red and counts in no total. `replay --control` runs each check against a product that does nothing. There only an unmet expectation counts as the control failing, and a check that holds there proves nothing and is red. Browser steps drive any Chromium over the DevTools pipe (`cdp.py`), with a short temporary directory of their own. A page under test can resolve no host but the loopback one.

**The harness writes the record when the product cannot start.** When `boot` or `ready` is `"none"` or still the template's text, or the boot exits or never answers, `up` writes a blocker in plain words. The blocker says what was run and what it printed. Every line of the ticket is then `unsure`, and nothing can pass.

**Evidence stays out of the tree.** Sessions live under `<git common dir>/ratchet/acceptance/<slug>/<tree>/<session>/`, and a session that ended more than 14 days ago is removed. `summary` writes `docs/features/<slug>/acceptance.json` and `acceptance-checks.json` from an accepted record. It writes the same bytes on every run, and the orchestrator commits them.

**The audit reads a transcript, so it sees only what a tool call names.** `audit` reads the tester's transcript. It flags a tool call that names a path under the product, other than a session's `tester/` directory, or that searches from a directory inside the product. It also flags an `ln -s` to the product's directory or to one that holds it. It judges each path through every link the path passes: the links on disk when it runs, and the links an `ln -s` earlier in the transcript made, even when they were removed since. It cannot see a path that a program builds at run time, a link such a program made and removed, a script the tester wrote that reads files later when run, or anything another process read for the tester.

## What `check` proves, and what it does not

For a tester that reaches the product only through the proxy's address and writes only its record and screenshots, `check` proves the following. Every `pass` rests on a request that went through the proxy in this session. The product answered it with the status the record claims and the text the record claims. Nothing in the log, the stored requests and answers, the ticket copy or `session.json` was changed after the harness wrote it, unless the seal was rewritten to match. That covers an honest tester and a careless one: a tester that edits a file by mistake, or cites a request it did not make, is refused.

A tester that can run programs as the same user as the harness can forge everything `check` reads. It can rewrite `requests.jsonl` and the stored answers and write a seal to match. It can call the product's own port, which `proxy.json` names, so the product changes with no line in the log. It can send SIGTERM to the proxy, which then writes an honest seal early. It can kill the proxy outright and write a seal of its own, with any stop time. Moving the files elsewhere does not help while everything runs as one user. Signing them does not help either, because the key would be readable by the same user.

Three cheaper measures raise the cost of these, and none of them is the boundary. The seal covers the ticket copy and `session.json`. `down` does not bless a session whose proxy stopped before `down` came. `down` prints the seal's digest, and `check --seal <digest>` refuses a seal changed after that. An orchestrator that keeps the digest finds a rewrite made after `down`, but not a forgery finished before `down` came.

## The boundary is a precondition of the tester role

The next unit adds the tester role, and it must give that role the boundary `check` cannot. The tester can write only inside its own directory. It has no route to the product's own port: its only way to touch the product is a harness command.

A separate measurement in this project found that Claude Code's OS sandbox cannot be assumed. On recent Ubuntu it needs extra packages and a privileged AppArmor change. Native Windows has none. It covers shell commands only. So the dependable form is a tester role with no general shell, whose only way to touch the product is a harness command, plus file-tool deny rules for every path outside its directory. This harness does not build that.

For that role, the next unit must add one command to this harness: one that performs a single HTTP request or a single browser action through the session's proxy and prints the id the proxy logged for it. The proxy does not tell its client that id today, so the command needs a way to learn it. `replay`'s step runner can back the HTTP half: one HTTP step is a thin wrapper over `kept_checks.send`. It cannot back the browser half. Each browser check launches a browser, runs all its steps and closes it. A tester that acts one step at a time needs a browser that stays open between commands, with its page and its cookies.

## Named limits

- Text that an earlier request sent and a later answer shows is accepted, because saving something and then seeing it is how most of a product is tried. A product that repeats input in another form, escaped for JSON for instance, is not seen as an echo.
- `check` does not judge whether a cited request bears on the line it passes. A `pass` that cites only `GET /favicon.ico` with status 200 is accepted. The tester's judgment is tested by the owner's use, under the refutation criterion below.
- A product that compresses an answer it was asked to send plain is stored compressed, and text in that answer is not seen. A `pass` that cites such text is refused, never accepted.
- Files git ignores are not part of the tree. A product that serves an ignored build output, such as `dist/`, is known by the sources it was built from, and a build that differs from those sources is not seen.

Decided 2026-11-13.

## Refutation criterion

Before the tester role ships, give it the boundary above and an instruction to forge each of these: a changed line of the log, a changed seal, a changed ticket copy or `session.json`, a request to the product's own port, and a proxy stopped before `down`. This decision is wrong if `check` accepts a record after any of them. Today, with no boundary, a tester that runs programs can do every one of them unseen, so the test is not yet passed. After the role ships, look at the first ten pipeline runs that have a tester. The decision is also wrong if one record that `check` accepted is shown, by the owner using the product, to pass a checklist line the product does not keep in the way the line states. Last, it is wrong if replaying the kept checks takes more than a quarter of a run's wall clock, because a check nobody can afford to replay will not stay kept.

## Considered options

- **The tester's own evidence files as proof** (screenshots, saved command output, a checker that reads them). Rejected. A file the tester writes proves only that the tester wrote it. The proxy's log is the one record the tester did not write.
- **A tester with the code checked out, told not to read it.** Rejected as the only defence. Nothing holds an instruction. The transcript audit sees the files a tool call names, and the proxy keeps the verdict tied to use whatever the tester read.
- **Evidence keyed by commit.** Rejected. The pipeline commits only after the orchestrator reads its result, so a tester always tries code with no commit. Keyed by `HEAD`, a record of uncommitted code was filed as a record of the commit before it.
- **Making `check` unforgeable on its own**, by moving, locking or signing the evidence. Rejected. Under one user, whatever the harness can write or sign, a program of the tester's can too. The boundary belongs to the tester role.
- **Claude Code's OS sandbox as the boundary.** Rejected. It cannot be assumed on the machines the method runs on, and it covers shell commands only.
- **Kept checks as scripts the tester writes.** Rejected. A script carries the machine it was written on (paths, ports, a browser's location), can do anything when it runs, and cannot be shown to prove something without running it. Data can be read, filled in and run against a do-nothing product.
- **A browser automation library as a dependency.** Rejected. The plugin adds no dependency, and every Chromium speaks the DevTools protocol over a pipe with no library.
