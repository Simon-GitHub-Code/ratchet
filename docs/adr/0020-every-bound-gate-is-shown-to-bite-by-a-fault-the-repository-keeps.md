# Every bound gate is shown to bite, by a fault the repository keeps

ADR 0017 deleted the presets and moved the guarantee from the recipe to the repository: the adopted repository "has shown each of its gates going red on a fault and on an empty collection: its `bite` entry point". Nothing made that true. `scripts/bite.py` proves the gates the plugin ships, and the template's `bite` recipe ran it beside whatever self-tests the repository had written for its own fitness tests. A gate bound to a tool the repository chose was never run against a fault, so a recipe that could not fail stayed green for as long as nobody looked.

Two adopted repositories were looked at, one in Python with uv and one in TypeScript with pnpm. Each was given a fault per bound gate: 34 faults over 29 gates, and 32 over 28. On the first run 16 and 13 of them bit. Some of the rest were faults that named the wrong words. The others were recipes. A documentation-example gate and a fuzz gate were green with nothing to run. A performance gate had no ceiling. Documentation coverage and type coverage were held to a threshold of zero. A smoke gate and a public-surface gate judged the last build, because they skipped the build when its output was already there. A changed-line coverage gate read a report another recipe had left behind, and a reproducibility gate was red on a fresh checkout for the same kind of reason. A test-count gate failed without a word. A static-analysis rule pack flagged none of six insecure patterns planted for it.

The owner decided that a gate with nothing to run is red, and that with no presets a deterministic proof replaces them: each bound gate is shown to bite. We decided how.

1. **The repository keeps the faults.** `quality/bites.toml` holds one `[[bite]]` or more for every Gates row whose Tool cell names a tool the repository chose. A row that pairs a plugin script with a tool of the stack (coverage, mutation, pins, a service gate with the repository's boot command) counts: the half the repository wrote is the half nobody has proven. A row bound `none`, and a row bound to the plugin's scripts alone, needs none.
2. **A bite is a gate, a fault and the words that prove it.** The fault is exactly one of `write` (create or replace a file), `patch` (a diff under `quality/bites/`) and `remove` (delete what the globs match). `expect` is required: words the gate prints because of this fault. Red alone shows nothing, since a fault that breaks the build or the import turns every gate red. The words must occur more often in the red run's output than in the green run's, because a task runner echoes a recipe's own text on both.
3. **Red when empty is one of the faults.** A gate whose question `application-types.toml` marks as judging a collection carries a `remove` bite: the tests, the benchmarks, the fuzz targets deleted, and the gate red.
4. **`scripts/project_bite.py` plants them in a scratch copy.** The copy is the work tree as git sees it, tracked and untracked and nothing ignored, as a repository of its own with the same refs, index and `HEAD`, borrowing the object store. The registry's `setup` commands rebuild what a gate does not build itself, from the lockfile. For each bite the gate runs and must be green, the fault is planted as a change git sees (committed first when the bite says `commit = true`), the gate runs again, and the copy is put back from a snapshot: every visible file, the index and `HEAD`. Gates run at once, one copy per lane. The real work tree is never written.
5. **Five verdicts, one of them green.** `bites`; `DOES NOT BITE`; `RED BEFORE THE FAULT`; `RED FOR ANOTHER REASON`; `THE FAULT WAS NOT PLANTED`.
6. **The whole proof is tier 2, and a pull request pays only when it touches a gate.** `bite-all` runs `bite.py` and then every bite. The tier 1 `bite` runs `project_bite.py --changed`: when the change touches the registry, a patch, the binding, or a path in the manifest's `tool-config`, `gate-commands`, `fitness`, `gate-tools` or `formal` group, it proves the tier 0 and tier 1 gates; otherwise it says there is nothing to prove. A threshold or a register entry is what a gate compares with, and `ratchet-lowered` and the snapshots already judge those.
7. **A gate cannot be added unproven.** The conformance gate is red on a missing or malformed registry, a bound gate with no bite, a collection gate with no `remove` bite, and a bite that names no gate. The registry and its patches sit under `quality/**`, the manifest's `ratchets` group, so dropping a bite asks the owner; a fault's content is inline in that file or in a patch beside it, never somewhere unguarded.

One fault shows that a gate is alive and wired to the thing it judges. It does not show that the tool's rule set is complete, and the method does not claim it. A gate nobody can plant a fault for is not a gate: its row is rebound `none` with a reason and an ADR, and the registry has no key that excuses one.

The tier 1 `bite` no longer runs `bite.py`. The plugin's own gates are proven in the plugin's `just check` and again in every adopted repository's `bite-all`. Decided 2026-11-12.

Superseded in part by ADR 0028: a gate with nothing to run is red once its question is asked. Before its trigger fires the row is bound `later: <trigger>`, judges nothing and needs no bite. The registry, the proof and its verdicts stand.

Point 2 superseded in part, 2026-11-13: a fault is one of four kinds, and the fourth is `replace`: in a file that exists, the one place an exact text stands becomes another. A fault inside a file other changes also edit, such as a manifest or a lockfile, keeps applying as a `replace` where a patch's context breaks on the first unrelated edit. `expect` and the other three kinds stand.

Points 4 and 5 superseded in part, 2026-11-13: every run of a gate starts from the copy as restoring leaves it, the first green run too, and the snapshot holds every file git sees or tracks, with the index, `HEAD` and the exclude file. Each bite gets a green run of its own, and after a gate's last bite the gate runs again with no fault, once for each set of `args` among its bites that bit, and not at all when none bit. A sixth verdict, `NOT PROVEN`, is a bite whose gate was red again on a later run with no fault planted. So `bites` proves green on the restored copy, red on the fault, and green again. It still proves nothing of where the red came from in three cases: a gate whose verdict hangs on state the restore does not put back (an ignored cache, a file outside the copy, the clock) can flip on its own, and one that alternates still bites; a gate that reads `RATCHET_BITING` can act otherwise in the copy; and `args` that narrow the command prove the narrowed command. A fault is planted only where restoring reaches, and only through descriptors of the copy's own directories, so a process setup leaves running cannot steer it into the real tree through a link. A gate with `B` bites runs at most `2B` times plus one closing run per set of `args` among the bites that bit, where it ran `B + 1`. The cost falls on a gate that flips on its own: one red one run in twenty failed a proof of five bites in 21% of trials before and 46% after, and those reds are named `RED BEFORE THE FAULT` or `NOT PROVEN`.

## Refutation criterion

This is wrong if the proof is theatre or costs more than it finds. On the next two adoptions, count what the first `bite-all` reports besides `bites`: if every verdict is a mistake in the fault and none is a defect of a recipe, the registry is paperwork, and a shorter check replaces it. If a gate that bites later passes a real defect of the kind its bite planted, one fault was too few and the registry needs a rule about which faults. If the registries of three adoptions hold the same fault for the same tool, the shipped fault library rejected below has been earned. If a gate is green in CI and `RED BEFORE THE FAULT` in the copy for a reason other than leaning on what another recipe left, the copy is not the tree a CI job sees and its construction is wrong. If `bite` proves the gates on most pull requests, because the command contract changes with most features, the trigger is too wide. And time it: on a Python trial repository the whole proof took 208 seconds on four lanes, on a machine under heavy load. If `bite-all` comes to take longer than the rest of tier 2 together, it is sharded over the binding's count or split by tier.

## Considered options

- Trust the tool: rejected. That is what was there, and fewer than half the first faults bit.
- A fault library shipped per tool: rejected. The plugin names no tool (ADR 0017), and whether a fault bites depends on the configuration the repository wrote, which is the thing under test.
- Every bite on every pull request: rejected. A gate runs once green and once per fault, so the proof costs at least twice the gates it proves, and most pull requests change no gate.
- One copy of the whole tree, dependencies included: rejected. Copying took 12 and 75 seconds on the two repositories, on a loaded machine; a virtualenv is bound to the path it was built in, so the package manager rebuilt it anyway; and a copy that carries build output hides the recipes that lean on it, which were among the commonest defects found.
- Undo each fault after its run: rejected for a restore from a snapshot. Gates write into the tree (a coverage report, a regenerated public-surface report), and undoing only the fault leaves that for the next gate.
- A `--project` mode of `bite.py`: rejected for a script of its own. `bite.py` calls the plugin's gates as functions on a synthetic repository; this one runs a repository's commands in copies of itself. They share a name and no code.
- A key that marks a gate as unprovable: rejected. It is the loophole the registry exists to close; `none` with an ADR is the honest form.
- Leave `expect` optional: rejected. On the first run a performance gate was red on its planted benchmark only because its own command line was malformed, and red alone would have passed it.
