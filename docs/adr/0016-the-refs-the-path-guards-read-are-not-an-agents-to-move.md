# The refs the path guards read are not an agent's to move

The path guards read `guards/manifest.toml` at the tip of the default branch (ADR 0005), and the additive-records check compares an edit with the merge base of `HEAD` and that branch (ADR 0014). Both trust the local refs, and the hook let through every command that moves one: `git branch -f main <older commit>`, `git update-ref refs/heads/main <older commit>`, `git checkout -B main`, `git switch -C main`, `git symbolic-ref refs/remotes/origin/HEAD <ref>`, `git replace`. An agent that moves the default branch back to a commit before the manifest was committed switches every path guard off. One that moves it back a few commits makes the terms merged since read as its own additions, free to change. A finder agent on 2026-11-11 saw the hook pass each of these commands, and a run in a copy of the dogfood project confirmed the consequence: after `git branch -f main` to the commit before the manifest, a Write to a guard path got no prompt. The owner was about to let agents merge without him, which makes the local checkout the only reader of the guard paths in a repository with no forge to compare, so this had to close first.

We decided that the hook denies, from the first session and whether or not a manifest is committed, any command that moves, deletes or re-points the default branch's ref or anything the guard reads it through. Three parts carry it.

First, the guard reads exact refs. `ratchet_guards.committed` names the default branch in full (`refs/remotes/origin/main`, `refs/remotes/origin/master`, `refs/heads/main`, `refs/heads/master`, or what `refs/remotes/origin/HEAD` names when it names a commit) and checks each with `git show-ref --verify`, which takes no other spelling. Git resolves a short name through `.git/<name>`, `refs/<name>` and `refs/tags/<name>` before `refs/heads/<name>`, so a tag or a stray ref under `main` would have been read in place of the branch. A head that names nothing falls through to the next name instead of switching the guards off.

Second, the command rules (`ratchet_guards.refmoves`, over the names in `ratchet_guards.refs`) refuse a write to a protected ref. Protected are the local `main` and `master`, every ref under `refs/remotes` (the rule cannot know which branch `origin/HEAD` names without asking git, so all of them count) and every ref under `refs/replace`. The commands are `git branch` creating, forcing, deleting, renaming or copying onto a default branch, or deleting a remote-tracking one; `update-ref`, also with `--stdin` and on `HEAD` while on main; `symbolic-ref` setting or deleting; `switch` and `checkout` with `-c`, `-C`, `-b`, `-B`, `--create`, `--force-create` or `--orphan` naming a default branch; `worktree add -b` and `-B`; `fetch` and `pull` with a refspec, or `--refmap`, whose destination is protected; `push` to a protected ref other than main's own name, which `push-main` still judges; `rebase` while on a default branch or naming one as the branch to rebase; `reset` that moves the branch it runs on, in any mode, while on main; `remote add origin`, `add` with `--mirror` or `-m`, and `set-url`, `set-head`, `set-branches`, `rename` and `remove`; `git config` or `git -c` on `remote.*`, `url.*`, `alias.*`, `include.*`, `extensions.*`, `core.useReplaceRefs`, `core.worktree` and a few siblings, or `git config --edit`; and `replace`, `fast-import`, `send-pack` and `receive-pack` whole. Each rule reads its arguments as git does: any unambiguous prefix of a long option, bundled short flags, `-C` and `git -c` before the subcommand, a refspec's destination after its colon, a `*` in a pattern. The existing machinery carries them through `sh -c`, `eval`, `env`, `xargs`, substitutions, heredocs and `find -exec`, and an interpreter given a program inline is now read for the `git` it runs (`subprocess`, `os.system`, `child_process`, `system`), whether as a command string or as an argument list. A reset that moves main was already refused with `--hard`; the other modes and a bare commit-ish are refused now, and `git reset -- <path>` and `git reset HEAD <path>` still pass.

Third, the files are guarded as well as the commands. The `git-state` group (`.git/refs/**`, `packed-refs`, `HEAD`, `info/grafts`, `shallow`, `objects/info/**`) is built into the hook with `edit = "deny"` and applies in every checkout, adopted or not, to the Edit tools and to a shell write, move, copy, link or delete. The template manifest's `local-git` group lists the same paths, so `just settings` writes an `Edit` rule for each, and a test keeps the two in step. `settings_rules.py` also writes command denies for the plain spellings of the above, never for a command the hook allows in another spelling (ADR 0006), so `git symbolic-ref` has none because reading `origin/HEAD` is ordinary.

What still passes, each a row in the corpus: `git pull` and `git merge --ff-only` on main, `git fetch`, `git switch main`, `git branch feature/x`, `git switch -c feature/x main`, `git commit`, `git branch -f feature/x`, `git update-ref` on a ref outside `refs/remotes` and `refs/replace` that is not a default branch, `git worktree add <path> -b feature/x`, `git stash`, `git rebase main` on a feature branch and `git clone`. A merge into the default branch is the merge rule's, not this decision's. Decided 2026-11-11.

## Refutation criterion

This is wrong if a command line the hook reads moves the default branch's ref, or the refs and settings it is read through, and passes. The standing attempt is `hooks/tests/test_default_ref.py`: each command there runs against a real repository, first to show that it does switch the path guards off, then behind the hook, where it must not. A new spelling that passes, found by hand or by an adversarial reviewer given only `refmoves.py`, goes into that file and the corpus before it is fixed. It is also wrong if the rule costs more than it protects: count the `default-ref` and `reset-main` denials in the first ten pull requests built this way, and if more than one in ten was a command the agent needed (a rename of the branch it was on, a `reset` it meant for a path), the rule is too wide and gains a narrower reading of that spelling.

Known residue, caught by no rule. A ref name that a variable, a file or a pipe supplies (`git branch -f "$b" old`, `xargs -I{} git branch -f {} old` with the name on stdin); a script file run by path (`python3 tool.py`, `sh run.sh`), which can run any of these commands or write `.git/refs` itself; a program decoded or fetched before it runs; an alias, a global hook or a `GIT_*` variable set in the owner's own configuration, outside the repository. Commits made on the default branch move it forward only, and their content meets the path rules when it is written. `git reflog expire`, `git gc --prune` and `git pack-refs` change no ref and are not refused. `guard-diff` in CI, on a forge's own copy of the default branch, still names the change; a repository with no forge has no second reader, which is why the first reader refuses.

## Considered options

- Pin the default branch's tip in a file or an environment variable and compare: rejected, anything an agent can set it can forge, and the file would need the same protection as the refs.
- Read the manifest from the forge on every call: rejected, it needs the network for each tool call and a login the hook should not hold, and the local reader is the one this decision protects.
- Check the refs after the command, in a post-tool hook: rejected, the damage is done and the next tool call is already judged by it; a refusal before the command is the only form that holds.
- Deny `update-ref` and `symbolic-ref` whole: rejected, `update-ref refs/heads/feature/x` and reading `origin/HEAD` are ordinary, and the hook itself reads the latter.
- Protect only the names `main` and `master`: rejected, `origin/HEAD` may name `trunk` or `develop`, and the guard cannot tell without a git call on every command, so every remote-tracking ref is protected instead.
- Allow ref writes on feature branches only, by an allow-list of prefixes: rejected, branch names are the project's (`fix/`, `docs/`, a ticket number) and an allow-list would refuse most of them.
- Make `.git/refs` read-only on disk: rejected, git itself writes there, and the hook must not depend on the owner's file modes.
- Rely on permission rules alone: rejected, a rule matches a command's words, so each of git's spellings (`-C <dir>`, `--git-dir`, option order, prefixes) would need its own rule; the rules ship as a second layer for the plain spellings.
- Supersede ADR 0005: rejected, what the guard reads and where it reads it from are unchanged; this decision protects the reading, so ADR 0005 gains a pointer and keeps its status.
