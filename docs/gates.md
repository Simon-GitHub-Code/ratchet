# The gates that ship

Reference for every gate the plugin ships, and the scripts a tier or a merge runs beside them. [The README](../README.md) says what the method is; [`skills/method/tiers.md`](../skills/method/tiers.md) says which question each gate answers and when it is asked.

These gates need no stack, so the plugin ships them as code and proves them in its own `just check`: `scripts/bite.py` runs a gate against a synthetic violation, red with it and green without, `conformance.py --self-test` does the same for the conformance gate, and the tests cover the rest.

| Gate | Tier | The question it answers |
| --- | --- | --- |
| `scripts/commits.py` | 0 | does every commit subject follow the convention? |
| `scripts/markers.py` | 0 | did the count of TODO, FIXME, HACK and XXX markers rise? |
| `scripts/suppressions.py` | 0 | did any kind of suppression the binding lists rise, or a marker it forbids appear? |
| `scripts/prose.py` | 0 | do the documents and comments keep to the glossary? |
| `scripts/snapshots.py` | 0 | does each gate config the guard manifest lists match its recorded copy? |
| `scripts/lowered.py` | 0 | was a threshold lowered, or a ceiling raised? |
| `scripts/flags.py` | 0 and 2 | is every feature flag declared once, owned and off when new; with `--expired`, is one past its removal date? `--temporary` lists the flags a gate that requests routes boots with on |
| `scripts/pins.py` | 0 | is every action pinned by commit, every image by digest, and does every workflow set a top-level `permissions:` block? |
| `scripts/coverage_groups.py` | 1 | is each coverage group at its ratchet, and each absolute path at 100%? Fed by the suite's Cobertura or LCOV report |
| `scripts/mutation_survivors.py` | 1 and 2 | is every surviving mutant registered, and no entry stale? Fed by any mutation tool through one neutral format: one JSON line per mutant, which the project's mutation recipe writes from its tool's report (ADR 0050) |
| `scripts/change_size.py` | 1 | is the change within its product files and lines ceiling, and its test lines within their own (ADR 0045)? (which paths are tests is the binding's `## Test paths`; records, the owed ledger (ADR 0076), the lockfiles the binding's Dependencies section names and their snapshots are not counted; a moved file counts by its changed lines) |
| `ratchet_guards.diff` | 1 | which guard paths changed? |
| `scripts/settings_rules.py` | 1 | do the permission rules hold the fixed denies, and ask nothing? `--write` (the `settings` entry point) writes them, and refuses under a plugin other than the one CI runs, whose check would reject what it wrote |
| `scripts/conformance.py` | 1 | does the repository still carry the method: its records, its binding, its application types, its Speed section, its CI shape? `--self-test` shows it bites |
| `scripts/with_service.py` | 1 | does the deliverable start and answer? Boots a service by any command, waits until a URL answers, stops the boot command's whole process group, retrying once on a new port when a service on a port it picked exits before it answers; with a command after `--` it holds the service up for that command. It replaces `{host}` with the ready URL's host, which a boot line passes where the service takes its address, and when the service first answers it reads where each listener of the boot command's process group and its descendants is bound, or, when none of them holds the ready URL's port, also the listener on that port, and notes each one beyond loopback that `--listens` does not declare (ADR 0079). `--refuses NAME` asks whether it exits non-zero, naming the setting, when `NAME` is missing; `--graceful SECONDS` whether, signalled mid-request, it finishes the request and exits in time |
| `scripts/triggers.py` | 1 | did the change add another instance of a kind whose safeguards are still owed? Counts each kind's instances at the merge base and at head by the binding's Triggers table; the change that brings a kind is green, however many files it touches, and names the rows it made owed |
| `scripts/load_smoke.py` | 1 | does a running service stay correct under seconds of concurrent requests? Judged on errors only, never on latency, and red while it requests nothing but the readiness URL, unless `--health-only` says that is the only route |
| `scripts/with_service.py --graceful` and `--refuses` | 1 | does a service stop cleanly when signalled under load, and refuse to start without a required setting, naming it? |
| `scripts/telemetry_sink.py` | 2 | does the telemetry arrive? An OTLP/HTTP receiver that is green only when traces, metrics and logs arrived non-empty for the expected `service.name`; no collector to install |
| `scripts/project_bite.py` | 1 and 2 | does every gate the repository bound go red on its fault, and on an empty collection? Plants each fault of `quality/bites.toml` in a scratch copy; with `--changed`, only when the change touches a gate, and first checks, planting nothing, that every `patch`, `replace` and `remove` fault of every tier still plants. A gap `quality/owed.toml` owes is named and not red (ADR 0075) |
| `scripts/acceptance.py` | before the merge judge | not a gate: the harness an acceptance tester stands behind, for a `service` or a `web-ui`. `up` boots the work tree as it is, committed or not, behind a proxy that logs every request, gives the tester one address and files the evidence under the tree it served, and starts no session whose product listens beyond loopback on an address the justfile's `listens` does not name, or whose listeners it could not check while `listens` is `none`; `down` stops it all, seals the log and prints the seal's digest; `check` holds the tester's record to that log, so a pass cites a request the harness saw; `replay` runs the record's kept checks on a fresh boot and, with `--control`, against a product that does nothing, where each must fail; `summary` writes what the owner reads. It holds against a careless tester, not one that can run programs: the tester role it is built for may write only in its own directory and touch the product only through a harness command. That role, and the command it needs, which performs one request or one browser action through the proxy and prints the id the proxy logged, are the next unit's (ADR 0035) |
| `scripts/merge_ready.py` | after tier 1 | may this change reach the default branch without the owner? The merge judge: guard paths, disputes and the pipeline's verdict record (no verdict record is asked of records alone; the adoption is judged by the manifest it brings, which must guard at least what the template's does, and by disputes), one-way doors and new surface with no flag once the binding declares the life events that make them matter, read from the commits |
| `scripts/merge.py` | with no forge | judge a branch, run `check` on the merge result (`check-deep` for the adoption), and merge it when both pass; `--records` lands records alone from the default branch through a branch of their own |
| `scripts/budget.py` | every tier | did a tier or gate finish under its ceiling in seconds? `--set` records the first ceiling or lowers one and never raises it, `--tier` also holds a CI job to its tier's ceiling, and `--over report` reports without blocking on a pull request |
| `scripts/parallel.py` | every tier | not a gate: runs a tier's gates at once through the repository's own runner, each gate's output whole, every red one named, so local wall clock is the slowest gate and not the sum |
| `scripts/changed.py` | every gate over the change | not a gate: hands such a gate the commit the change is compared with, and runs nothing on the adoption, the change whose base holds no binding |
| `scripts/plugin_pin.py` | every tier | is the plugin this run uses the version, commit and tree id the binding pins, the release CI checks out? The justfile hashes the copy with system git before any recipe runs it, tries the recorded folder's siblings, and is red in one line when no copy on disk has the pinned tree id, with both ways out |
| `scripts/upgrade.py` | after the plugin updates | not a gate: what this plugin version needs that the repository lacks, each item marked `auto`, `agent` or `owner`; it reads the conformance gate's rules and plans on a copy of the repository. `--apply` writes the pin, the workflow refs, the permission rules and every other `auto` item in one run, writes down what the conformance gate can excuse in `quality/owed.toml` as owed, and lists the few findings that stay red |
| `scripts/owed.py` | after an upgrade | not a gate: how many things the project owes since an upgrade, in one plain line for `/ratchet:next`. An owed finding is counted and not red; `lowered.py` is red when a change adds to the list without moving the pin, and the merge judge lets a change that only drops entries through (ADR 0037) |
| `scripts/hooks_installed.py` | before a feature | would a commit here run tier 0? Red with the repair when not: the `hooks-install` entry point (`scripts/hooks_install.py`) where the repository's own hooks are missing, the owner's one command where git config must change; asked by the preflight, the route and `just ratchet`, not by CI |

## The gates a repository adds

Every other gate is the repository's: a tool it chose, behind an entry point the binding names. The plugin cannot vouch for a tool it did not choose, so the repository does: `quality/bites.toml` holds a fault for each such gate, `just bite-all` plants each one and requires the gate red, and the conformance gate is red on a bound gate with no fault (ADR 0020) and on a fault that no longer plants in the work tree as git sees it: a patch that does not apply, a `replace` whose text is gone, a `remove` that matches no file. The part of a fault that reaches a file git does not see is not checked when the registry has a `setup` that may make it, and `bite` and conformance both say so; a file the base or the head commit holds is not one `setup` makes, so a change that moves or ignores it is red. An owed fault keeps its ledger key, the bite and its gate, while the reason it fails changes.
