# The route

Four plugins build software on the method, and most of their skills are the owner's keystrokes. The harness enforces that: a skill marked `disable-model-invocation` is refused to an agent, in the main session and in every subagent, with the instruction not to reproduce it another way. So the method's job at every stage is to say which keystroke comes next, and `scripts/route.py` decides it from the checkout, never from a guess: `/ratchet:next` relays it, every ratchet skill ends with it, and the session hook prints it.

## The invocation rule

- **A user-invoked skill is the owner's.** In mattpocock-skills: `setup-matt-pocock-skills`, `grill-with-docs`, `wayfinder`, `to-spec`, `to-tickets`, `triage`, `implement`, `implement-spec`, `retro`, `handoff`. In pstack: everything except `setup-pstack`, so `poteto-mode`, `how`, `why`, `architect`, `arena`, `swarm`, `interrogate`, `blast-radius`, `no-comments`, `correct`, `reflect`, the verification skills. A page of this method names one of these only as a command for the owner to type, never as a skill an agent loads or a file an agent follows.
- **A model-invoked skill is anyone's.** In mattpocock-skills: `tdd`, `code-review`, `codebase-design`, `domain-modeling`, `diagnosing-bugs`, `grilling`, `prototype`, `research`, `pr`, `wizard`, `writing-for-agents`. `impeccable`, with every sub-command. `pstack:setup-pstack`. An agent calls these through the Skill tool by name, without waiting to be asked; the pipeline's roles use only these. Where the stage table below lists one under "The owner types", the owner may type it for a pass of their own, and an agent building or reviewing the work runs it anyway: an agent that builds a surface without `impeccable` because the table named it as a keystroke has misread the table.
- **Nothing is lost by the rule.** The owner types `/pstack:poteto-mode` once and it reaches `how`, `architect`, `arena`, `interrogate` and the principles on its own, since pstack chains its own skills by reading their files. `/mattpocock-skills:to-tickets` grills and models on its own. What the rule fixes is who presses the first key.

## The stages

Each stage names what the owner types, what exists afterwards, and what the method checks or guards there. Stages 4 to 9 repeat per feature.

| Stage | The owner types | Afterwards | The method's part |
| --- | --- | --- | --- |
| 1 Initialise | `/ratchet:init` | a git repository, `AGENTS.md` naming the four plugins, `CLAUDE.md` linked to it, `PRODUCT.md` from `impeccable init`, the pstack model rule, the first commit, the remote | the hand-over ends with stage 2's command |
| 2 Tracker | `/mattpocock-skills:setup-matt-pocock-skills` | `docs/agents/issue-tracker.md`, `triage-labels.md`, `domain.md`; the labels on the forge | the guard allows `gh label create` for a recorded name on this checkout |
| 3 Adopt | `/ratchet:adopt` | the binding, the gates and their thresholds, the manifest, CI, ADR 0001, the design brief and glossary from `grilling` and `domain-modeling` | the floor bites from the first commit, and every other row is bound or `later: <trigger>`; the path guards switch on when the adoption merges |
| 3b Hooks (whenever missing) | nothing where the repository's own hooks are missing: the route prints the `hooks-install` entry point and an agent runs it. A change of git config is the owner's command (`git config --unset core.hooksPath` where the repository sets one; `git config core.hooksPath <the repository's hooks>` where a global hook does not chain to them) | the commit hooks installed, so tier 0 runs on every commit | `hooks_installed.py` proves it by running the hooks; the route, the feature preflight and `just ratchet` are red until then, and the guard refuses a change of git config from an agent (ADR 0026) |
| 4 Understand and decide | `/mattpocock-skills:grill-with-docs`; `/mattpocock-skills:wayfinder` when the effort is too big for one session; `/pstack:how` and `/pstack:why` on code that exists; `/pstack:architect` at a boundary; `impeccable shape` before a surface | `GLOSSARY.md`, ADRs with their refuters, a design sketch, `DESIGN.md` | conformance checks the records; the records are guard paths |
| 5 Specify | `/mattpocock-skills:to-spec`, then `/mattpocock-skills:to-tickets`; `/mattpocock-skills:triage` for an issue that arrived | the spec issue; tickets with blocking edges, each with the agent-ready label the skill applies | the guard asks once per call that applies the agent-ready label, since the label is the owner's agreement; one call over the tickets of a spec (`gh issue edit <n>... --add-label`, one command over the local ticket files) is one ask that names each |
| 6 Conjecture | `/ratchet:conjecture <ticket>` | `## Conjecture` on the ticket, or on the spec its tickets name as parent: the approach, its refuter, the alternatives and the criticism that killed each | the feature preflight refuses a ticket without one |
| 7 Build | `/ratchet:feature <ticket>` when the owner steps away, or `/ratchet:feature` alone for every agent-ready ticket at once; `/pstack:poteto-mode <ticket, goal, done check>` when they stay | code, tests, commits on `feature/<n>-<slug>`; after a drain, the changes the judge passed merged and one report | the preflight before any agent; `check` on every commit; the guards hold whoever is building |
| 8 Criticise and open | `/pstack:interrogate`, `/pstack:blast-radius`, `/pstack:no-comments`, as the change warrants; agents run `impeccable audit`, `critique` and `polish` on a surface, and `code-review`, themselves | findings with the runs that prove them; the pull request with every template section, `check` green | every finding is a criticism the pull request answers; the merge judge decides who merges |
| 9 Keep | `/mattpocock-skills:retro`, `/pstack:correct`, `/pstack:reflect`; an agent runs `impeccable document` itself on a branch, and the owner merges `DESIGN.md`, a guard path | new lints and tests, skill edits, `DESIGN.md` current | a check that `correct` writes is a gate: `/ratchet:adopt` again binds it; `ratchet` raises the thresholds |

Debugging enters at stage 7: `diagnosing-bugs`, which an agent may call, or `/pstack:poteto-mode` with its bug-fix playbook.

A `/ratchet:feature` run that blocks leaves a stash named `<branch>: blocked run`. The route holds that ticket while the default branch has not moved past the stash, or has gained only records an agent lands alone (ADR 0031), and names the questions or guard edits instead, so `/ratchet:next` never offers a rerun that would block the same way. The owner answering the ticket or landing the edits on the default branch releases it; an answer that moves no commit, as an issue comment on a forge, releases it once the owner drops the stash.

With more than one agent-ready ticket that states a conjecture the route names `/ratchet:feature` with no ticket: the drain, which builds them in work trees of their own and merges what the merge judge passes ([pipeline.md](pipeline.md), ADR 0023). A ticket the drain parked is held by its note in `.ratchet/queue/` until the ticket's text changes, and the route reads that note, not only the stash: it names the step that releases the hold for each kind the note records. A ticket too large for one change names the split (`/mattpocock-skills:to-tickets` on its spec); open questions name the answers on the ticket; guard edits name landing them on the default branch; an owed safeguard names `/ratchet:safeguard`; any other park names a change to the ticket. It never names a bare `/ratchet:feature` for a held ticket, since the drain would refuse it again. Dropping the stash releases nothing.

A spec, tickets, a conjecture or an added term that a skill leaves uncommitted on the default branch land through the merge judge, never as a commit there (ADR 0031). With no forge the route names `just merge --records`, which an agent runs: it commits them on a branch of their own and merges it when the judge and `check` pass. With a forge it names a branch and a pull request. A change among them is the owner's to merge when it gives a ticket the agent-ready label, changes a labelled ticket, the spec it inherits from or whether a ticket it is blocked by is open, closes a ticket, or brings an ADR, which the judge names by its title. So a local ticket batch that `to-tickets` labelled costs the owner one merge, and so do answers or a conjecture written on a labelled ticket, and marking a finished ticket resolved. Its `records/<time>` branch waits, and the route asks the judge about it: it names the owner's merge command with the judge's first reason, or `just merge <branch>` for an agent when the judge passes it, as it does when a run stopped while `check` ran. A `records/<time>` branch checked out is a run that stopped before it switched back, and the route names `just merge --records` again, which finishes it.

A safeguard the project now owes comes before the next feature (ADR 0028). When a merged change brought the first instance of a kind, or the owner declared a life event, and a row it fires is still `later:`, the route names `/ratchet:safeguard` and what is owed: an agent chooses the tool, writes the recipe and the fault, and binds the row. It sits after everything that stops work outright (init, the tracker, adoption, the hooks, an unfinished change, an open branch), since a safeguard is its own branch off a clean default branch. It sits before the records and the tickets, since the next change that adds another instance of an owed kind is red, and binding first keeps that build from stalling. It never hides the build: the `why:` line ends `or carry on with <the step it would otherwise name>`, and `then:` names that step. The change that brought the kind was free, however many files it touched (ADR 0030), and the next one that adds another instance waits for the safeguard, so carrying on costs nothing until the owner adds another; a declared event is never red.

When the tree shows a sign of a life event the binding does not declare (a `signs` glob of `application-types.toml`: a deploy file for `deployed`, a migrations directory for `irreplaceable-data`), the route adds an `also:` line that names the sign, the event's meaning and `/ratchet:safeguard <event>`. Declaring it is the owner's. When the owner says not yet, `/ratchet:next` runs `route.py --decline <event>`, which records each sign it saw in `.ratchet/events.tsv`; the line comes back only when a sign appears that was not there then, so an owner who said no is not asked again for the same evidence.

The route cannot see an incident. When the owner reports one (something broke for them or a user, data was lost, a deploy went wrong), the agent they told proposes an incident record ([records.md](records.md#incident-record-docsincidentsnnnn-slugmd)).

After its three lines the route prints an `also:` line for each question the owner has answered with the recommended option three times running (`scripts/questions.py`, ADR 0022). It proposes a standing answer and changes nothing.

A binding with no plugin pin is the template's: an adoption stopped after copying the templates, and the route names `/ratchet:adopt` to resume it, ahead of the hooks install, which cannot finish an adoption. `/ratchet:adopt` writes the pin last of what it binds.

An `AGENTS.md` that still holds the purpose placeholder sends the owner back to `/ratchet:init`, which an init stopped before its questions were answered leaves unfinished. A local spec with no tickets beside it is split with `to-tickets` before another spec is written. Two more states the route reads from the local tracker. A ticket whose `feature/<n>-*` branch is merged but which is still open is marked resolved before anything is built again. Open tickets of which none is agent-ready name the first unblocked one for the owner to agree, before a new spec is written.

## Where poteto-mode meets the guard

`/pstack:poteto-mode` is pstack's front door and runs its own playbooks. On a repository on the method they run under the guard, and three of them meet it:

- **Opening a PR** rebases unpushed commits into small ordered ones, which the guard allows; it amends only unpushed commits, since an amend of a pushed one is refused. Its `/deslop` and the control skills come from a Cursor kit that is not installed, and pstack's own adapter says to skip them.
- **Babysit, Shipping, Autopilot-full and Orchestrate** merge, retarget or land pull requests. A merge an agent types asks the owner: the guard turns their "land the stack" into one question per pull request. The merge job has by then merged what the merge judge passes, so what is left to land is the owner's.
- **Autonomy** in poteto-mode proceeds on ticket updates without asking. Applying the agent-ready label is the one update the guard asks on, because the label is the agreement the preflight reads.

Nothing here changes pstack. It says what the owner will see when its playbooks and the guard meet.
