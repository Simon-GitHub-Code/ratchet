# The feature pipeline

One agent grading its own work is confirmation, not criticism. A feature is therefore built by roles with fixed sight lines: spec, a ticket check, implement and review always, and a critic with its fix loop once the project is `depended-on`, run by the `pipeline` workflow the plugin ships (`workflows/pipeline.js`), which the `/ratchet:feature` skill invokes once its preflight is green: once for a ticket, and once for each ticket when it drains the queue ([the drain](#the-drain) below). The script is a pure function of its arguments and the agents' structured results, so it resumes cleanly. Each role does its work with the other plugins' skills; the method fixes what a role sees, what it returns and when it is done.

## Roles

| **Spec** | `mattpocock-skills:tdd`: what a good test is, the seams under test; `mattpocock-skills:codebase-design`: placement, seams, deep modules over shallow wrappers | the ticket with its comments, the glossary, the design brief, the relevant ADRs, the architecture ADR and the declared layers, code only as far as placing the feature needs | | `docs/features/<slug>/spec.md` holds numbered Given/When/Then criteria (one for every promise the ticket makes, and for each thing users or other systems send the product, one each for an empty, an oversized and a hostile value), glossary terms, a Design section (placement tied to the architecture ADR and the declared layers, the seams it adds or changes and why each module behind one is deep, what was considered and rejected), the seams under test, the telemetry that shows each criterion working, the feature flag that gates the behaviour or why there is none, a test plan mapped to criteria, the assumptions made, out of scope; the failing tests exist and each fails for the right reason, its failure content quoted in the result and in the spec; tier 0 is green and the new tests are red; the spec runs `tier0` and only its own tests, never `check`. It decides each case of an input the ticket leaves open with the narrowest safe answer (an empty value: nothing is saved and nothing breaks; an oversized one: refused with a message, keeping what the user typed; a hostile one: kept as plain text that does nothing) and lists it as an assumption; a case where that answer takes something from the user, such as refusing an empty value that clears a note, is a `direction` question. A promise of the ticket it believes cannot or should not be built as written is a question under the fork test too, never one it leaves out. When the ticket check finds a gap, the same role amends `spec.md` and its tests once, with the findings in hand: the smallest change that closes each gap, nothing the gaps do not touch (every other criterion keeps its wording exactly), and nothing another ticket of the feature promises. It also estimates the whole change (spec, tests, the critic's share, implementation, records) against the change-size ceiling and proposes a split when the ticket cannot fit. A change that implies a change to the architecture (a new layer, a new kind of storage, a new process boundary) is a `direction` question under the fork test, with options and a recommendation, never decided silently ([ADR 0051](../../docs/adr/0051-the-spec-designs-the-placement-and-the-review-judges-it-against-the-architecture.md)). A sentence about how the method treats the work (what a gate charges) is no promise, and a header the change checks to guard itself is no input. |
| **Implement** | `mattpocock-skills:tdd`: one slice at a time; `impeccable` (`shape`, then `polish`) for any user interface | the spec and its tests, the paths named, and each promise the run kept from the ticket and each input case it assumed after the amend | the ticket, the spec author's reasoning | every listed test passes and `check` exits 0. A test that cannot be made to pass is left red. |

Tests that expose real defects stay, in the one flat critique directory the binding's Critique tests section names, or `tests/critique/` when it names none (`<slug>.<layer>.critique.test.<ext>`), never beside the code. The critic runs `tier0` and its own tests, not `check`. A finding whose kept test passes (`heldByKeptTest`) is resolved by that test. |
| **Review** | `mattpocock-skills:code-review`: its Spec and Standards axes and smell baseline; `mattpocock-skills:codebase-design` for the design axis | the ticket with its comments and `## Answers`, the readings the ticket check settled, the spec, the uncommitted diff, `AGENTS.md`, the glossary, `docs/adr/`, the binding, `docs/disputes/`, `DESIGN.md`, generated contract artefacts | the implementer's notes, the critic's findings | axis A, the spec: criteria narrowed, tests weakened, behaviour added; axis B, the standards, the telemetry and the flag among them; axis C, guard paths; axis D, the ticket, and axis E, the inputs: starting from the readings the ticket check settled, and not arguing them again, whether the change as built still keeps each promise and decides each input case as `spec.md` states, or as the settled reading states where the run kept the promise from the ticket or assumed the case; axis F, the design, with `mattpocock-skills:codebase-design`'s vocabulary: the change against the architecture ADR and the declared layers (a layer or seam violated, a module that bypasses a declared seam, logic in the wrong layer, a new dependency direction, a shallow wrapper, an architecture decision the spec did not raise). Approve only with no blocker or major issue, no dropped promise, no undecided input case, no undisputed guard change, and `check` exit 0. |

The critic runs only once the binding's `- Life events:` line declares `depended-on` (ADR 0028). Before that people outside do not rely on the project, and an adversary on every ticket costs more than what it would find: a ticket is built by spec, the ticket check, implement and review. The merge rule is unchanged. A finding the review opens is still open, and the review still judges the spec's tests and the change against the records.

A skill that spawns sub-agents of its own (`code-review`) is followed in-process: the pipeline fixes the agent count, so the role is the single reviewer its skill describes. The roles call model-invoked skills only (`tdd`, `code-review`, `impeccable`, `diagnosing-bugs`); a user-invoked one is the owner's keystroke and the harness refuses it to an agent. [route.md](route.md)

Three roles read the ticket: the spec role, which writes the spec from it; the ticket check, which reads only the ticket and `spec.md` before anything is built; and the review, which reads the change against the readings the check settled. Every other role works from the spec alone, so a spec that drops or bends a promise of the ticket would be built to the letter and pass every other check. Each of the three reads a local ticket file as the base branch holds it (`git show <base>:<path>`), not the copy in the working tree that an agent of the run could have edited. The check and the review return the same two axes, `ticketPromises` and `acceptedInputs`, from one definition. The schema makes each role answer both and gives each reading the evidence that shows it. It cannot make an answer complete: a list that leaves a promise out fits it, and so does an empty `acceptedInputs`.

A gap the check finds, a promise `dropped` or `bent` or an input case no criterion decides, goes back to the spec role, which amends `spec.md` once while no code exists, and the check reads it again. After that the run decides, and the script asks the owner nothing. A promise still `dropped` is kept from the ticket: the readings the script settles say, in the ticket's words, that the app does it; the implementer builds it with a test; the review judges the build against it; and it joins the `assumptions` as "the plan left this out, so it was built as your ticket says", which the owner overrules as he would any assumption. A ticket line about how the change is built, such as a tool to run, is kept the same way. A case still undecided takes the safe answer the same way (an empty value: nothing is saved and nothing breaks; an oversized one refused with a message; a hostile one kept as plain text that does nothing), and joins the `assumptions` under the input's plain name. A promise still read as `bent` is a reading the two roles do not share; it joins the `assumptions` and holds nothing. No question comes from the check: the owner is asked only the spec role's own open questions, such as a ticket that contradicts itself or a promise the role believes cannot or should not be built as written, and those still stop the run before the build. At the review a `dropped` promise or an undecided case means the build lost what the spec had: the script files it as a major issue, the verdict record carries it as unresolved, the merge judge refuses, and the result's `ticketFindings` go to the spec role of the next run as `args.ticketFindings`. A `bent` or `assumed` reading at either role joins the `assumptions`, which the pull request lists for the owner to overrule; it holds no merge (ADR 0036).

Severity: *blocker* is a wrong result, data loss, a layer violation or a broken non-negotiable from `AGENTS.md`; *major* is a missing criterion or a test that does not test, a dependency direction the architecture ADR rules out, or an architecture decision made without the owner; *minor* is everything else (a shallow wrapper, a placement the Design section does not explain).

## The loop

0. Preflight. `scripts/feature_preflight.py` on the ticket: open, `## Conjecture` stated, the agent-ready label present, the tree clean, `HEAD` on the branch, and in an adopted repository a commit that would run tier 0 (`scripts/hooks_installed.py`, which prints the repair when the commit hooks are missing, since the pipeline's commits would otherwise skip tier 0). The skill runs it before the workflow and spawns nothing while it is red; the workflow runs it again as its first stage through one low-effort agent that types the command and relays its JSON. Red stops the run with `verdict: "blocked"` and, per failure, what produces the missing piece.
1. Spec. An undecided point is an assumption: the spec takes the conservative, reversible answer, builds on it, and returns it in `assumptions` with its refuter, and the pull request lists each one for the owner to counter (ADR 0013). An assumption is by definition one that can be taken back, so it does not hold a merge: under ADR 0021 the owner may read it after the change has merged. A point is an open question in two cases (ADR 0022). It is `irreversible` when a wrong guess cannot be taken back (stored data lost, a public contract fixed, money spent, a security or privacy rule weakened). It is `direction` when the options are different products, which [the fork test](#the-fork-test) decides. A choice the user could not tell apart is the role's own. Each question carries its kind, two to four options with the recommended one first, and why; the role never asks the owner to confirm. A non-empty `openQuestions` stops the run with `verdict: "blocked"`; the orchestrator asks the owner each one as the registered product question `feature.open-question` ([questions.toml](questions.toml)), writes the answer on the ticket under `## Answers`, and builds the ticket again. So does a non-empty `guardEdits`: criteria that need a guard path changed (an import contract, a shared test fixture, a Layers row, the definition of a term the glossary already has) cannot be met by a run with no owner at the keyboard, so the owner lands those edits first, or builds the ticket with `/pstack:poteto-mode` while present and merges the change. A word the glossary lacks is not one: the spec role adds the term with its *Avoid* list, the guard lets an addition through, and the pull request lists it (ADR 0014).
2. Ticket check. One agent reads the ticket and `spec.md`; a gap goes back to the spec role once, a promise still left out is built as the ticket says it, and an input case still undecided with the safe answer, as above. The check asks the owner nothing.
3. Implement. The change-size gate counts product code and tests apart (ADR 0045): the binding's `## Test paths` section says which files are tests, and each side has a ceiling. After the spec and again after the implementation the script reads the gate's numbers. Product lines over their ceiling stop the run as `blocked`, too large: nothing still to come adds much product code, so there is no margin. Test lines over two thirds of the test ceiling stop it while the critic's tests are still to come, and over the whole ceiling before the project is `depended-on` (ADR 0040). The spec stage also adds up the whole change before it returns (product: the lines measured, the implementation, the records; tests: the lines measured and the critic's) and, when either sum passes its ceiling, stops as `blocked`, too large, with a proposed split.
4. Critique, once the project is `depended-on`; skipped before.
5. Once the project is `depended-on`: while a blocker or major finding remains that no kept passing test resolves, or a test the critic kept failing (whatever the finding's severity), up to two rounds: a *fresh* fix agent (it has not seen the previous implementer's reasoning), then re-critique by title plus a search for new breakage.
6. Review.
7. The script forces `request_changes` when blocking findings are unresolved, when the last implement or fix reported `checkPasses: false`, when the review's own run of `check` on the final tree was not green, when the spec's tests did not fail for the right reason or a test file has no quoted failure, when the critic ran and found nothing and attempted nothing, or when a guard path changed without a dispute naming it, unless it is a dependency the spec named (ADR 0011) or a record whose `guard-diff` note is `additions:` (ADR 0014). `verdictForcedBy` says which.

Each role is one agent. The ticket check adds two when it finds a gap (the amend and the second read), the fix loop two per round, and a change judged again behind another merge two more (reconcile and review). `AGENTS_AT_MOST` in the script holds the most a run spawns before and after `depended-on`; the drain's plan reads it, and a test counts a worst-case run against it. Agents leave every change uncommitted; the orchestrator commits and publishes. An agent blocked by a guard path writes a dispute and returns it.

## The fork test

It decides whether an undecided point is the owner's. `/ratchet:conjecture` applies it to every behaviour of a spec or ticket before anything is built, and the Spec role's prompt carries a copy (below), so the owner is asked before a drain what a drain would stop on.

The rule, which says what a product question is: ask the owner when a choice decides what becomes of something of the user's (kept, deleted, merged, duplicated, overwritten, shared), who may see or do it, or what the user can do at all, and nothing the owner said or answered settles it. Ask all of a step's open questions in the user's words, in one message, each with your recommended answer first and why, so the owner can accept them all at once. A choice an agent wrote down earlier (a spec, a conjecture, an **Assumed** line) does not settle it. Assume, and list under **Assumed**, anything a later change reverses without loss to the user: order, wording, layout, timing, limits, tools, and how it is built.

To apply it, describe the product to one of its users after each option, in the user's words and with no code in the sentence, and read the two descriptions against the rule. What the owner said or answered is what a record keeps as theirs ([records.md](records.md#questions-assumptions-and-standing-answers)): a user story an agent wrote settles nothing unless it quotes them. Where their words do settle a choice, the spec follows them; a criterion that contradicts them is a defect, and the conjecture says so.

The owner's, for example: "When you paste a link you already saved, should it stay one item or become a second one?" (what becomes of their item: duplicated or kept); "When you paste a link you already marked read, should it come back as unread or stay read?" (what becomes of it); "May anyone with the link close a poll, or only the person who made it?" (who may do it). The agent's: the order of a list, the words on a button, a status code, where a check lives, a limit with one plainly safe value, how long to wait for a slow page.

### The Spec role's copy

The pipeline's Spec role reads the test from its prompt in `workflows/pipeline.js`, which a test holds to the text below. That copy is older and asks more than the rule in one place: it also sends a difference only in what the user sees, such as the expired-link page, to the owner. It never asks less. Bringing the prompt to the rule is a change to the pipeline of its own.

The test: describe the product to one of its users after each option, in the user's words and with no code in the sentence. When the two descriptions differ in what the user sees, what they can do, who may do it or what becomes of something that is theirs, the owner chooses. When the user could not tell which option was built, the agent chooses.

- "Should an expired link show a page that says it expired, or send the visitor to the home page?" The visitor sees a different thing.
- "May anyone with the link close a poll, or only the person who made it?" Who may do it.
- "When a voter answers twice, does the second answer replace the first or is it refused?" What becomes of their answer.
- Which HTTP status answers a reserved code. No user's product changes with it.
- Whether the expiry is checked in the store or in the route. The user cannot tell.
- A limit the ticket leaves unstated where one value is plainly the safe one: take it, and the owner relaxes it in a later change.

## The orchestrator

The orchestrator is the `/ratchet:feature` skill's session: it runs the preflight, creates the branch, runs the workflow, reads its result and the spec, and nothing else: reading the implementation would anchor it on one agent's reasoning and defeat the independence the pipeline exists for. If the result is not enough to decide, add the missing field to the schema.

1. Check `verdict === "approve"`, empty `unresolvedBlockingFindings`, and a green tail in `checkOutput`. Otherwise stash what the agents left (`git stash push -u`), switch back to the base branch, and rerun `/ratchet:feature <ticket>` after the ticket has been adjusted, or stop and report.
2. Report every dispute to the owner in the hand-over, in plain words: what the rule stopped and what changing it would allow. It is a report, not a question; the owner answers in their own words if they want the rule changed, and any gate change is theirs.
3. Run the `ratchet` entry point when it is bound, so each threshold rises to what the approved change measured, and confirm `ratchet-lowered` stays green. Commit `filesChanged` and the raised `quality/` files on the branch with a message naming the slug. Without this step a floor recorded at adoption never moves, and coverage can fall back to it with every gate green.
4. Commit what else the change holds. If an ADR is suggested, write it under the next free number: the guard lets a new ADR through, and one that must supersede another or carry a `Relaxes:` line waits for the owner, in an interactive session where the guard can ask. With no forge (the binding's Forge section names a change template instead of a pull request template) the filled template is `.scratch/changes/<branch>.md` (the branch's `/` written as `-`), committed on the branch with the local ticket's `Status:` line set to `resolved` (the local form of `Closes #N`, so the merge resolves it).
5. Write the verdict record: put the result's `verdictRecord` on stdin of the `merge-ready` entry point's `record` form (`just merge-ready record`), and commit the `docs/features/<slug>/verdict.json` it writes alone, as the last commit. The record names the tree the review saw, so any commit after it sends the merge to the owner.
6. Push, and open the pull request with every section of the repository's template filled ([records.md](records.md)), every entry of `recordNotes` (each added term, *Avoid* item and ADR) listed in the Decisions section. With no forge nothing is pushed.
7. The merge judge decides who merges, never the orchestrator ([guards.md](guards.md), ADR 0021). Run the `merge-ready` entry point and report its lines: `merge: agent`, or `merge: owner` with every reason. On a forge the pull request's merge job asks the same judge once `ci` is green, merges what it passes and comments why on the rest. With no forge run the `merge` entry point with the branch (`just merge <branch>`): it judges, runs `check` on the merge result and merges, or prints why the merge is the owner's. Merge nothing by hand.

## The drain

`/ratchet:feature` with no ticket builds every agent-ready ticket (ADR 0023). `scripts/drain.py` holds everything about it that needs no judgement, and the skill runs the pipelines.

- **The plan.** `drain.py plan` lists the open agent-ready tickets with the preflight's verdict on each, ordered by their `Blocked by` lines: `buildable`, `building`, `built`, `waiting`, `held`, `merged` or `refused`. It starts at most three at once unless the owner names another number, and prints the most agents the drain can run, from the numbers the script declares.
- **A work tree per ticket.** `drain.py open <ticket>` makes the ticket's branch and work tree under the temporary directory, outside the repository, and only when the plan starts that ticket. The pipeline runs there (`args.root`). `close`, `land` and `clean` remove it, so no work tree is left for an agent to remember.
- **Merging is serial.** One result is settled at a time. When another change merged first, `drain.py update <ticket>` rebases the branch onto the default branch, or names the conflicts and leaves it as it was. The pipeline then runs with `args.rejudge`: one reconcile agent when the rebase conflicted or `check` went red, and the reviewer again on the change as it now stands, reading the ticket as the base branch holds it and held to the readings the first run's ticket check settled, which the skill passes back as `settled`. The verdict record comes from that review, since the first one saw another tree. `ratchet` runs after the rebase.
- **The judge merges.** With no forge `drain.py land <ticket>` runs the `merge` entry point and closes the ticket with the judge's lines. With a forge the skill opens the pull request and watches it, and the merge job merges.
- **A ticket that cannot go on is parked.** An open question, a guard edit, a dispute, a verdict that is not an approval or a `merge: owner` closes the ticket with the reasons as given, and the others go on. A parked ticket is held until its text changes or a path its run named as the cause (a guard edit, a dispute file) changes on the default branch.
- **One report.** `drain.py report` writes `.ratchet/queue/<date>-<time>.md`: what merged, what waits for the owner and why, what is parked, every assumption with its refuter, every record added, the time each ticket took. The owner's questions come after it.
- **An interrupted drain.** The next one starts with `drain.py clean --all`, which another drain's live session refuses. A merged ticket is done and recorded, a branch with commits goes to the judge, and a build that had not committed is built again. `update` and `land` run again finish what they left: an abandoned rebase starts over, a merge that landed is recorded, a fast-forward cut off half-way is put back.
