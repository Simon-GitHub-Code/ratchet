# The feature pipeline

One agent grading its own work is confirmation, not criticism. A feature is therefore built by roles with fixed sight lines: spec, implement and review always, and a critic with its fix loop once the project is `depended-on`, run by the `pipeline` workflow the plugin ships (`workflows/pipeline.js`), which the `/ratchet:feature` skill invokes once its preflight is green: once for a ticket, and once for each ticket when it drains the queue ([the drain](#the-drain) below). The script is a pure function of its arguments and the agents' structured results, so it resumes cleanly. Each role does its work with the other plugins' skills; the method fixes what a role sees, what it returns and when it is done.

## Roles

| Role | Works with | Sees | Never sees | Done when |
| --- | --- | --- | --- | --- |
| **Spec** | `mattpocock-skills:tdd`: what a good test is, the seams under test | the ticket with its comments, the glossary, the design brief, the relevant ADRs, code only as far as placing the feature needs | | `docs/features/<slug>/spec.md` holds numbered Given/When/Then criteria, glossary terms, placement with reasons, the seams under test, the telemetry that shows each criterion working, the feature flag that gates the behaviour or why there is none, a test plan mapped to criteria, the assumptions made, out of scope; the failing tests exist and each fails for the right reason, its failure content quoted in the result and in the spec; tier 0 is green and the new tests are red; the spec runs `tier0` and only its own tests, never `check`. It also estimates the whole change (spec, tests, the critic's share, implementation, records) against the change-size ceiling and proposes a split when the ticket cannot fit. Open questions stay open. |
| **Implement** | `mattpocock-skills:tdd`: one slice at a time; `impeccable` (`shape`, then `polish`) for any user interface | the spec and its tests, the paths named | the ticket, the spec author's reasoning | every listed test passes and `check` exits 0. A test that cannot be made to pass is left red. |
| **Critic** | the method's rule of evidence, as the one adversary (`/pstack:interrogate` is the owner's to type on the branch afterwards, never the critic's to imitate); `impeccable` `audit` and `critique` for any user interface | the spec, its tests, the changed files, the fitness tests, the fuzz harness | the implementer's notes, the ticket | every finding carries the command and output that proves it, and `attempted` lists every command run, so "nothing found" carries its severity. Property and edge-case tests written; changed-code mutation run; fuzzing run; every new entry point attacked and overloaded, its telemetry read for a secret, its flag flipped; the fitness tests sabotaged in a scratch copy and seen to bite; vocabulary and contracts checked; `guard-diff` run. Tests that expose real defects stay, in the one flat critique directory the binding's Critique tests section names, or `tests/critique/` when it names none (`<slug>.<layer>.critique.test.<ext>`), never beside the code. The critic runs `tier0` and its own tests, not `check`. A finding whose kept test passes (`heldByKeptTest`) is resolved by that test. |
| **Review** | `mattpocock-skills:code-review`: its Spec and Standards axes and smell baseline | the spec, the uncommitted diff, `AGENTS.md`, the glossary, `docs/adr/`, the binding, `docs/disputes/`, `DESIGN.md`, generated contract artefacts | the implementer's notes, the critic's findings, the ticket | axis A, the spec: criteria narrowed, tests weakened, behaviour added; axis B, the standards, the telemetry and the flag among them; axis C, guard paths. Approve only with no blocker or major issue, no undisputed guard change, and `check` exit 0. |

The critic runs only once the binding's `- Life events:` line declares `depended-on` (ADR 0028). Before that people outside do not rely on the project, and an adversary on every ticket costs more than what it would find: a ticket is built by spec, implement and review. The merge rule is unchanged. A finding the review opens is still open, and the review still judges the spec's tests and the change against the records.

A skill that spawns sub-agents of its own (`code-review`) is followed in-process: the pipeline fixes the agent count, so the role is the single reviewer its skill describes. The roles call model-invoked skills only (`tdd`, `code-review`, `impeccable`, `diagnosing-bugs`); a user-invoked one is the owner's keystroke and the harness refuses it to an agent. [route.md](route.md)

Severity: *blocker* is a wrong result, data loss, a layer violation or a broken non-negotiable from `AGENTS.md`; *major* is a missing criterion or a test that does not test; *minor* is everything else.

## The loop

0. Preflight. `scripts/feature_preflight.py` on the ticket: open, `## Conjecture` stated, the agent-ready label present, the tree clean, `HEAD` on the branch, and in an adopted repository a commit that would run tier 0 (`scripts/hooks_installed.py`, which prints the repair when the commit hooks are missing, since the pipeline's commits would otherwise skip tier 0). The skill runs it before the workflow and spawns nothing while it is red; the workflow runs it again as its first stage through one low-effort agent that types the command and relays its JSON. Red stops the run with `verdict: "blocked"` and, per failure, what produces the missing piece.
1. Spec. An undecided point is an assumption: the spec takes the conservative, reversible answer, builds on it, and returns it in `assumptions` with its refuter, and the pull request lists each one for the owner to counter (ADR 0013). An assumption is by definition one that can be taken back, so it does not hold a merge: under ADR 0021 the owner may read it after the change has merged. A point is an open question in two cases (ADR 0022). It is `irreversible` when a wrong guess cannot be taken back (stored data lost, a public contract fixed, money spent, a security or privacy rule weakened). It is `direction` when the options are different products, which [the fork test](#the-fork-test) decides. A choice the user could not tell apart is the role's own. Each question carries its kind, two to four options with the recommended one first, and why; the role never asks the owner to confirm. A non-empty `openQuestions` stops the run with `verdict: "blocked"`; the orchestrator asks the owner each one as the registered product question `feature.open-question` ([questions.toml](questions.toml)), writes the answer on the ticket under `## Answers`, and builds the ticket again. So does a non-empty `guardEdits`: criteria that need a guard path changed (an import contract, a shared test fixture, a Layers row, the definition of a term the glossary already has) cannot be met by a run with no owner at the keyboard, so the owner lands those edits first, or builds the ticket with `/pstack:poteto-mode` while present, where the guard can ask. A word the glossary lacks is not one: the spec role adds the term with its *Avoid* list, the guard lets an addition through, and the pull request lists it (ADR 0014).
2. Implement. After the spec and again after the implementation the script reads the change-size gate's two numbers: a change already over two thirds of the ceiling stops as `blocked`, too large, and the owner splits the ticket, since the critic's tests and the fixes are still to come. The spec stage also adds up the whole change before it returns (the lines measured, the implementation, the critic's tests, the records) and, when the sum passes the ceiling, stops as `blocked`, too large, with a proposed split.
3. Critique, once the project is `depended-on`; skipped before.
4. Once the project is `depended-on`: while a blocker or major finding remains that no kept passing test resolves, or a test the critic kept failing (whatever the finding's severity), up to two rounds: a *fresh* fix agent (it has not seen the previous implementer's reasoning), then re-critique by title plus a search for new breakage.
5. Review.
6. The script forces `request_changes` when blocking findings are unresolved, when the last implement or fix reported `checkPasses: false`, when the review's own run of `check` on the final tree was not green, when the spec's tests did not fail for the right reason or a test file has no quoted failure, when the critic ran and found nothing and attempted nothing, or when a guard path changed without a dispute naming it, unless it is a dependency the spec named (ADR 0011) or a record whose `guard-diff` note is `additions:` (ADR 0014). `verdictForcedBy` says which.

At most nine agents run, the preflight's included, and at most two more when the change is judged again behind another merge. Before the project is `depended-on` it is four: the preflight, spec, implement and review. Agents leave every change uncommitted; the orchestrator commits and publishes. An agent blocked by a guard path writes a dispute and returns it.

## The fork test

It decides whether an undecided point is the owner's because the options are different products. The Spec role's prompt carries this text and `/ratchet:conjecture` applies it, so the owner is asked the same things before a drain as during one.

The test: describe the product to one of its users after each option, in the user's words and with no code in the sentence. When the two descriptions differ in what the user sees, what they can do, who may do it or what becomes of something that is theirs, the owner chooses. When the user could not tell which option was built, the agent chooses.

Three that are the owner's:

- "Should an expired link show a page that says it expired, or send the visitor to the home page?" The visitor sees a different thing.
- "May anyone with the link close a poll, or only the person who made it?" Who may do it.
- "When a voter answers twice, does the second answer replace the first or is it refused?" What becomes of their answer.

Three that are the agent's to assume:

- Which HTTP status answers a reserved code. No user's product changes with it.
- Whether the expiry is checked in the store or in the route. The user cannot tell.
- A limit the ticket leaves unstated where one value is plainly the safe one: take it, and the owner relaxes it in a later change.

## The orchestrator

The orchestrator is the `/ratchet:feature` skill's session: it runs the preflight, creates the branch, runs the workflow, reads its result and the spec, and nothing else: reading the implementation would anchor it on one agent's reasoning and defeat the independence the pipeline exists for. If the result is not enough to decide, add the missing field to the schema.

1. Check `verdict === "approve"`, empty `unresolvedBlockingFindings`, and a green tail in `checkOutput`. Otherwise stash what the agents left (`git stash push -u`), switch back to the base branch, and rerun `/ratchet:feature <ticket>` after the ticket has been adjusted, or stop and report.
2. Report every dispute to the owner in the hand-over, in plain words: what the rule stopped and what changing it would allow. It is a report, not a question; the owner answers in their own words if they want the rule changed, and any gate change is theirs.
3. Run the `ratchet` entry point when it is bound, so each threshold rises to what the approved change measured, and confirm `ratchet-lowered` stays green. Commit `filesChanged` and the raised `quality/` files on the branch with a message naming the slug. Without this step a floor recorded at adoption never moves, and coverage can fall back to it with every gate green.
4. Commit what else the change holds. If an ADR is suggested, write it under the next free number: the guard lets a new ADR through, and one that must supersede another or carry a `Relaxes:` line waits for the owner, in an interactive session where the guard can ask. With no forge (the binding's Forge section names a change template instead of a pull request template) the filled template is `.scratch/changes/<branch>.md` (the branch's `/` written as `-`), committed on the branch with the local ticket's `Status:` line set to `resolved` (the local form of `Closes #N`, so the merge resolves it).
5. Write the verdict record: put the result's `verdictRecord` on stdin of the `merge-ready` entry point's `record` form (`just merge-ready record`), and commit the `docs/features/<slug>/verdict.json` it writes alone, as the last commit. The record names the tree the review saw, so any commit after it sends the merge to the owner.
6. Push, and open the pull request with every section of the repository's template filled ([records.md](records.md)), every entry of `recordNotes` (each added term, *Avoid* item and ADR) listed in the Decisions section. With no forge nothing is pushed.
7. The merge judge decides who merges, never the orchestrator ([guards.md](guards.md), ADR 0021). Run the `merge-ready` entry point and report its lines: `merge: agent`, or `merge: owner` with every reason. On a forge the pull request's merge job asks the same judge once `ci` is green, merges what it passes and comments why on the rest. With no forge run the `merge` entry point with the branch (`just merge <branch>`): it judges, runs `check` on the merge result and merges, or prints why the merge is the owner's. Merge nothing by hand.

## The drain

`/ratchet:feature` with no ticket builds every agent-ready ticket (ADR 0023). `scripts/drain.py` holds everything about it that needs no judgement, and the skill runs the pipelines.

- **The plan.** `drain.py plan` lists the open agent-ready tickets with the preflight's verdict on each, ordered by their `Blocked by` lines: `buildable`, `building`, `built`, `waiting`, `held`, `merged` or `refused`. It starts at most three at once unless the owner names another number, and prints the most agents the drain can run: four for each ticket before the project is `depended-on` and nine after, and two more for each one judged again.
- **A work tree per ticket.** `drain.py open <ticket>` makes the ticket's branch and work tree under the temporary directory, outside the repository, and only when the plan starts that ticket. The pipeline runs there (`args.root`). `close`, `land` and `clean` remove it, so no work tree is left for an agent to remember.
- **Merging is serial.** One result is settled at a time. When another change merged first, `drain.py update <ticket>` rebases the branch onto the default branch, or names the conflicts and leaves it as it was. The pipeline then runs with `args.rejudge`: one reconcile agent when the rebase conflicted or `check` went red, and the reviewer again on the change as it now stands. The verdict record comes from that review, since the first one saw another tree. `ratchet` runs after the rebase.
- **The judge merges.** With no forge `drain.py land <ticket>` runs the `merge` entry point and closes the ticket with the judge's lines. With a forge the skill opens the pull request and watches it, and the merge job merges.
- **A ticket that cannot go on is parked.** An open question, a guard edit, a dispute, a verdict that is not an approval or a `merge: owner` closes the ticket with the reasons as given, and the others go on. A parked ticket is held until its text changes.
- **One report.** `drain.py report` writes `.ratchet/queue/<date>-<time>.md`: what merged, what waits for the owner and why, what is parked, every assumption with its refuter, every record added, the time each ticket took. The owner's questions come after it.
- **An interrupted drain.** The next one starts with `drain.py clean --all`. A merged ticket is done, a branch with commits goes to the judge, and a build that had not committed is built again.
