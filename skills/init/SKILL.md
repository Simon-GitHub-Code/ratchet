# Initialise a repository

The bare bones. `/ratchet:adopt` builds the gates on top later, when the owner is ready. The template is `${CLAUDE_SKILL_DIR}/templates/AGENTS.md`.

The Ratchet guard hook is already on: its command rules apply from the first session, with or without a binding, and nothing in these steps should trip it. If a tool call is denied while you follow this skill, that is a bug in this skill: write the dispute as [Before adopt](#before-adopt) says and tell the owner. Keep any command the guard might refuse in a Bash call of its own; a denied Bash call runs none of its commands, so a file write chained with it is lost.

Every step says when it is already done. A second run on the same directory skips every step and ends with the same hand-over.

## What the owner is asked

The owner is asked about the product they are making and about nothing else (ADR 0034). The questions below go to the owner in one message, in this order, each in the words written here, with your recommended answer first where the records give one, two to four options where options help and the free-text answer always open, so the owner can accept them all at once; an answer is taken as given, never refined with a follow-up. A question whose answer a record already holds (a README, a package manifest, `PRODUCT.md`, an earlier run) is not asked: read the answer and say where it came from in the hand-over.

1. **Ask** `init.purpose`: "What are you making? Tell me in a sentence or two what it should do."
2. **Ask** `init.user`: "Who is it for, and what are they doing when they reach for it?"
3. **Ask** `init.difference`: "What should make it better for them than what they use today?"
4. **Ask** `init.place`: "Where will people use it: on this computer only, on other devices at home, or from anywhere?"
5. **Ask** `init.online`: "Should this project be kept on this computer only, or also as a private copy on your GitHub account?" Only when `gh auth status` succeeds and `origin` is missing (`glab` and GitLab alike); otherwise the repository stays local and the hand-over says why. The remote is created only from an answer that asks for it.

**What the owner asked for wins.** Anything typed after the command (`/ratchet:init no GitHub, use Python`) is a preference. It chooses among the options a choice allows and never loosens a safeguard, as [the rule on preferences](../method/records.md#a-preference-typed-after-a-command) says: read it before you act on one. Within that, it settles the choice it names, it wins over the defaults below, and a question it answers is not asked ("no GitHub" answers `init.online`). Each one is listed under **Assumed** as "you asked for", or as not applied with the route that exists.

Questions 2 and 3 are `impeccable init`'s own first two; asked here, they are passed to it in step 5 so it does not ask again.

**Everything else is assumed.** Take each default below from the evidence, act on it, and list it in the hand-over under **Assumed** (step 9) with what changing it later costs, where the owner reads it and overturns it in their own words. Leave out a row whose step is already done.

- **Assume** `init.defaults`: the repository name is the directory name (the `gh repo view` name when `origin` exists); the issue tracker is GitHub Issues when the repository has a GitHub remote or gets one from `init.online`, GitLab's likewise, and local markdown otherwise (the tracker's record, labels and domain-doc layout are written by `/mattpocock-skills:setup-matt-pocock-skills`, which the owner types after init); pstack's models are the tiered mix at `medium` when `~/.claude/rules/pstack-models.md` is missing; a missing companion plugin is installed by the harness page's commands.
- **Assume** `init.stack`: on an empty directory, the stack your reading of the purpose and of where it is used points to, the plainest that does the job, named with its reason in a clause (a list kept on a phone and a laptop needs a small server and a store; one page on one device does not). A repository with code has its stack already.
- **Assume** `init.interface`: a web interface that works on a phone and a laptop, unless the purpose names something else (a native app, a command-line tool, a service with no screen) or the code has one already.

## Steps

1. **Check the ground.** Name the harness you run in and read its page, `${CLAUDE_PLUGIN_ROOT}/docs/harness/<harness>.md` (Claude Code, Grok, Codex, Antigravity, pi or OpenCode): it gives the command that lists installed plugins, the one that installs each of the four, and the names this skill uses mapped to that harness. List the plugins; note each one's version and marketplace (`<plugin>@<marketplace>` in Claude Code) for step 5. When `mattpocock-skills`, `pstack` or `impeccable` is missing, run the page's install commands, each in a Bash call of its own (`init.defaults` assumes it); installing is allowed, removing is refused. In Claude Code the ratchet marketplace declares the three as dependencies, so they are normally already there. A plugin the page says has no package for this harness is reported in the hand-over as missing, not installed another way. `gh auth status` (and `glab auth status` when `glab` exists) decides whether `init.online` is asked. Look for code: a package manifest, a lockfile, source directories; none means greenfield, and `init.stack` is yours. Then git:
   - No `.git` here and no enclosing repository (`git rev-parse --show-toplevel` fails): run `git init -b main`. An empty directory is the normal case, not a failure.
   - `.git` is a directory: nothing to do.
   - Ambiguous: `.git` is a file (a worktree or submodule), `git rev-parse --show-toplevel` names a parent directory (a nested checkout), or the directory is a bare repository. Stop and say what you found: the owner runs init again in the directory they mean.

   Ask the questions of [What the owner is asked](#what-the-owner-is-asked) and settle the assumptions. Done when the directory is the top level of a git repository, the four plugins are listed (or the hand-over will name the one missing) and each question is answered.

2. **Write `AGENTS.md`.** Copy the template to the repository root. If an `AGENTS.md` already exists, insert the template's opening stanza (the four plugins and their questions) above its first heading and keep the rest. If a `CLAUDE.md` with content exists and no `AGENTS.md`, move that content under the stanza. When the stanza is there but a plugin line differs from the template's (an older ratchet wrote it), replace those lines with the template's and name them in the hand-over; the route sends the owner here when they differ. Done, and skipped on a rerun, when `AGENTS.md` opens with the four-plugin stanza and its plugin lines match the template.

3. **Link `CLAUDE.md`.** `ln -s AGENTS.md CLAUDE.md` at the root, replacing a plain `CLAUDE.md` whose content step 2 moved. Done, and skipped, when `CLAUDE.md` is a symlink to `AGENTS.md`. Then append to `.gitignore` (create it if missing) each line of `${CLAUDE_SKILL_DIR}/templates/gitignore` it lacks: the agent worktrees pstack's panels leave under `.claude/worktrees/` and impeccable's caches, which whole-tree gates would otherwise judge. Done, and skipped, when every line is present.

4. **Fill the title and "What this is".** Replace `# <project>` with the repository name and write the purpose paragraph from the owner's answers, in their words where they gave them. Then record the two answers a later command would otherwise ask again, since the owner gave them once:
   - **The stack.** When `init.stack` was assumed and `impeccable` will not run (`init.interface` is no user interface), add a `## Stack` section after "What this is" with the stack and where it is used. Adopt reads `## Stack` to recognise the stack it chooses tools for, from `PRODUCT.md` when impeccable writes one, from here otherwise.
   - **The tracker.** Under the "Agent skills" heading, above its placeholder, add one line naming the tracker `init.defaults` settled and why, such as `Tracker chosen at init: local markdown, because the repository has no remote.` The tracker setup reads this file and takes it as its answer.

   The sections below keep their placeholders: "Agent skills" for the tracker setup, the rest for `/ratchet:adopt`. Done, and skipped, when the title and "What this is" have no angle-bracket placeholder.

5. **Run the other plugins' setup once, from the answers already given.** Resolve a plugin's files at `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, with the marketplace and version from step 1; when in doubt, `find ~/.claude/plugins/cache -path '*/<plugin>/*/SKILL.md'`.
   - **`mattpocock-skills`.** Not run here. Its `setup-matt-pocock-skills` skill is user-invoked (`disable-model-invocation: true`): the Skill tool refuses it to an agent and its author's rule is that no skill calls or imitates it, so the owner types `/mattpocock-skills:setup-matt-pocock-skills` after init, and the hand-over names it as the next command. It writes `docs/agents/issue-tracker.md`, `triage-labels.md` and `domain.md`, fills the `## Agent skills` section of `AGENTS.md`, and creates the labels on the forge (the guard allows `gh label create` for a name in the record it just wrote). Init creates the remote first (step 7) so that those labels have somewhere to go. Skipped, and said so in the hand-over, when `docs/agents/issue-tracker.md` already exists. A forge tracker needs a repository, so a repository with no remote has local markdown as its tracker, and the hand-over says why. Put its `## Agent skills` block in the template's "Agent skills" section of `AGENTS.md` (edit `AGENTS.md`, the link target, not `CLAUDE.md`).
   - **`pstack`.** Skipped when `~/.claude/rules/pstack-models.md` exists; say so in the hand-over, since the owner may not remember writing it. Otherwise read `<pstack>/docs/harness/claude-code.md` first (it maps the skill's Cursor names and says the rule is written to that path), then follow `<pstack>/skills/setup-pstack/SKILL.md` with the budget answered as `medium` and the roles taken from the tiered mix: `haiku` for read-only exploration, `sonnet` for code-writing and investigation, `opus` for judgment, prose and synthesis, panels mixing `opus` and `sonnet`; every model written must be one the Agent tool lists. Skip its two closing offers (a verification skill, a formal verification skill): `/ratchet:adopt` names them in the binding's formal group when the stack is known. The file is pstack's, not this plugin's; `init.defaults` assumes the mix, and the owner can rerun `/pstack:setup-pstack` at any time.
   - **`impeccable`.** Skipped when `PRODUCT.md` exists, or when `init.interface` is no user interface. Otherwise invoke the `impeccable` skill with the argument `init` followed by the owner's answers: the purpose paragraph, the user and job, what makes it better, where it is used, the stack and the interface as assumed, and the sentence "the owner gave these answers this session and the stack and platform are assumptions they can overturn; write PRODUCT.md from them, keep the owner's own words, and record no workflow default". Its Setup runs the `impeccable context` launcher from its `scripts/` folder before the init reference; let it, and do not rerun it after `PRODUCT.md` is written. It records the stack under `## Stack`, which adopt reads. A question it still asks is listed in the hand-over.

   Done when each has run, was already done, or the owner declined.

6. **Commit.** `git add -A && git commit -m "chore(method): initialise the repository"`. The pstack rule lives in `~/.claude/rules/`, outside the repository, and is not part of it. Done, and skipped, when `git status --porcelain` prints nothing.

7. **Remote and push.** When the answer to `init.online` asked for a private copy and `git remote get-url origin` fails, run, in a Bash call of its own, `gh repo create <name> --private --source . --remote origin --push` (`glab repo create` for GitLab). This is the one outward-facing action in init; it needs that answer and nothing else, never from the tracker choice alone. Done, and skipped, when `origin` exists. Skipped with "local only" when the question was not asked or the owner kept it on this computer.

8. **Labels.** Only on a rerun where `docs/agents/triage-labels.md` exists (the tracker setup wrote it) and the tracker is GitHub or GitLab with `origin` present: `gh label list` (one Bash call), then for each row of the record whose "Label in our tracker" value is missing, `gh label create <name> --description "<meaning>"` in a Bash call of its own, with exactly one name, no `--force` and no `-R`. That is the one `gh label create` the guard allows: the name is in the record the owner just accepted, on this checkout's own repository. A denial here is a bug: see [Before adopt](#before-adopt). Done, and skipped, when every recorded label is listed. Not applicable for a local tracker.

9. **Hand over.** Report, in this order:
   - Four lines, one per plugin, saying what it now does in this repository; the pstack line says where the rule lives and whether this run wrote it or found it.
   - The commit hash, and the remote URL or "local only" with the reason (no forge login, or the owner kept it on this computer, and so local markdown is the tracker).
   - The label state: created (the count), already present, not applicable (local tracker), not yet (the tracker setup creates them), or refused (the dispute's path).
   - **Assumed.** The block the method's rule on asking describes: one line per assumption this run took (each part of the defaults that applied, the stack, the interface) and per preference the owner typed ("you asked for"), what was chosen and why in a clause, what changing it later costs (what changes, roughly how much work, and whether anything built is redone), and what the owner can say to change it, such as ``Stack: TypeScript with a small server that keeps your list in one file, because the list has to be the same on your phone and your laptop. Changing it before you run `/ratchet:adopt` is one line in the project notes, and nothing built is redone. After that, every check is set up for this stack and Ratchet has no step yet that sets them up for another, so a switch means an agent redoes that setup by hand, tool by tool, in changes whose merge is yours; once features are built, their code is rewritten too. Say "make it simpler" or name another.`` No question key or method term in the block. Then the count of questions the owner answered, and each one a companion plugin's setup still asked.
   - The route, as the last lines. Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/route.py" --root . --offline` in one Bash call and print its lines (`next:`, `why:`, `then:`, and any `also:`) as they are. After a default run they name `/mattpocock-skills:setup-matt-pocock-skills` (it writes the tracker's records and labels, taking the tracker this run chose), then `/ratchet:adopt` (it asks what the first usable part is and what can wait, and chooses the tools itself). Close with the bare command on its own line.

   No pasted commands besides that one. Everything init can do, it has done; what it cannot do is the owner's keystroke, and the route names it.

## Before adopt

`/ratchet:adopt` creates `docs/disputes/`, the binding and ADR 0001; during init none exists. A denial is still the dispute signal: create `docs/disputes/`, write `docs/disputes/0001-<slug>.md` in the format `ratchet:method` gives in its guards page, and report it to whoever started you, which during init is the owner reading your reply. Adopt's template copy skips an existing file, so the record survives adoption.
