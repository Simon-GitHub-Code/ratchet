# Adopt the Ratchet method

Load the `ratchet:method` skill first; this skill assumes its vocabulary. Templates live in `${CLAUDE_SKILL_DIR}/templates/` and mirror the repository layout; the `justfile` and `.github/` among them are the `just` and GitHub examples.

The method ships the questions, its own gates and three gates that work on any service. It ships no tool for any stack. What kind of software the repository is decides which questions apply, and you choose the tool behind each one now, from what is current. [tiers.md](../method/tiers.md) holds the questions, the application types, what a recipe must get right, and what the method asks for speed.

## What the owner is asked

Two dialogs in a default run, one round each, through the question tool. Nothing else asks the owner anything. A question is for a choice that leads to a different product, or that cannot be taken back. A reversible engineering choice is yours: make it, and list it in the hand-over. What a record already says is never asked again. An answer is recorded as given, and one you cannot act on is carried into the hand-over as an open item. `/ratchet:adopt interactive` runs one dialog per topic instead; say the count before the first.

**Dialog 1, what this is and what judges it.** Print the table of step 5, then ask two questions.

1. The application types. Offer the types the tree and the records point to, recommended first, each with its evidence in a clause. This is a product question: the answer decides which questions the method asks of every later change.
2. The tools. Accept the proposed tools, or name the ones you want. An owner with an opinion names a tool for any row, and you bind what they name.

**Dialog 2, the design brief.** Draft the brief from what is already written (`AGENTS.md`'s purpose, `PRODUCT.md`, the README, the code) and ask one round of up to four questions on what no record answers: slice one as checkable items, the explicit out-list, and at most two decisions that would be hard to reverse. A deeper interview is the owner's `/mattpocock-skills:grill-with-docs`, whenever they want one; adoption does not wait for it.

## Steps

1. **Check the ground.** The repository is a git repository with a default branch; `claude plugin list` shows `ratchet`, `mattpocock-skills`, `pstack` and `impeccable`; `python3` (3.11 or later) is installed for the plugin's own gates; `docs/agents/issue-tracker.md` exists, which `/mattpocock-skills:setup-matt-pocock-skills` writes and only the owner can run (stop and name that command when it is missing: the feature route reads the tracker it records). When the only uncommitted files are the records that setup wrote (`docs/agents/**` and its `## Agent skills` section of `AGENTS.md`), commit them as `chore(tracker): record the issue tracker`, so adoption starts on a clean default branch. Done when all hold or you have told the owner which is missing.

2. **Initialise.** Run `/ratchet:init` unless `AGENTS.md` already opens with its four-plugin stanza. Done when `AGENTS.md` exists and `CLAUDE.md` links to it.

3. **Copy the templates.** Work on a branch. Copy every file under `templates/`, dotfiles included, to the same path in the repository, skipping any that exists. Append to `.gitignore` each line of the init skill's `templates/gitignore` it lacks; step 10 adds what this stack's tools write (reports, caches, mutation copies, build output), so no whole-tree gate judges them. Done when the listing of `templates/` and the repository agree and the skipped files are listed for the hand-over.

4. **Recognise the repository.** Read `## Stack` from `PRODUCT.md`, else from `AGENTS.md`, and then the tree: the language, the package manager and its lockfile, the task runner, the forge (`git remote`), what the deliverable is and how it starts. Decide which application types you will recommend, and run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/application_types.py" <type>...`: it prints every question the types narrow, with `applies` or the `none: not a <type>` cell to write. Every other question applies. Done when you can name the stack, the runner, the forge, the types and the rows they leave out.

5. **Choose a tool for every row that applies.** One row of the binding's Gates table at a time, by these rules.

   - **What is there wins.** A tool the tree already configures answers its row. Propose replacing one only with the reason.
   - **Look it up, now.** What you remember of a tool is a conjecture. Check against its current documentation that it exists, is maintained and answers the row: Context7 (`resolve-library-id`, then `query-docs`) or a web search, where the session has them. Say in the table which rows you could not check. Versions come from the package registry when you install, through the package manager's own add command, which writes the lockfile. They never come from memory, and never from this plugin.
   - **Prefer** one tool that answers several rows; a tool the stack's package manager locks; a tool that fails when it finds nothing to run; a tool that uses every core and can run one shard of several.
   - **`none` is rare.** For a row that applies, `none` is for a property the project will never have (no persisted data by design, no container to scan), and it carries the reason and an ADR you write. A row whose tool needs code that does not exist yet is bound now, against the walking skeleton of step 10: a row waits for nothing, because a row left for "the first route" is a guard edit the first feature cannot make with the owner away.
   - **Already bound.** The method's own gates, and for a service `smoke`, `load-smoke` and `telemetry-e2e`, arrive bound to the plugin's scripts. Keep them unless the owner names something else.

   Then print one table: each row that applies with its tier, the tool you propose and where you checked it; the rows the types leave out, on one line; and under the table what you will assume without asking, each with its reason: the layers and their direction, the non-negotiables with the gate that enforces each, the telemetry and flag seams, and who may turn a flag on in production (the owner, unless a record says otherwise). Done when every row that applies has a tool or a reasoned `none`.

6. **Ask dialog 1**, then act on the answers with no further question. Other types than you recommended: rerun step 4's command and choose tools for the rows that now apply. A named tool: bind it; if it cannot answer its row, bind your proposal and carry the difference into the hand-over. Done when the types and every tool are settled.

7. **Runner and forge.** Fill the binding's Runner and Forge sections from step 4. With `just` and GitHub the templates already fit. Another runner, another forge, or no forge at all (no `origin`): do what [runners-and-forges.md](runners-and-forges.md) says before you go on. Done when every entry point names a command and the Forge section has no placeholder.

8. **Write the binding and `AGENTS.md`.** In `docs/process/binding.md`: the `- Application types:` line; for every row that applies, the tool, the threshold source and the entry point; for every row the types leave out, the `none: not a <type>` cell from step 4. A row is never deleted. Write the ADR for the tools now, under the next free number: the tools chosen, and the reason for each `none` on a row that applies; those cells cite its number, and the conformance gate checks the ADR is there. Fill Absolute paths, Limits (size and complexity, change size, performance, and the load numbers: the arrival rate, percentile latency and error rate of `load`, the concurrency and seconds of `load-smoke`), Telemetry (the one module that starts the SDK and registers every entry point, the attributes a span carries and the ones it never does), Feature flags (the one module a flag is read through, the override it honours, who may turn one on) and Tool versions. In `AGENTS.md`, from step 5's assumptions: the declared paths or layers with their allowed direction, the non-negotiables with the ADR that holds each and the gate that enforces it, the stack rules the method leaves open; delete the Layers section when the project declares none. Done when no Tool cell is empty and neither file holds an angle-bracket placeholder outside the Speed section, which step 11 fills.

   Two placements the gates depend on. A snapshot of the product's own contract (a command's `--help`, a public API report, a schema) changes with the feature that changes the contract, so it lives beside the tests, never under `quality/`: `quality/**` is a guard path for what only rises, and a contract snapshot there can be landed neither ahead of its feature nor with it. And when the `prose` gate flags a word on a glossary *Avoid* list in the owner's own text, reword the text; never shorten an *Avoid* list to turn a gate green.

9. **Fill the manifest, then generate the permission rules.** Add the paths of this stack's tool configs (the dependency manifest and its lockfile among them), fitness tests and gate tools to `guards/manifest.toml`, so no group is left with an empty `paths`; a path may be listed before its file exists. Then run `just settings`, which rewrites the `deny` and `ask` lists of `.claude/settings.json` from the finished manifest and keeps every other key; never edit those two lists by hand. Done when `just settings-check` is green. The guard reads the manifest as committed on the default branch, so none of this provokes a prompt until the adoption merges.

10. **Build the walking skeleton and bind the entry points, tier 0 first.** Install each tool through the package manager, add what the tools write to `.gitignore`, then replace each `bind:` body in the `justfile` with the real command. A row bound `none` becomes `@echo "none: <reason>"`, in the binding's words.

    **The walking skeleton.** On a repository with no code yet, write the thinnest deliverable every gate can run against, so that the first feature changes no gate: the package with its `core` path; one health entry point registered through the telemetry seam, and the telemetry test that reads its span from an in-memory exporter; the flag seam with its override and the empty `flags.toml`; one end-to-end test; the contract snapshot beside the tests when the stack publishes a contract; the container file when the deliverable is an image; and one of each thing a gate is red without: a test, a benchmark, a fuzz target, a documentation example, and where the types ask for them a load scenario and an accessibility check. A repository with code binds the same rows against what exists.

    **The deliverable as a running thing.** For a service, fill `boot`, `ready` and `service` at the top of the `justfile`: `smoke`, `load-smoke` and `telemetry-e2e` then need nothing else, beyond a `--url` per route worth overlapping. The boot command builds what it runs and stays in the foreground, since CI gives each gate a job of its own; raise `boot_timeout` when the build is slow, and write `{port}` wherever the port goes. Any other type sets the three to `none`, binds `smoke` to one real run of its deliverable where that row applies, and gives the recipes its types leave out their `none` body.

    **A gate with nothing to run is red.** No test, no benchmark, no fuzz target, no scenario: the recipe fails, on every stack, and says what is missing. Check each tool's exit code on an empty collection before you trust it, and make the recipe fail where the tool would pass. The other rules a recipe must keep are in [tiers.md](../method/tiers.md#what-a-recipe-must-get-right); read them before you write the first recipe.

    Run `just snapshots` once the tool configs exist, so `snapshots-check` has something to compare. Every bound entry point runs green on the skeleton before you move to the next: tier 0, then tier 1, then tier 2. A tier 2 recipe that is red on the skeleton is a defect of the binding, fixed now, never left for the first feature. Then run `just ratchet` once and commit what it writes: the first thresholds and the public-surface report. It is red, by design, while a commit here would not run tier 0: deal with the command it prints as step 15 says, and where that command is the owner's, the thresholds stay at the values you wrote until their first `just ratchet`. Done when `tier0`, `tier1` and `tier2` are green and no `bind:` body is left.

11. **Speed.** Build it in now, while nothing is slow ([tiers.md](../method/tiers.md#speed)). Turn the test runner's parallel mode on in the committed configuration, so every core is used locally and in CI without a flag anyone must remember. Have each long gate's recipe hand `{{shard}}` and `{{shards}}` to its tool; a local run is shard 1 of 1. Keep the CI templates' shape when you bind them: one job per gate, the long gates over the shard count, superseded runs cancelled; fill each `bind:` cache line with this stack's dependency directory and tool caches, keyed on its lockfiles and tool configs. Fill the binding's Speed section, one line per concept, saying how this stack meets it; leave `- Shards: 1`. Run `just budget tier0 --set` and `just budget tier1 --set` once on the skeleton: they record the first ceilings with headroom, never under the tier's budget, and the ceilings only fall from here. Done when the Speed section has no placeholder, the suite runs in parallel, and `[ceilings.seconds]` has a key per tier.

12. **Records.** Ask dialog 2 and write the design brief from its answers (purpose, shape, slice one as checkable items, the explicit out-list); facts you can look up are never questions, and `mattpocock-skills:grilling` runs its rounds only in `interactive` mode. Then run `mattpocock-skills:domain-modeling` to write the ADRs and glossary entries the answers crystallised, and record the agreed brief in `docs/design-brief.md`, dated. Replace `<project>` in `GLOSSARY.md` with the project's name. When the tree already has user-interface surfaces, run `/impeccable document` so `DESIGN.md` records the incumbent design system; when it has none yet, do not create `DESIGN.md`: write under slice one in the design brief that the first surface's pull request runs `/impeccable shape` and then `/impeccable document`. Fill ADR 0001 with the plugin version from `$CLAUDE_PLUGIN_ROOT/.claude-plugin/plugin.json` and the commit it was installed from: `git -C "$CLAUDE_PLUGIN_ROOT" rev-parse HEAD` when the plugin directory is a checkout, else the latest commit of `Simon-GitHub-Code/ratchet` that changed `.claude-plugin/plugin.json` (`gh api 'repos/Simon-GitHub-Code/ratchet/commits?path=.claude-plugin/plugin.json&per_page=1' --jq '.[0].sha'`); say in the hand-over which of the two you used. Done when the brief is dated, the glossary names the project and ADR 0001 names the version and the commit.

13. **CI.** Put the commit ADR 0001 names into every `ref: "<ratchet-sha>"` of `ci.yml` and `deep.yml`, so CI runs the plugin's gates at the version this repository adopted; `RATCHET_PLUGIN` already points the recipes at that checkout. Add the toolchain setup, pinned, with its own cache on. The template's actions are pinned and `just pins` is green on it; keep it so for every step you add: a commit SHA with the version in a trailing comment, images by digest. Done when the workflows parse and name no placeholder.

14. **Prove it.** Run `conformance` and fix each failure it names. Run `check`, then `check-deep`. Adoption ends with every bound gate shown to bite: the `bite` entry point plants a fault for each gate the binding names, the empty collection among them, and is green only when each gate went red on its fault. Done when `conformance`, `check-deep` and `bite` exit 0.

15. **Hand over.** Commit on the branch as `chore(method): adopt the ratchet method` (the `commits` gate accepts it, and the change-size gate exempts a range made only of such commits and prints the size instead), push, and open a pull request (with no forge, the change description at `.scratch/changes/<branch>.md`) with every template section filled, the `tier0` tail under Gates, and under Criticism, as standing criticisms of the binding: every `none` row that applies, every tool you could not check against its documentation, every assumption of step 5, every answer you could not act on, and the adoption's measured size, which is the counter to the change-size gate for this one change. The tier 0 commit hooks: run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/hooks_installed.py"` in one Bash call. It is green only when a commit here would run tier 0, and red with the one command that makes it so. Run that command yourself when it is a plain `pre-commit install` or `uvx pre-commit install`, which the guard allows, then run the gate again. Any other command (it unsets or sets aside a `core.hooksPath`, which the guard refuses from an agent as a hook-path change) is the owner's: name it in the hand-over and under Criticism, do not run it, and say that `just ratchet`, the route and the feature preflight stay red until the owner has. Merging is the owner's too. Say also that the guard's path rules switch on when this pull request merges, since the hook reads the manifest from the default branch.

    Then the route, as the last lines: run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/route.py" --root .` in one Bash call and print its three lines as they are. On the adoption branch they say to wait for the merge; say also what follows it, from [route.md](../method/route.md): `/mattpocock-skills:grill-with-docs` when the design brief or glossary is still thin, else `/mattpocock-skills:to-spec` and `to-tickets` for the first feature, `/ratchet:conjecture` on its ticket, then `/ratchet:feature` or `/pstack:poteto-mode`. Close with `/ratchet:next` on its own line, which prints the step whenever the owner asks.
