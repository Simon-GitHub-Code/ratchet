# Adopt the Ratchet method

Load the `ratchet:method` skill first; this skill assumes its vocabulary. Templates live in `${CLAUDE_SKILL_DIR}/templates/` and mirror the repository layout; the `justfile` and `.github/` among them are the `just` and GitHub examples, and each template's comments say what its placeholders need.

The method ships the questions, its own gates and three gates for any service, and no tool for any stack: the application types decide which questions apply, and you choose the tool behind each one now, from what is current. A question is asked once its trigger fires (ADR 0028). Adoption binds the floor (`always`) and the rows whose trigger has already fired in this tree, and writes every other row `later: <trigger>`; `/ratchet:safeguard` binds each one when the route says it is owed. No skeleton is built: on an empty repository the next thing written is the owner's idea. [tiers.md](../method/tiers.md) holds the questions, the types, the triggers, what a recipe must get right, and speed.

## What the owner is asked

Two dialogs, one round each, through the question tool, and nothing else. A question is for a choice that leads to a different product or cannot be taken back; a reversible choice is yours to make and list in the hand-over. What a record says is never asked. An answer you cannot act on goes into the hand-over. A question whose key `## Standing answers` in `AGENTS.md` lists is not asked, and its answer there is taken. Record each answer in one Bash call: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/questions.py" record --skill adopt --key <key> --kind <kind> --recommended <yes|no> --root .`. The keys are `adopt.types` (`direction`), `adopt.events` (`direction`), `adopt.tools` (`tooling`) and `adopt.brief.<n>` (`direction`, or `irreversible` for a decision hard to reverse).

`/ratchet:adopt interactive` asks four dialogs instead, one per topic: the application types and life events, the tools, the assumptions printed under step 5's table, and the design brief, followed by the rounds of `mattpocock-skills:grilling`. Say the count before the first.

**Dialog 1, what this is and what judges it.** Print the table of step 5, then ask three questions. First, the application types: offer the types the tree and the records point to, recommended first, each with its evidence in a clause; the answer decides which questions the method asks of every later change. Second, the life events: which of `deployed`, `irreplaceable-data` and `depended-on` already hold, each with its meaning from `application-types.toml`; the recommended answer is `none` for a new project, and an event the tree shows a sign of is offered with that sign. Third, the tools: accept the proposal, or name the ones you want for any row.

**Dialog 2, the design brief.** Draft the brief from the records and the code, and ask up to four questions no record answers: slice one as checkable items, the out-list, and at most two decisions hard to reverse. A deeper interview is the owner's `/mattpocock-skills:grill-with-docs`; adoption does not wait for it.

## What it costs

Adoption installs the tools of the rows it binds, runs those gates, plants each one's fault in a scratch copy, and runs `check-deep` once, in step 12. On an empty repository that is the floor alone: minutes. A repository with code also binds what its code already holds. Tell the owner before step 1; it is not a question.

## Steps

1. **Check the ground.** Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/route.py" --root . --offline` in one Bash call. When it names `/ratchet:init` or `/mattpocock-skills:setup-matt-pocock-skills`, print its lines and stop: both are the owner's keystrokes, and adoption needs what they write. Then check that later steps can run: `git` 2.36 or later; `python3` 3.11 or later; `just`, or the runner the repository uses; the `pre-commit` framework (`pre-commit` or `uvx pre-commit`); with an `origin` on GitHub, `gh` with `gh auth status` green; and `claude plugin list` showing `ratchet`, `mattpocock-skills`, `pstack` and `impeccable`. Commit the tracker setup's uncommitted records, if any, on the default branch as `chore(tracker): record the issue tracker`. Done when all hold, or you have named what is missing and stopped.

2. **Copy the templates.** On a new branch, every commit's subject starts `chore(method): adopt`: the `commits` gate accepts it, and the change-size gate exempts a range made only of such commits and prints the size instead. Copy every file under `templates/`, dotfiles included, to the same path, skipping any that exists and skipping `.claude/settings.json` (its `deny` rules lock `guards/**`, and Claude Code applies them the moment the file exists, before step 8 has filled the manifest; step 8 writes it), and append to `.gitignore` the lines of the init skill's `templates/gitignore` it lacks. Done when both listings agree and the skipped files are noted for the hand-over.

3. **Recognise the repository.** Read `## Stack` from `PRODUCT.md`, else from `AGENTS.md`, then the tree: the language, the package manager and its lockfile, the task runner, the forge (`git remote`), what the deliverable is and how it starts. Choose the types to recommend and run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/application_types.py" <type>...`: it prints each question the types narrow, with `applies` or the `none: not a <type>` cell to write; every other question applies. Done when you can name the stack, runner, forge, types and the rows they leave out.

4. **Find what has arrived.** In `docs/process/binding.md` write the `- Application types:` line, `- Life events: none` until dialog 1 answers, and in the Gates table every row whose question's trigger in `application-types.toml` is not `always` as `later: <trigger>`, copied exactly, or `none: not a <type>` where step 3 printed that. Fill `## Triggers`: one row per kind of code the declared types are asked about (the `conformance` entry point names each kind missing), with this stack's Paths and a Pattern where a path is not enough, or `none: <reason>` for a kind this project will never have. `flag` is `flags.toml` with the pattern of a flag's table, and `layer` is the layers section of `AGENTS.md`. Prove each row with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/triggers.py" --count`: it prints what each row finds. A row that finds nothing in a tree that has the kind is wrong; for a kind with no instance yet, write one line of it in a scratch file the Paths match, see it counted, and delete it. Then `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/triggers.py" --json` lists the rows owed now: those, with the floor, are the rows this adoption binds. Done when every kind asked has a row, each count is what the tree holds, and you know the rows to bind.

5. **Choose a tool for every row bound now.** The floor and the owed rows of step 4, one at a time; a `later:` row gets no tool until its trigger fires.

   - **What is there wins**, unless you give the reason to replace it.
   - **Look it up, now.** What you remember of a tool is a conjecture. Check its current documentation (Context7 or a web search) that it exists, is maintained and answers the row; say which rows you could not check. Versions come from the registry through the package manager's add command, never from memory, and never from this plugin.
   - **Prefer** one tool for several rows; a tool the package manager locks; a tool that fails when it finds nothing to run; a tool that uses every core and can run one shard of several.
   - **`none` is rare.** For a row that applies, `none` is for a property the project will never have, with the reason and an ADR you write. A row whose code does not exist yet is `later:`, never `none`.
   - **Already bound.** The method's own gates arrive bound to the plugin's scripts. For a service, `smoke`, `load-smoke` and `telemetry-e2e` do too, once their triggers have fired.

   Print one table: each row bound now with its tier, the tool and where you checked it; the `later:` rows on one line per trigger; the rows left out, on one line; and under it what you assume without asking, with reasons: the layers and their direction, the non-negotiables and their gates, and, where their rows are bound now, the telemetry and flag seams and who may turn a flag on in production (the owner, unless a record says otherwise). Done when every row bound now has a tool or a reasoned `none`.

6. **Ask dialog 1**, then act on the answers with no further question. Other types: rerun step 3's command and step 4's count. A declared life event: write it on `- Life events:` and bind its owed rows with the rest. A named tool that cannot answer its row: bind your proposal and carry the difference into the hand-over. Done when the types, the life events and the tools are settled.

7. **Write the binding and `AGENTS.md`.** Fill the binding's Runner and Forge sections, the default branch included; another runner, another forge, or no `origin`: do what [runners-and-forges.md](runners-and-forges.md) says first. In the Gates table: every row bound now with its tool, threshold source and entry point; the rest stay `later:` or `none: not a <type>`, and a row is never deleted. Write the ADR for the tools under the next free number, with the reason for each `none` on a row that applies, which those cells cite. Fill every other section but Speed, which step 10 fills; a section that describes only `later:` rows (Telemetry, Feature flags) says so in one line. In `AGENTS.md`, from step 5's assumptions: the layers with their allowed direction (or delete the section), the non-negotiables with the ADR and the gate behind each, the stack rules the method leaves open. Done when every entry point names a command, no Tool cell is empty, and neither file holds an angle-bracket placeholder outside Speed.

8. **Fill the manifest, then generate the permission rules.** Add this stack's tool configs (the dependency manifest and its lockfile among them), fitness tests and gate tools to `guards/manifest.toml`, so no group has an empty `paths`; a path may be listed before its file exists. Bind the three `[[door]]` tables, the one-way doors the merge judge sends to the owner; a door with no path here keeps `paths = []` and says why in `none = "<reason>"`. Run `just settings`, which creates `.claude/settings.json` and writes its `deny` and `ask` lists from the manifest, last, so the permission rules switch on only once every guard file is in place; never edit them by hand. Two things stay apart: the guard hook reads its path rules from the manifest on the default branch, so they start with the adoption's merge, while the permission rules come from the work tree's `.claude/settings.json` and start the moment `just settings` writes it. Done when `just settings-check` is green.

9. **Bind the entry points, tier 0 first, and show each one bites.** Install each tool through the package manager, add what the tools write to `.gitignore`, and replace each `bind:` body in the `justfile`: a bound row with the real command, a `later:` row with `@echo "later: <trigger>"`, the same words as its Tool cell, and a row bound `none` with `@echo "none: <reason>"`. Both exit 0. Read [what a recipe must get right](../method/tiers.md#what-a-recipe-must-get-right) before the first recipe.

    For a service whose `entry-point` has arrived, fill `boot`, `ready`, `service` and `flags_on` at the top of the `justfile`: `smoke`, `load-smoke` and `telemetry-e2e` then need only a `--url` per route worth overlapping. The boot command builds what it runs and stays in the foreground; raise `boot_timeout` when the build is slow, and write `{port}` where the port goes. A gate that requests routes from outside boots through `{{probed}}`, every flag due for removal on; `smoke` and the end-to-end suite judge the defaults. The other types bind those rows as the table says, a `none` with the cell step 3 printed; `telemetry_sink.py` wraps any command after `--`. Set the four to `"none"` where no bound row uses them; `/ratchet:safeguard` fills them when the first entry point arrives.

    | Type | `smoke` | `load-smoke`, `load` | `telemetry-e2e` |
    | --- | --- | --- | --- |
    | `web-ui` | `boot` serves the built bundle, `ready` is its first page; then as a service | `none` | one page's end-to-end run, the browser exporting over OTLP/HTTP |
    | `app` | the built app starts headless, reaches its first screen and exits 0 | `none` | one end-to-end run of the app |
    | `job` | one run on a small fixture input: exit 0 and the expected output | a burst of inputs (messages, files, rows): errors only, then the Limits' rate and latency | one run of the job |
    | `cli` | `--version` and one real command, each exit 0 with the expected output | `none` | `none` |
    | `library` | `none` | `none` | `none` |

    **A gate with nothing to run is red.** No test, benchmark, fuzz target or scenario: the recipe fails and says what is missing, even where the tool's own exit code would pass. A row is bound only once its trigger has fired, so what it judges already has a member.

    **A bite for every gate you bind.** With each recipe, add its `[[bite]]` to `quality/bites.toml` as its header says: the smallest fault the gate exists to catch, and the words it prints for it; a collection gate gets a second bite that removes the collection. A row whose question requires a proof by name (`[proofs]` in `application-types.toml`: telemetry emitted, changed flags off and on, load smoke) gets a bite that plants that fault and claims it with `proof = "<name>"`. A shipped service gate bound now needs one, since its row names your `boot`: `smoke` a deliverable that exits, `load-smoke` a route that answers with an error, `telemetry-e2e` a deliverable that exports nothing. A `later:` row needs none. `just bite-one <gate>` proves one gate in a scratch copy; a whole-tree gate's bite narrows it with `args`, and the registry's `setup` holds the build. A verdict other than `bites` is a defect of the recipe or the fault ([tiers.md](../method/tiers.md#every-bound-gate-is-shown-to-bite)): fix it, never loosen `expect`. A gate you cannot plant a fault for is bound `none`, with its reason and ADR.

    **In order.** Run `just snapshots` once the tool configs exist. Bind tier 0 until `just tier0` is green. Then install the commit hooks: run `just hooks-install` in one Bash call. It prints `hooks: green` once a commit here runs tier 0. An `owner:` line instead names a change of git config, which the guard refuses from an agent: give the owner that one command now, not at the hand-over, and go on. Then bind tier 1 until `just tier1` is green, each gate over the change through `{{changed}}`, which judges nothing on the adoption, and each tier 2 gate bound now until it is green alone. Run `just ratchet`, with its `bind:` line replaced by the suites and mutation run that are bound, or removed while none is, and commit the first thresholds it writes; while the hooks wait for the owner it is red, and the thresholds stay as you wrote them. Done when tier 0 and tier 1 are green, every tier 2 gate is green alone, and no `bind:` body is left.

10. **Speed.** Build it in while nothing is slow ([tiers.md](../method/tiers.md#speed)). Turn the parallel mode of the test runner and of the mutation tool on in the committed configuration, where they are bound. Have each long gate hand `{{shard}}` and `{{shards}}` to its tool. Add a gate to its tier's list at the top of the `justfile` and nowhere else: CI reads the same lists. Run `tier0-tree` and `tier1` three times each; a gate red in parallel and green alone shares state, which tiers.md says how to separate. Fill each `bind:` cache line of the CI templates with this stack's caches, keyed on its lockfiles and tool configs, and keep their shape. Fill the binding's Speed section, one line per concept, saying how this stack will meet it where nothing is bound yet; leave `- Shards: 1`. Run `just budget tier0 --set` and `just budget tier1 --set` once. Take those readings on a quiet machine or the CI runner, and vet each with `pstack:benchmark-checklist`; on a shared machine cap the gates with `RATCHET_JOBS`. Done when the Speed section has no placeholder, three runs of each are green, and `[ceilings.seconds]` has a key per tier.

11. **Records and CI.** Ask dialog 2 and write `docs/design-brief.md` from its answers, dated (`mattpocock-skills:grilling` runs only in `interactive` mode). Run `mattpocock-skills:domain-modeling` for the ADRs and glossary entries the answers crystallised, and replace `<project>` in `GLOSSARY.md`. When the tree has user-interface surfaces, run `impeccable document` for `DESIGN.md`. When it has none, do not create `DESIGN.md`: write under slice one that the first surface is built with `impeccable shape`, and that an agent runs `impeccable document` once it merges.

    Write the plugin's version (from `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`) and its commit (`git -C "${CLAUDE_PLUGIN_ROOT}" rev-parse HEAD` when that is a checkout, else the latest commit of `Simon-GitHub-Code/ratchet` that changed that file) into the binding's `- Ratchet plugin:` line, and the same commit into every `ref: "<ratchet-sha>"` of `ci.yml`, `deep.yml`, `weekly.yml` and `merge.yml`, so CI and every local tier run the plugin's gates at one version, which `just plugin-pin` and the conformance gate hold. Add the toolchain setup, pinned by commit SHA with the version in a trailing comment, so `just pins` stays green, and set the nightly hour in `deep.yml`. Done when the brief is dated, the glossary names the project, the binding names the plugin's version and commit, and the workflows name no placeholder.

12. **Prove it.** Commit first: the change-size gate knows the adoption by its subjects, and in a bite the change is what the tree holds beyond `HEAD`. Run `conformance` and fix what it names. Run `check`, then `check-deep`, once. Its last gate is the proof: the `bite-all` entry point plants each fault of `quality/bites.toml` in a scratch copy and is green only when each gate was green without its fault and red with it. Done when `conformance` and `check-deep` exit 0.

13. **Hand over.** Commit what the proof changed, push and open a pull request (with no forge, the change description at `.scratch/changes/<branch>.md`) with every template section filled and the `tier0` tail under Gates. Under Criticism: every `none` row that applies, every tool you could not check, every assumption of step 5, every answer you could not act on, the adoption's measured size, and the owner's hooks command, if any, which `just ratchet`, the route and the feature preflight wait for. Say in one line which rows wait for which trigger, and that the route names `/ratchet:safeguard` when one fires. The adoption changes guard paths, so its merge is the owner's; the path rules switch on with it, and from then on the `merge` workflow (with no forge, `just merge <branch>`) merges what the judge passes.

    The last lines are the route: run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/route.py" --root .` in one Bash call and print its lines as they are. Close with `/ratchet:next` on its own line.
