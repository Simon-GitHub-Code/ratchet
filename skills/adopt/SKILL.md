# Adopt the Ratchet method

Load the `ratchet:method` skill first; this skill assumes its vocabulary. Templates live in `${CLAUDE_SKILL_DIR}/templates/` and mirror the repository layout; the `justfile` and `.github/` among them are the `just` and GitHub examples, and each template's comments say what its placeholders need. Read nothing else of the plugin: the templates' comments, the output of the scripts this skill runs and the pages it links hold every rule you need, and a red gate's line names its repair.

The method ships the questions, its own gates and three gates for any service, and no tool for any stack: the application types decide which questions apply, and you choose the tool behind each one now, from what is current. A question is asked once its trigger fires (ADR 0028). Adoption binds the floor (`always`) and the rows whose trigger has already fired in this tree, and writes every other row `later: <trigger>`; `/ratchet:safeguard` binds each one when the route says it is owed. No skeleton is built: on an empty repository the next thing written is the owner's idea. What that idea will need is ready, though (ADR 0032): the test runner, every config the stack rules promise, how the product starts, and the change-size ceiling, so the first feature, built unattended, changes no guard path but the dependencies it adds. Step 12 rehearses the first slice to show it. [tiers.md](../method/tiers.md) holds the questions, the types, the triggers, what a recipe must get right, and speed.

## What the owner is asked

The owner is asked about the product and nothing else (ADR 0034), and only at step 3, so that every question comes in the first minutes and the rest of adoption runs while they are away. One at a time, each in the words written here, with your reading of the records as the recommended option:

1. **Ask** `adopt.first`: "What is the first thing you want to be able to do with it, from start to finish?" The options are the first usable part the records point to, as a few things a person can check, in the owner's words.
2. **Ask** `adopt.later`: "Which of these can wait until that first part works?" The options are what the records name beyond that part; several may be chosen.
3. **Ask** `adopt.hard-to-undo`: "<a choice about what happens to someone's things that would be hard to undo later, asked as someone using it would put it>" At most two, only where the first part meets such a choice and nothing the owner said settles it, such as "When you mark an item read, should it stay in your list as read, or be deleted?". `/ratchet:conjecture` asks the rest before anything is built.

Whether others reach it, rely on it, or trust it with what cannot be got back is something a machine cannot see reliably (ADR 0028), so the owner declares it. On a repository that already has code, always ask the first, naming any sign the tree shows (a deploy configuration or workflow, a production address, a host's configuration); recommend "no" only when the tree shows none:

- **Ask** `event.deployed`: "Is it now running somewhere that people other than you can reach?"

Ask the other two when the tree shows a sign of them (data the tree says is kept, users outside the project) or the owner answered yes to the first:

- **Ask** `event.irreplaceable-data`: "Does it now hold anything that could not be got back if it were lost?"
- **Ask** `event.depended-on`: "Do people other than you now rely on it?"

On an empty repository none of the three is asked. So a repository with code is asked at most seven questions here, an empty one at most four.

A choice the owner's words already make is not asked. A deeper interview is the owner's `/mattpocock-skills:grill-with-docs`; adoption does not wait for it.

**What the owner asked for wins.** Anything typed after the command (`/ratchet:adopt use ESLint, no GitHub`) is a preference: it settles the choice it names, it wins over the defaults below unless it cannot answer a row (then say why, and take the default), and a question it answers is not asked. Each one is listed under **Assumed** as "you asked for".

**Everything else is assumed.** Act on each with no question and list it at the end of the hand-over under **Assumed**, in plain words, with what changing it later costs and what the owner can say to change it:

- **Assume** `adopt.types`: the application types the records and the tree point to (`## Stack`, the code, how it starts), each with its evidence, said as "a web page served by a small server of its own" rather than by type name.
- **Assume** `adopt.events`: on an empty repository, no life event, said as "nobody but you reaches it yet"; on one with code, each event the owner answered yes to. The route asks again when a sign appears.
- **Assume** `adopt.tools`: the tools step 5 chooses, each looked up now, with the one you passed over.

## What it costs

Adoption installs the tools of the rows it binds and the test runner, runs those gates, plants each one's fault in a scratch copy, rehearses the first slice in another, and runs `check-deep` once, in step 12. On an empty repository the only rows it binds are those whose trigger is `always`: with the test runner and the rehearsal, about 25 minutes on an idle machine, an estimate. A repository with code also binds the rows its code has already triggered. Tell the owner before step 1; it is not a question.

## Steps

1. **Check the ground.** Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/route.py" --root . --offline` in one Bash call. When it names `/ratchet:init` or `/mattpocock-skills:setup-matt-pocock-skills`, print its lines and stop: both are the owner's keystrokes, and adoption needs what they write. Then check that later steps can run: `git` 2.36 or later; `python3` 3.11 or later; `just`, or the runner the repository uses; the `pre-commit` framework (`pre-commit` or `uvx pre-commit`); with an `origin` on GitHub, `gh` with `gh auth status` green; and `claude plugin list` showing `ratchet`, `mattpocock-skills`, `pstack` and `impeccable`. Commit the tracker setup's uncommitted records, if any, on the default branch as `chore(tracker): record the issue tracker`. Done when all hold, or you have named what is missing and stopped.

2. **Copy the templates.** On a new branch, every commit's subject starts `chore(method): adopt`: the `commits` gate accepts it, and the change-size gate exempts a range made only of such commits and prints the size instead. Copy every file under `templates/`, dotfiles included, to the same path, skipping any that exists and skipping `.claude/settings.json` (its `deny` rules lock `guards/**`, and Claude Code applies them the moment the file exists, before step 8 has filled the manifest; step 8 writes it), and append to `.gitignore` the lines of the init skill's `templates/gitignore` it lacks. Done when both listings agree and the skipped files are noted for the hand-over.

3. **Recognise the repository.** Read `## Stack` from `PRODUCT.md`, else from `AGENTS.md`, then the tree: the language, the package manager and its lockfile, the task runner, the forge (`git remote`), what the deliverable is and how it starts. Choose the types to recommend and run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/application_types.py" <type>...`: it prints each question the types narrow, with `applies` or the `none: not a <type>` cell to write; every other question applies. Then draft the design brief from the records and ask the questions of [What the owner is asked](#what-the-owner-is-asked); nothing after this step asks the owner anything. Done when you can name the stack, runner, forge, types and the rows they leave out, and each question is answered.

4. **Find what has arrived.** In `docs/process/binding.md` write the `- Application types:` line, `- Life events:` as `adopt.events` settles it, and in the Gates table every row whose question's trigger in `application-types.toml` is not `always` as `later: <trigger>`, copied exactly, or `none: not a <type>` where step 3 printed that. Fill `## Triggers`: one row per kind of code the declared types are asked about (the `conformance` entry point names each kind missing), with this stack's Paths and a Pattern where a path is not enough, or `none: <reason>` for a kind this project will never have. `flag` is `flags.toml` with the pattern of a flag's table, and `layer` is the layers section of `AGENTS.md`. Prove each row with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/triggers.py" --count`: it prints what each row finds. A row that finds nothing in a tree that has the kind is wrong; for a kind with no instance yet, write one line of it in a scratch file the Paths match, see it counted, and delete it. Then `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/triggers.py" --json` lists the rows owed now: those, with the floor, are the rows this adoption binds. Done when every kind asked has a row, each count is what the tree holds, and you know the rows to bind.

5. **Choose a tool for every row bound now, and for the tests.** The floor, the owed rows of step 4 and the tests, one at a time; any other `later:` row gets no tool until its trigger fires.

   - **The tests are provisioned, not asked.** The first feature writes its tests before any module exists, so every repository gets its test runner now, and a property-testing library where the runner has none, while their row stays `later: code:source`. Step 7 names them in the binding's Tests section and step 9 sets `test_runner` in the `justfile`; `/ratchet:safeguard` later binds the row to them and installs nothing.
   - **What is there wins**, unless you give the reason to replace it.
   - **Look it up, now.** What you remember of a tool is a conjecture. Check its current documentation (Context7 or a web search) that it exists, is maintained and answers the row; say which rows you could not check. Versions come from the registry through the package manager's add command, never from memory, and never from this plugin.
   - **Prefer** one tool for several rows; a tool the package manager locks; a tool that fails when it finds nothing to run; a tool that uses every core and can run one shard of several.
   - **`none` is rare.** For a row that applies, `none` is for a property the project will never have, with the reason and an ADR you write. A row whose code does not exist yet is `later:`, never `none`.
   - **Already bound.** The method's own gates arrive bound to the plugin's scripts. For a service, `smoke`, `load-smoke` and `telemetry-e2e` do too, once their triggers have fired.

   Write one table, for the pull request and the hand-over: each row bound now with its tier, the tool and where you checked it; the test runner and property-testing library on a line marked `provisioned`; the `later:` rows on one line per trigger; the rows left out, on one line; and under it what you assume without asking, with reasons: the layers and their direction, the non-negotiables and their gates, and, where their rows are bound now, the telemetry and flag seams and who may turn a flag on in production (the owner, unless a record says otherwise). Done when every row bound now has a tool or a reasoned `none`.

6. **Settle what is assumed.** A life event the owner answered yes to: write it on `- Life events:` and bind its owed rows with the rest. Done when the types, the life events and the tools are settled.

7. **Write the binding and `AGENTS.md`.** Fill the binding's Runner and Forge sections, the default branch included; another runner, another forge, or no `origin`: do what [runners-and-forges.md](runners-and-forges.md) says first. In the Gates table: every row bound now with its tool, threshold source and entry point; the rest stay `later:` or `none: not a <type>`, and a row is never deleted. Write the ADR for the tools under the next free number, with the reason for each `none` on a row that applies, which those cells cite. Fill every other section but Speed, which step 10 fills; a section that describes only `later:` rows (Telemetry, Feature flags) says so in one line. In `AGENTS.md`, from step 5's assumptions: the layers with their allowed direction (or delete the section), the non-negotiables with the ADR and the gate behind each, the stack rules the method leaves open. A stack rule describes the tree as adoption leaves it. Every config it names (an exemption for the one module allowed something, a directory a tool includes, a compiler key a declared type needs) is written now, and no rule leaves a config to "the change that brings" something: that change is the unattended pipeline's, and a config is a guard path it cannot edit. Name the file `boot` runs and, where settings are read, the one module that reads them. Done when every entry point names a command, no Tool cell is empty, and neither file holds an angle-bracket placeholder outside Speed.

8. **Fill the manifest, then generate the permission rules.** Add this stack's tool configs (the dependency manifest and its lockfile among them), fitness tests and gate tools to `guards/manifest.toml`, so no group has an empty `paths`; a path may be listed before its file exists. Bind the three `[[door]]` tables, the one-way doors the merge judge sends to the owner; a door with no path here keeps `paths = []` and says why in `none = "<reason>"`. Run `just settings`, which creates `.claude/settings.json` and writes its `deny` and `ask` lists from the manifest, last, so the permission rules switch on only once every guard file is in place; never edit them by hand. Two things stay apart: the guard hook reads its path rules from the manifest on the default branch, so they start with the adoption's merge, while the permission rules come from the work tree's `.claude/settings.json` and start the moment `just settings` writes it. Done when `just settings-check` is green.

9. **Bind the entry points, tier 0 first, and show each one bites.** Install each tool through the package manager, the provisioned test tools included, add what the tools write to `.gitignore`, and replace each `bind:` body in the `justfile`: a bound row with the real command, a `later:` row with `@echo "later: <trigger>"`, the same words as its Tool cell, and a row bound `none` with `@echo "none: <reason>"`. Both exit 0. Set `test_runner` to the command that runs the test files named after it; the test runner's configuration includes the test directories and the Critique tests directory. Read [what a recipe must get right](../method/tiers.md#what-a-recipe-must-get-right) before the first recipe.

    **A key a declared type needs is never removed to quiet a gate.** When a gate is red on such a key, or on a provisioned package nothing uses yet, fix the other side: install the runtime package the key names when the stack names it, have the configuration that sets a tool up use it (a setup file the test runner loads), or give the gate its narrowest exception. Step 12's rehearsal must leave the fix green.

    Fill `boot`, `ready` and `service` at the top of the `justfile` for every type that boots, whether or not its code has arrived, as the template's comments say: the command this stack's conventions imply for the file `AGENTS.md` names, and where it answers. The boot command builds what it runs and stays in the foreground; raise `boot_timeout` when the build is slow, and write `{port}` where the port goes (`$PORT` also works in `boot`). On an empty repository that file does not exist yet, and nothing is red for it: every row that boots is `later:`, so only `just start` and step 12's rehearsal run `boot` before the first entry point arrives. `flags_on` stays `"none"` until the flag seam exists. Where an entry point has arrived, bind its rows: for a service, `smoke`, `load-smoke` and `telemetry-e2e` need only a `--url` per route worth overlapping. A gate that requests routes from outside boots through `{{probed}}`, every flag due for removal on; `smoke` and the end-to-end suite judge the defaults. The other types bind those rows as the table says, a `none` with the cell step 3 printed. `{{booted}}` waits for a URL and refuses a `ready` of `"none"`, so a `cli`, `job` or `app` writes its `smoke` as a run of `boot` itself, to its exit; `telemetry_sink.py` wraps any command after `--`.

    | Type | `smoke` | `load-smoke`, `load` | `telemetry-e2e` |
    | --- | --- | --- | --- |
    | `web-ui` | `boot` serves the built bundle, `ready` is its first page; then as a service | `none` | one page's end-to-end run, the browser exporting over OTLP/HTTP |
    | `app` | `boot` starts the built app headless; it reaches its first screen and exits 0 | `none` | one end-to-end run of the app |
    | `job` | `boot` runs once on a small fixture input: exit 0 and the expected output | a burst of inputs (messages, files, rows): errors only, then the Limits' rate and latency | one run of the job |
    | `cli` | `boot` with `--version` and with one real command, each exit 0 with the expected output | `none` | `none` |
    | `library` | `none` | `none` | `none` |

    **A gate with nothing to run is red.** No test, benchmark, fuzz target or scenario: the recipe fails and says what is missing, even where the tool's own exit code would pass. A row is bound only once its trigger has fired, so what it judges already has a member.

    **A bite for every gate you bind.** With each recipe, add its `[[bite]]` to `quality/bites.toml` as its header says: the smallest fault the gate exists to catch, and the words it prints for it; a collection gate gets a second bite that removes the collection. A row whose question requires a proof by name (`[proofs]` in `application-types.toml`: telemetry emitted, changed flags off and on, load smoke) gets a bite that plants that fault and claims it with `proof = "<name>"`. A shipped service gate bound now needs one, since its row names your `boot`: `smoke` a deliverable that exits, `load-smoke` a route that answers with an error, `telemetry-e2e` a deliverable that exports nothing. A `later:` row needs none. `just bite-one <gate>` proves one gate in a scratch copy; a whole-tree gate's bite narrows it with `args`, and the registry's `setup` holds the build. A verdict other than `bites` is a defect of the recipe or the fault ([tiers.md](../method/tiers.md#every-bound-gate-is-shown-to-bite)): fix it, never loosen `expect`. A gate you cannot plant a fault for is bound `none`, with its reason and ADR.

    **In order.** Run `just snapshots` once the tool configs exist. Bind tier 0 until `just tier0` is green. Then install the commit hooks: run `just hooks-install` in one Bash call. It prints `hooks: green` once a commit here runs tier 0. An `owner:` line instead names a change of git config, which the guard refuses from an agent: give the owner that one command now, not at the hand-over, and go on. Then bind tier 1 until `just tier1` is green, each gate over the change through `{{changed}}`, which judges nothing on the adoption, and each tier 2 gate bound now until it is green alone. Run `just ratchet`, with its `bind:` line replaced by the suites and mutation run that are bound, or removed while none is, and commit the first thresholds it writes; while the owner has yet to install the hooks it is red, and the thresholds stay as you wrote them. Done when tier 0 and tier 1 are green, every tier 2 gate is green alone, and no `bind:` body is left.

10. **Speed.** Build it in while nothing is slow ([tiers.md](../method/tiers.md#speed)). Turn on the parallel mode of the test runner, provisioned or bound, and of the mutation tool where it is bound, in the committed configuration. Keep the template's `[ceilings.change]` in `quality/thresholds.toml` as it is (ADR 0032); never set it from the adoption's own size. Have each long gate hand `{{shard}}` and `{{shards}}` to its tool. Add a gate to its tier's list at the top of the `justfile` and nowhere else: CI reads the same lists. Run `tier0-tree` and `tier1` three times each; a gate red in parallel and green alone shares state, which tiers.md says how to separate. Fill each `bind:` cache line of the CI templates with this stack's caches, keyed on its lockfiles and tool configs, and keep their shape. Fill the binding's Speed section, one line per concept, saying how this stack will meet it where nothing is bound yet; leave `- Shards: 1`. Run `just budget tier0 --set` and `just budget tier1 --set` once. Take those readings on a quiet machine or the CI runner, and vet each with `pstack:benchmark-checklist`; on a shared machine cap the gates with `RATCHET_JOBS`. Done when the Speed section has no placeholder, three runs of each are green, and `[ceilings.seconds]` has a key per tier.

11. **Records and CI.** Write `docs/design-brief.md` from step 3's answers, dated, and under `## In the owner's words` each question the owner answered here with the answer word for word, after init's answers as `AGENTS.md` and `PRODUCT.md` hold them. Run `mattpocock-skills:domain-modeling` for the ADRs and glossary entries the answers crystallised, and replace `<project>` in `GLOSSARY.md`. When the tree has user-interface surfaces, run `impeccable document` for `DESIGN.md`. When it has none, do not create `DESIGN.md`: write under slice one that the first surface is built with `impeccable shape`, and that an agent runs `impeccable document` once it merges.

    Write the plugin's version (from `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`) and its commit (`git -C "${CLAUDE_PLUGIN_ROOT}" rev-parse HEAD` when that is a checkout, else the latest commit of `Simon-GitHub-Code/ratchet` that changed that file) into the binding's `- Ratchet plugin:` line, and the same commit into every `ref: "<ratchet-sha>"` of `ci.yml`, `deep.yml`, `weekly.yml` and `merge.yml`, so CI and every local tier run the plugin's gates at one version, which `just plugin-pin` and the conformance gate hold. Add the toolchain setup, pinned by commit SHA with the version in a trailing comment, so `just pins` stays green, and set the nightly hour in `deep.yml`. Done when the brief is dated, the glossary names the project, the binding names the plugin's version and commit, and the workflows name no placeholder.

12. **Prove it.** Commit first: the change-size gate knows the adoption by its subjects, and in a bite the change is what the tree holds beyond `HEAD`. Run `conformance` and fix what it names. Run `check`.

    **Rehearse the first slice.** Show that the first feature finds every config it needs, in a throwaway copy that is never committed. Slice one is the one step 11's design brief names. When the brief names none, rehearse the smallest slice the declared types imply (one module, the file `boot` runs and the two tests) and say so in the hand-over. Make a worktree of the adoption's commit outside the repository (`git worktree add --detach "${TMPDIR:-/tmp}/rehearsal" HEAD`), run the `setup` of `quality/bites.toml` in it, and add with the package manager the runtime packages the stack names for slice one. Write the smallest real instance of slice one, one small file each: every kind of code it brings, where `AGENTS.md` places it and in a form its Triggers row counts (`just triggers --count`); the file `boot` runs; one instance of each stack rule that allows something in one place, such as the one module that reads settings; and a unit test and a property test written with the provisioned tools. Run `just snapshots`, `check`, `just test-files` with the two tests, and `boot`: for a type that serves `eval "$(just --evaluate booted)"`, for a `cli`, `job` or `app` the run step 9's table gives its `smoke`. It passes when `check` is red on nothing but `triggers`, the tests fail or pass on their assertions and not on a configuration or an import, the deliverable answers `ready` or its run exits 0, and `PYTHONPATH="${CLAUDE_PLUGIN_ROOT}/hooks" python3 -m ratchet_guards.diff --root . --base HEAD` lists no guard path but the dependency manifest, its lockfile and their snapshots. Any other edit the rehearsal needed is a config the adoption owes, or a key it removed: make it in the adoption, commit, run `check`, and rehearse once more in a fresh worktree. Rehearse at most twice: an edit the second round still needs is not chased, but named with its file for the hand-over. Remove each worktree when its round ends.

    Run `check-deep` once. Its last gate is the proof: the `bite-all` entry point plants each fault of `quality/bites.toml` in a scratch copy and is green only when each gate was green without its fault and red with it. Done when `conformance` and `check-deep` exit 0 and the rehearsal passed, or its second round ended with the edits it still needs named.

13. **Hand over.** Commit what the proof changed, push and open a pull request (with no forge, the change description at `.scratch/changes/<branch>.md`) with every template section filled, and under Gates the `tier0` tail and the guard paths the rehearsal changed. Say how to start the product and open it: `just start` and the address it prints, and on an empty repository that it starts once the first feature brings the file `boot` runs. Under Criticism: every `none` row that applies, every tool you could not check, every assumption of step 5, every answer you could not act on, a rehearsal with no slice one named and each edit its second round still needed, the adoption's measured size, and the owner's hooks command, if any, which `just ratchet`, the route and the feature preflight wait for. Say in one line which rows wait for which trigger, and that the route names `/ratchet:safeguard` when one fires. The adoption changes guard paths, so its merge is the owner's; the path rules switch on with it, and from then on the `merge` workflow (with no forge, `just merge <branch>`) merges what the judge passes.

    Before the route, end the reply with the **Assumed** block the method's rule on asking describes: what kind of software it is, who reaches it, the tools, then step 5's assumptions (how the code is split, the rules every change keeps), and each preference the owner typed as "you asked for". One plain line each, with what changing it later costs and what the owner can say to change it, such as `Checks: Biome tidies the code and oxlint looks for mistakes, both current and fast; ESLint was the other choice. Changing later: a decision record, four checks rewired and shown to work again, and two protected files you approve. Say "use ESLint" to switch.` The block is for the owner: no question key, type name or other method term in it. Then the number of questions the owner answered.

    The last lines are the route: run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/route.py" --root .` in one Bash call and print its lines as they are. Close with `/ratchet:next` on its own line.
