# Adopt the Ratchet method

Load the `ratchet:method` skill first; this skill assumes its vocabulary. Templates live in `${CLAUDE_SKILL_DIR}/templates/` and mirror the repository layout; the `justfile` and `.github/` among them are the `just` and GitHub examples.

## Steps

1. **Check the ground.** The repository is a git repository with a default branch; `claude plugin list` shows `ratchet`, `mattpocock-skills`, `pstack` and `impeccable`; `python3` (3.11 or later) is installed for the plugin's own gates; `docs/agents/issue-tracker.md` exists, which `/mattpocock-skills:setup-matt-pocock-skills` writes and only the owner can run (stop and name that command when it is missing: the feature route reads the tracker it records). Done when all hold or you have told the owner which is missing.

2. **Initialise.** Run `/ratchet:init` unless `AGENTS.md` already opens with its four-plugin stanza. Done when `AGENTS.md` exists and `CLAUDE.md` links to it.

3. **Copy the templates.** Copy every file under `templates/` to the same path in the repository, skipping any that exists and listing the skipped ones for the owner. Done when the listing of `templates/` and the repository agree, and the skip list is reported.

   **Then merge the stack preset.** Read `## Stack` from `PRODUCT.md`, else from `AGENTS.md` (init writes it there when the project has no user interface); without either, recognise the tree (`pyproject.toml` with `uv.lock` is `python-uv`; `package.json` with `pnpm-lock.yaml` is `typescript-pnpm`). When `presets/<stack>/` exists, merge each of its files as `presets/README.md` says: its `justfile` recipes replace the template's `bind:` bodies of the same name, its `binding.md` fills the Runner, the Tool cells, Absolute paths, Limits and Tool versions, its `manifest.toml` paths replace the groups' `# bind:` comments, its `thresholds.toml` is appended, its `ci.yml` steps and cache lines go into every job, its `tools/` stanzas into the project's config files, its `fitness/` scaffold into the fitness directory the manifest names. Then confirm the binding in **one dialog**, recommended answers first: accept the preset's binding as merged (recommended); name the gates whose tool this project changes; or no preset, interview instead. Steps 5 to 8, 10 and 11 then only touch what the preset left open (`bound per project` rows, `bind:` bodies that remain, the Layers contracts). Without a preset, those steps run their interviews as written, and the finished binding is a candidate for the next preset.

4. **Fill `AGENTS.md`.** Through the interactive question dialog, one dialog per topic: the declared paths or layers, if any, with their allowed direction; the non-negotiables, each with the ADR that will hold it and the gate that will enforce it; the stack rules the method leaves open. Delete the Layers section when the project declares none. Done when `AGENTS.md` has no angle-bracket placeholder left.

5. **Choose the runner and the forge.** Fill the binding's Runner and Forge sections. A runner other than `just`: delete the `justfile`, create the same entry points in that runner, and rewrite the Entry points table. A forge other than GitHub: move the pull request template to the path the forge reads and name it in the binding, replace `.github/workflows/` with the forge's CI running `tier0`, `tier1` and `tier2`, and put those paths in the manifest's `ci` group. No forge (no `origin`; the owner kept the repository local at init): delete `.github/`, move the pull request template to `docs/process/change-template.md` and name it in the Forge section as the change template; a change is then a branch whose description is written from that template to `.scratch/changes/<branch>.md` (the branch's `/` written as `-`), and the owner merges it with `git merge --no-ff` once `check` is green. Tier 0 runs from the commit hook, tier 1 as `check` before each merge, tier 2 as `check-deep` on the default branch after it. Write that as an ADR with its refuter (a merge with `check` red or unrun; tier 2 unrun for a week) and the rejected options, and read "push" and "pull request" in steps 10 and 13 that way: nothing is pushed, and step 10 has no workflow to pin. Done when every entry point names a command and the Forge section has no placeholder.

   Two placements the gates depend on. A snapshot of the product's own contract (a CLI's `--help`, a public API report, a schema) changes with the feature that changes the contract, so it lives beside the tests, never under `quality/`: `quality/**` is a guard path for what only rises, and a contract snapshot there can be landed neither ahead of its feature (the default branch goes red) nor with it (an owner-away run stops on the guard edit). And when the `prose` gate flags a word on a glossary *Avoid* list in the owner's own text, reword the text or ask the owner which word the project means; never shorten an *Avoid* list to turn a gate green.

6. **Write the binding.** For each question row of the Gates table, name the tool for this stack, the threshold source and the entry point. A question with no tool in this stack gets `none`, the reason, and the number of the ADR that accepts the gap; write that ADR. Fill Absolute paths and Limits. Done when every Tool cell is filled.

7. **Bind the entry points, tier 0 first.** The method's own gates arrive bound to the plugin's scripts (`markers`, `suppressions`, `prose`, `snapshots`, `snapshots-check`, `commits`, `change-size`, `ratchet-lowered`, `settings-check`, `guard-diff`, `conformance`, `budget`, the tool-neutral half of `pins`, the shipped half of `bite`, `coverage` once the suite writes a Cobertura report, and `mutation-changed` and `mutation` once the mutation tool's output reaches `scripts/mutation_survivors.py`: the register is the gate, the score is a trend); `python3 "$RATCHET_PLUGIN/scripts/bite.py"` shows each of them bite. Replace each remaining `bind:` body with the real command; a `none` row prints its reason and exits 0. Every bound entry point runs green on the skeleton before you move to the next. Tier 0, then tier 1, then tier 2. Done when `tier0` is green and every remaining `bind:` body is listed for the owner with its tier.

8. **Fill the manifest, then generate the permission rules.** Add this stack's tool-config, fitness-test and gate-tool paths to `guards/manifest.toml` so no group is left with an empty `paths` (conformance reports one). Then run `just settings`, which rewrites the `deny` and `ask` lists of `.claude/settings.json` from the finished manifest (one `Edit` rule per pattern, `deny` for a locked group, plus the fixed command rules) and keeps every other key; never edit those two lists by hand. Done when `just settings-check` is green. The path rules of the guard hook come from the manifest as committed on the default branch, so none of this provokes a prompt until the adoption merges.

9. **Records.** Run `mattpocock-skills:grilling` for the design brief (purpose, shape, slice one as checkable items, the explicit out-list) and put each of its rounds through the question tool: one dialog per round, up to four questions, the recommended answer first in every question so the owner accepts a round in a word; facts you can look up are never questions. Then run `mattpocock-skills:domain-modeling` to write the ADRs and glossary entries the rounds crystallised, and record the agreed brief in `docs/design-brief.md`, dated. (`grill-with-docs` is only those two calls, and the Skill tool refuses it.) Replace `<project>` in `GLOSSARY.md` with the project's name. When the tree already has user-interface surfaces (templates, components, screens), run `/impeccable document` so `DESIGN.md` records the incumbent design system; when it has none yet, do not create `DESIGN.md`: write under slice one in the design brief that the first surface's pull request runs `/impeccable shape` and then `/impeccable document`, after which `DESIGN.md` is the record the reviews judge against. Fill ADR 0001 with the plugin version from `$CLAUDE_PLUGIN_ROOT/.claude-plugin/plugin.json` and the commit it was installed from: `git -C "$CLAUDE_PLUGIN_ROOT" rev-parse HEAD` when the plugin directory is a checkout, else the latest commit of `Simon-GitHub-Code/ratchet` that changed `.claude-plugin/plugin.json` (`gh api 'repos/Simon-GitHub-Code/ratchet/commits?path=.claude-plugin/plugin.json&per_page=1' --jq '.[0].sha'`); say in the hand-over which of the two you used. Done when the brief is dated, the glossary names the project and ADR 0001 names the version and the commit.

10. **CI.** Put the commit ADR 0001 names into every `ref: "<ratchet-sha>"` of `ci.yml` and `deep.yml`, so CI runs the plugin's gates at the version this repository adopted, by SHA; `RATCHET_PLUGIN` already points the recipes at that checkout. The template's own actions are pinned and `just pins` is green on it; keep it so for every step the preset or you add: a commit SHA with the version in a trailing comment, images by digest. Done when the workflows parse and name no placeholder.

11. **Speed.** The CI templates arrive cached, split one job per gate and cancelling superseded runs; keep that shape when you bind them. Fill each `bind:` cache line with the dependency directory and the tool caches of this stack, keyed on its lockfiles and tool configs. Run `just budget tier0 --set` and `just budget tier1 --set` once on the skeleton, which records the first ceilings in `quality/thresholds.toml` with headroom and never under the tier's budget (a minute for tier 0, fifteen for tier 1); they only fall from here. Name in the binding's Speed section the ceilings, the cache keys, the shard counts for any suite over the budget you set there, and the affected-only tool if the repository is a monorepo. Done when the Speed section has no placeholder and `[ceilings.seconds]` has a key per tier.

12. **Conformance.** Run the `conformance` entry point. Fix each failure it names. Done when it exits 0.

13. **Hand over.** Commit on a branch as `chore(method): adopt the ratchet method` (the `commits` gate accepts it, and the change-size gate exempts a range made only of such commits and prints the size instead), push, and open a pull request (with no forge, the change description at `.scratch/changes/<branch>.md`) with every template section filled, the `tier0` tail under Gates, and under Criticism, as standing criticisms of the binding: the list of unbound entry points and `none` rows, and the adoption's measured size, which is the counter to the change-size gate for this one change. The tier 0 commit hooks: the copied `.pre-commit-config.yaml` runs `just pre-commit` before each commit and `just commit-msg` on its message, so run `pre-commit install` yourself (`uvx pre-commit install` when the stack does not pin pre-commit); the guard allows it. If it refuses because `core.hooksPath` is set, the owner unsets it (`git config --unset core.hooksPath`), which the guard refuses from an agent as a hook-path change, so the hand-over and the Criticism section name that command for the owner to run once rather than running it. Merging is the owner's too. Say also that the guard's path rules switch on when this pull request merges, since the hook reads the manifest from the default branch.

   Then the route, as the last lines: run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/route.py" --root .` in one Bash call and print its three lines as they are. On the adoption branch they say to wait for the merge; say also what follows it, from [route.md](../method/route.md): `/mattpocock-skills:grill-with-docs` when the design brief or glossary is still thin, else `/mattpocock-skills:to-spec` and `to-tickets` for the first feature, `/ratchet:conjecture` on its ticket, then `/ratchet:feature` or `/pstack:poteto-mode`. Close with `/ratchet:next` on its own line, which prints the step whenever the owner asks.
