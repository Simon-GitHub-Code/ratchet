# Adopt the Ratchet method

Load the `ratchet:method` skill first; this skill assumes its vocabulary. Templates live in `${CLAUDE_SKILL_DIR}/templates/` and mirror the repository layout; the `justfile` and `.github/` among them are the `just` and GitHub examples.

## Two dialogs, one round each

The owner answers two dialogs in a default run, both through the question tool, and nothing else asks them anything. The dogfood run of 2026-11-11 asked seven here, most of them confirming what the preset, `AGENTS.md` and `PRODUCT.md` already said. Each dialog is one round: an answer is recorded as given, and an answer you cannot act on is carried into the hand-over as an open item. `/ratchet:adopt interactive` runs the interviews as the steps describe them instead, one dialog per topic; say the count before the first one.

**Dialog 1, the binding.** Print one table first: the preset chosen and why, each gate the preset leaves "bound per project" with the tool you will bind it to on the walking skeleton (step 7), each row you propose as `none` with its reason, the layers and their direction (the preset's `core` inside, everything else outside, unless the tree shows more), the non-negotiables you propose with the gate that enforces each, and the telemetry and flag seams. Then up to four questions, recommended answers first: accept the table; the gates whose tool this project changes; a layer or non-negotiable to add; who may turn a flag on in production.

**Dialog 2, the design brief.** Draft the brief from what is already written (`AGENTS.md`'s purpose, `PRODUCT.md`, the README, the code) and ask one round of up to four questions on what no record answers: slice one as checkable items, the explicit out-list, and at most two decisions that would be hard to reverse. A deeper interview is the owner's `/mattpocock-skills:grill-with-docs`, whenever they want one; adoption does not wait for it.

## Steps

1. **Check the ground.** The repository is a git repository with a default branch; `claude plugin list` shows `ratchet`, `mattpocock-skills`, `pstack` and `impeccable`; `python3` (3.11 or later) is installed for the plugin's own gates; `docs/agents/issue-tracker.md` exists, which `/mattpocock-skills:setup-matt-pocock-skills` writes and only the owner can run (stop and name that command when it is missing: the feature route reads the tracker it records). When the only uncommitted files are the records that setup wrote (`docs/agents/**` and its `## Agent skills` section of `AGENTS.md`), commit them as `chore(tracker): record the issue tracker` before anything else, so adoption starts on a clean default branch. Done when all hold or you have told the owner which is missing.

2. **Initialise.** Run `/ratchet:init` unless `AGENTS.md` already opens with its four-plugin stanza. Done when `AGENTS.md` exists and `CLAUDE.md` links to it.

3. **Copy the templates.** Copy every file under `templates/` to the same path in the repository, skipping any that exists and listing the skipped ones for the owner. Done when the listing of `templates/` and the repository agree, and the skip list is reported. Check also that `.gitignore` holds every line of the init skill's `templates/gitignore` (a repository initialised before it existed lacks them), and append the missing ones.

   **Then merge the stack preset.** Read `## Stack` from `PRODUCT.md`, else from `AGENTS.md` (init writes it there when the project has no user interface); without either, recognise the tree (`pyproject.toml` with `uv.lock` is `python-uv`; `package.json` with `pnpm-lock.yaml` is `typescript-pnpm`). When `presets/<stack>/` exists, merge each of its files as `presets/README.md` says: its `justfile` recipes replace the template's `bind:` bodies of the same name, its `binding.md` fills the Runner, the Tool cells, Absolute paths, Limits and Tool versions, its `manifest.toml` paths replace the groups' `# bind:` comments, its `thresholds.toml` is appended, its `ci.yml` steps and cache lines go into every job, its `tools/` stanzas into the project's config files, its `fitness/` scaffold into the fitness directory the manifest names. Then confirm the binding in dialog 1, recommended answers first: accept the table (recommended); name the gates whose tool this project changes; or no preset, interview instead. Steps 5 to 8, 10 and 11 then only touch what the preset left open (`bound per project` rows, `bind:` bodies that remain, the Layers contracts). Without a preset, those steps run their interviews as written, and the finished binding is a candidate for the next preset.

4. **Fill `AGENTS.md`.** From dialog 1's answers, with no further question: the declared paths or layers, if any, with their allowed direction; the non-negotiables, each with the ADR that will hold it and the gate that will enforce it; the stack rules the method leaves open. Delete the Layers section when the project declares none. Done when `AGENTS.md` has no angle-bracket placeholder left.

5. **Choose the runner and the forge.** Fill the binding's Runner and Forge sections. A runner other than `just`: delete the `justfile`, create the same entry points in that runner, and rewrite the Entry points table. A forge other than GitHub: move the pull request template to the path the forge reads and name it in the binding, replace `.github/workflows/` with the forge's CI running `tier0`, `tier1` and `tier2`, and put those paths in the manifest's `ci` group. No forge (no `origin`; the owner kept the repository local at init): delete `.github/`, move the pull request template to `docs/process/change-template.md` and name it in the Forge section as the change template; a change is then a branch whose description is written from that template to `.scratch/changes/<branch>.md` (the branch's `/` written as `-`), and the owner merges it with `git merge --no-ff` once `check` is green. Tier 0 runs from the commit hook, tier 1 as `check` before each merge, tier 2 as `check-deep` on the default branch after it. Write that as an ADR with its refuter (a merge with `check` red or unrun; tier 2 unrun for a week) and the rejected options, and read "push" and "pull request" in steps 10 and 13 that way: nothing is pushed, and step 10 has no workflow to pin. Done when every entry point names a command and the Forge section has no placeholder.

   Two placements the gates depend on. A snapshot of the product's own contract (a CLI's `--help`, a public API report, a schema) changes with the feature that changes the contract, so it lives beside the tests, never under `quality/`: `quality/**` is a guard path for what only rises, and a contract snapshot there can be landed neither ahead of its feature (the default branch goes red) nor with it (an owner-away run stops on the guard edit). And when the `prose` gate flags a word on a glossary *Avoid* list in the owner's own text, reword the text or ask the owner which word the project means; never shorten an *Avoid* list to turn a gate green.

6. **Write the binding.** For each question row of the Gates table, name the tool for this stack, the threshold source and the entry point. A question with no tool in this stack gets `none`, the reason, and the number of the ADR that accepts the gap; write that ADR. Fill Absolute paths and Limits, the Limits with the load numbers (the arrival rate, the percentile latency and the error rate the `load` gate holds; the concurrency and seconds of the `load-smoke`). Fill the Telemetry and Feature flags sections: the module that starts the telemetry SDK and through which every entry point is registered, the attributes a span carries and the ones it never does, the module through which a flag is read and the override it honours. Done when every Tool cell is filled and neither section holds a placeholder.

   **A row waits for nothing.** `none` is for a property the project will never have (no user interface, no persisted data by design, a library with nothing to serve). A row whose tool needs code that does not exist yet is bound now, against the walking skeleton of step 7. The dogfood run of 2026-11-11 bound four rows as "none until the first route", and the first owner-away feature stopped at its spec stage on exactly those four, as guard edits only the owner could make.

7. **Bind the entry points, tier 0 first.** The method's own gates arrive bound to the plugin's scripts (`markers`, `suppressions`, `prose`, `snapshots`, `snapshots-check`, `commits`, `change-size`, `ratchet-lowered`, `settings-check`, `guard-diff`, `conformance`, `budget`, the tool-neutral half of `pins`, the shipped half of `bite`, `coverage` once the suite writes a Cobertura report, and `mutation-changed` and `mutation` once the mutation tool's output reaches `scripts/mutation_survivors.py`: the register is the gate, the score is a trend); `python3 "$RATCHET_PLUGIN/scripts/bite.py"` shows each of them bite. Replace each remaining `bind:` body with the real command; a `none` row prints its reason and exits 0.

   **The walking skeleton.** On a repository with no code yet, write the thinnest deliverable every gate can run against, so that the first feature changes no gate: the package with its `core` path; one health entry point registered through the telemetry seam, and the telemetry test that reads its span from the in-memory exporter; the flag seam with its override and the empty `flags.toml`; the `smoke` and `load-smoke` recipes on its boot command; one end-to-end test; the contract snapshot beside the tests when the stack publishes a contract; the container file when the deliverable is an image, so `iac` and `artefact-scan` judge the real thing; and one test of each kind a preset recipe is red without (a benchmark, a fuzz property, and where the project has them an end-to-end and an accessibility test). Then run `just ratchet` once and commit what it writes: the first thresholds, snapshots and public-surface report. A repository with code binds the same rows against what exists.

   Every bound entry point runs green on the skeleton before you move to the next. Tier 0, then tier 1, then tier 2: a tier 2 recipe that is red on the skeleton is a defect of the binding, fixed before the hand-over, never left for the first feature. Done when `tier0` is green and every remaining `bind:` body is listed for the owner with its tier.

8. **Fill the manifest, then generate the permission rules.** Add this stack's tool-config, fitness-test and gate-tool paths to `guards/manifest.toml` so no group is left with an empty `paths` (conformance reports one). Then run `just settings`, which rewrites the `deny` and `ask` lists of `.claude/settings.json` from the finished manifest (one `Edit` rule per pattern, `deny` for a locked group, plus the fixed command rules) and keeps every other key; never edit those two lists by hand. Done when `just settings-check` is green. The path rules of the guard hook come from the manifest as committed on the default branch, so none of this provokes a prompt until the adoption merges.

9. **Records.** Write the design brief (purpose, shape, slice one as checkable items, the explicit out-list) from dialog 2's answers; facts you can look up are never questions, and `mattpocock-skills:grilling` runs its rounds only in `interactive` mode, one dialog per round. Then run `mattpocock-skills:domain-modeling` to write the ADRs and glossary entries the rounds crystallised, and record the agreed brief in `docs/design-brief.md`, dated. (`grill-with-docs` is only those two calls, and the Skill tool refuses it.) Replace `<project>` in `GLOSSARY.md` with the project's name. When the tree already has user-interface surfaces (templates, components, screens), run `/impeccable document` so `DESIGN.md` records the incumbent design system; when it has none yet, do not create `DESIGN.md`: write under slice one in the design brief that the first surface's pull request runs `/impeccable shape` and then `/impeccable document`, after which `DESIGN.md` is the record the reviews judge against. Fill ADR 0001 with the plugin version from `$CLAUDE_PLUGIN_ROOT/.claude-plugin/plugin.json` and the commit it was installed from: `git -C "$CLAUDE_PLUGIN_ROOT" rev-parse HEAD` when the plugin directory is a checkout, else the latest commit of `Simon-GitHub-Code/ratchet` that changed `.claude-plugin/plugin.json` (`gh api 'repos/Simon-GitHub-Code/ratchet/commits?path=.claude-plugin/plugin.json&per_page=1' --jq '.[0].sha'`); say in the hand-over which of the two you used. Done when the brief is dated, the glossary names the project and ADR 0001 names the version and the commit.

10. **CI.** Put the commit ADR 0001 names into every `ref: "<ratchet-sha>"` of `ci.yml` and `deep.yml`, so CI runs the plugin's gates at the version this repository adopted, by SHA; `RATCHET_PLUGIN` already points the recipes at that checkout. The template's own actions are pinned and `just pins` is green on it; keep it so for every step the preset or you add: a commit SHA with the version in a trailing comment, images by digest. Done when the workflows parse and name no placeholder.

11. **Speed.** The CI templates arrive cached, split one job per gate and cancelling superseded runs; keep that shape when you bind them. Fill each `bind:` cache line with the dependency directory and the tool caches of this stack, keyed on its lockfiles and tool configs. Run `just budget tier0 --set` and `just budget tier1 --set` once on the skeleton, which records the first ceilings in `quality/thresholds.toml` with headroom and never under the tier's budget (a minute for tier 0, fifteen for tier 1); they only fall from here. Name in the binding's Speed section the ceilings, the cache keys, the shard counts for any suite over the budget you set there, and the affected-only tool if the repository is a monorepo. Done when the Speed section has no placeholder and `[ceilings.seconds]` has a key per tier.

12. **Conformance.** Run the `conformance` entry point. Fix each failure it names. Done when it exits 0.

13. **Hand over.** Commit on a branch as `chore(method): adopt the ratchet method` (the `commits` gate accepts it, and the change-size gate exempts a range made only of such commits and prints the size instead), push, and open a pull request (with no forge, the change description at `.scratch/changes/<branch>.md`) with every template section filled, the `tier0` tail under Gates, and under Criticism, as standing criticisms of the binding: the list of unbound entry points and `none` rows, and the adoption's measured size, which is the counter to the change-size gate for this one change. The tier 0 commit hooks: the copied `.pre-commit-config.yaml` runs `just pre-commit` before each commit and `just commit-msg` on its message, so run `pre-commit install` yourself (`uvx pre-commit install` when the stack does not pin pre-commit); the guard allows it. If it refuses because `core.hooksPath` is set, read where with `git config --show-origin --get core.hooksPath` (a read, which the guard allows) and name the one command that fits, for the owner to run once, since the guard refuses each of them from an agent as a hook-path change. Set in this repository's own config: `git config --unset core.hooksPath`. Set globally to a directory whose hooks chain to the repository's `.git/hooks` (read one to see): `GIT_CONFIG_GLOBAL=/dev/null pre-commit install`, which writes the repository's hooks and leaves the global setting alone. Set globally to hooks that do not chain: `git config --global --unset core.hooksPath`, or the owner adds the chain. Until `.git/hooks/pre-commit` and `.git/hooks/commit-msg` exist, tier 0 does not run on commit: say so as the first line of the hand-over and of the Criticism section, and run `just pre-commit` and `just commit-msg` by hand before each commit of your own. Merging is the owner's too. Say also that the guard's path rules switch on when this pull request merges, since the hook reads the manifest from the default branch.

   Then the route, as the last lines: run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/route.py" --root .` in one Bash call and print its three lines as they are. On the adoption branch they say to wait for the merge; say also what follows it, from [route.md](../method/route.md): `/mattpocock-skills:grill-with-docs` when the design brief or glossary is still thin, else `/mattpocock-skills:to-spec` and `to-tickets` for the first feature, `/ratchet:conjecture` on its ticket, then `/ratchet:feature` or `/pstack:poteto-mode`. Close with `/ratchet:next` on its own line, which prints the step whenever the owner asks.
